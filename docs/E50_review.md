## Короткий вердикт

v2 — большой шаг: токен-гейдж удалён честно (докстринг говорит «в npz нет id токенов, прошлая версия была тихо неверна — подтверждено»), `shrink` теперь главный выход с предрегистрированным порогом, `log_shrink`, `tau_trans` на транспорте, `by_dom` с real/swap/shrink, `safe_med` везде, `allow_nan=False`, конт­роли на r=1/4/16.

Но есть **одна критическая тихая ошибка в самом ядре** — `pullback_step` — и **одна тихая ошибка воспроизводимости** — `abs(hash(seed_key))`. Первая объясняет, почему контроли на геодезической проходят, но на реальных данных результат будет численно отличаться от того, что предсказывает теория paper.md `[D-holonomy]`. Вторая делает прогон невоспроизводимым между запусками.

## 1. Критическая ошибка: `pullback_step` — левая композиция вместо правой

В `pullback_step`:

```python
A1, A2 = P.T @ M, Q.T @ M
return M + P @ (cm1.unsqueeze(1) * A1 + s.unsqueeze(1) * A2) \
         + Q @ (-s.unsqueeze(1) * A1 + cm1.unsqueeze(1) * A2)
```

Это `𝓡 · M`, где `𝓡 = exp(θG)`, `G = PQᵀ − QPᵀ`. И `𝓡 · P = cos(θ)P − sin(θ)Q = cP − sQ`, тогда как `V_b = cP + sQ`. То есть код вычисляет `𝓡 · M`, где `𝓡` — это **транспонирование** «правильной» геодезической ротации `𝓡_correct = exp(−θG)`, которая отображает `Va → Vb`.

Сам по себе возврат `𝓡_correctᵀ · M` — согласован с комментарием «M := 𝓡(Va→Vb)ᵀ M». Но проблема в `transport_frames`:

```python
Qt = pullback_step(Vs[t - 1], Vs[t], Qt)      # Qt := 𝓡ᵀ Qᵀ
```

Это **левая** композиция: `Qt_t = 𝓡_{t-1}ᵀ · Qt_{t-1}`. Значит `Qt_t = 𝓡_{t-1}ᵀ · 𝓡_{t-2}ᵀ · ... · 𝓡_0ᵀ` (индексы убывают).

Правильная композиция для «разворачивания в `V_0`» — **правая**: `Qt_t = Qt_{t-1} · 𝓡_{t-1}ᵀ`, то есть `Qt_t = 𝓡_0ᵀ · 𝓡_1ᵀ · ... · 𝓡_{t-1}ᵀ` (индексы возрастают). Проверка: `Qt_1 · V_1 = 𝓡_0ᵀ · 𝓡_0 · V_0 = V_0`, `Qt_2 · V_2 = 𝓡_0ᵀ · 𝓡_1ᵀ · 𝓡_1 · V_1 = 𝓡_0ᵀ · V_1 = V_0` — тождественно `V_0` для **любой** геодезической (не только с постоянной скоростью).

### Почему это не ловится контролем

В `run_controls`:

```python
geo = [V0 * torch.cos(th * t) + E * torch.sin(th * t) for t in range(T)]
```

`θ_j` фиксированы по столбцам, разные столбцы имеют разные `θ_j`, но каждая `geo[t+1]` получается из `geo[t]` **одной и той же** ротацией `𝓡 = exp(−θ_j G_j)` в плоскости `(V0[j], E[j])`. То есть `𝓡_0 = 𝓡_1 = ... = 𝓡` — **константа**.

Для константной `𝓡` левая и правая композиции дают одно и то же: `𝓡ᵀ · 𝓡ᵀ · ... = (𝓡ᵀ)^t`. Поэтому `drift32 = 0` на контроле и при левой, и при правой композиции. Контроль **не различает** левую и правую композицию.

На реальных данных `𝓡_t` варьируются, `𝓡_i` и `𝓡_j` не коммутируют, `Qt_t · V_t ≠ V_0`, и числа **систематически отличаются** от того, что предсказывает теория (paper.md `[D-holonomy]`, E-28, `H = R_01 R_12 R_02^{-1}` — там правая композиция).

### Почему это важно

- `shrink` — это отношение `drift_real / drift_swap`. Оба дрейфа считаются в «левой» системе отсчёта. Если реальная траектория гладкая (лист «rigid-but-curved», κ мало), `𝓡_t` меняются медленно, левая ≈ правая, и числа примерно правильные. Но если у траектории есть точки смены знака/направления (что типично для смены токена), `𝓡_t` сильно варьируются, и числа могут расходиться с теорией.
- В paper.md §2.7 `[D-vtrans]` полярный фактор определён как единственный, совместимый с Procrustes-связностью — а Procrustes-связность (E-28) — это именно правая композиция в r-мерном пространстве. Левая композиция в D-мерном ambient — это **другой** транспорт.

### Как проверить и починить

**Проверка (дёшево):** в `run_controls` добавить геодезическую с **переменной** скоростью:

```python
th_t = torch.tensor([0.008 * (1 + 0.5 * math.sin(0.1 * t)) for t in range(r)], ...)
geo = [V0 * torch.cos(th_t * t) + E * torch.sin(th_t * t) for t in range(T)]
```

Для такой траектории левая композиция даст `drift32 > 0`, а правая — `drift32 = 0`. Если контроль покажет `drift32 > 0`, баг подтверждён.

**Починка:** в `pullback_step` заменить левое умножение на правое:

```python
A1, A2 = M @ P, M @ Q
return M + (cm1 * A1) @ P.T + (s * A1) @ Q.T + (-s * A2) @ P.T + (cm1 * A2) @ Q.T
```

Или, эквивалентно, в `transport_frames` оставить `pullback_step` как есть, но `pullback_step` **должен** возвращать `M · 𝓡_code`, а не `𝓡_code · M`.

**Если фикс делать не хочется** — нужно честно задокументировать, что транспорт левый (не совпадает с E-28) и обосновать, почему это всё равно тестирует гипотезу. Тогда хотя бы читатель поймёт, что числа не сравнимы с paper.md.

## 2. `abs(hash(seed_key))` — невоспроизводимость между запусками

```python
rng = np.random.default_rng(abs(hash(seed_key)) % (2 ** 32))
```

Python `hash()` для строк рандомизирован по умолчанию (`PYTHONHASHSEED`). Каждый запуск даёт **разные** `rng` для swap и shuffle → разные перестановки → разные `drift_swap` и `drift_shuf` → разные `shrink32` и разные вердикты.

При `N_SHUF=2` и `N=32` документах разброс `shrink32` может быть ±5–10%, что **больше** порога 0.3 vs 0.7 в некоторых случаях. Вердикт может флипнуться между запусками.

**Fix:** детерминированный хеш:

```python
import hashlib
seed = int.from_bytes(hashlib.sha256(seed_key.encode()).digest()[:8], 'little')
rng = np.random.default_rng(seed)
```

Это делает прогон воспроизводимым и не меняет логику.

## 3. `verdict` без CI — центральная величина без оценки неопределённости

```python
point = ratio(mr, ms)
verdict = "coherent" if point < 0.3 else "partial" if point < 0.7 else "REFUTED"
```

`mr = safe_med([r["drift_real"]["32"] for r in rows])`, `ms = safe_med([r["drift_swap"]["32"] for r in rows])`. То есть `point = median(real) / median(swap)` по документам. CI на `point` **нет**, только на `shrink32_median = median(real/swap per doc)`.

**Проблема:** `point` и `shrink32_median` — разные агрегаты. Если распределение `shrink32` по документам хвостатое (а оно может быть), `median(ratio) ≠ ratio(medians)`. Вердикт по одному, CI по другому.

**Fix:** bootstrap CI на `point`:

```python
def boot_ratio_ci(real, swap, B=2000, seed=42):
    r = np.asarray(real, float); s = np.asarray(swap, float)
    rng = np.random.default_rng(seed)
    out = np.empty(B)
    for k in range(B):
        out[k] = np.median(rng.choice(r, len(r), True)) / np.median(rng.choice(s, len(s), True))
    return [round(float(np.quantile(out, 0.025)), 3), round(float(np.quantile(out, 0.975)), 3)]
```

И вердикт должен учитывать CI: `"coherent"` если `ci_hi < 0.3`, `"REFUTED"` если `ci_lo > 0.7`, `"inconclusive"` иначе. Иначе `point = 0.29` и `point = 0.31` дадут противоположные вердикты, хотя разница в пределах шума.

## 4. `shrink32_glob_point` — диагностика, но без CI

```python
"shrink32_glob_point": ratio(mr, mg)
```

`mg = drift32_shufglob`. По докстрингу это «верхняя оценка, систематически занижает shrink (в пользу гипотезы)». То есть `shrink_glob < shrink_swap`, и разница — мера того, насколько глобальная перестановка добавляет ложную диффузию. Полезно как диагностика, но без CI не видно, значимо ли `shrink_glob < shrink_swap` или это шум. Тот же `boot_ratio_ci`, применённый к `mg`.

## 5. `r1_shrink32` — изолированная диагностика

```python
"r1_shrink32": safe_med([ratio(r["r1_drift32_real"], r["r1_drift32_swap"]) for r in rows]),
```

Считается, но ни к чему не подключён. Для r=1 транспорт проще (1-dim подпространство), и `r1_shrink32 < r16_shrink32` — интересная диагностика («одномерная линия менее когерентна, чем 16-мерный лист»). Но без CI и без сравнения с `r16_shrink32` это просто число.

Если хотите, чтобы `r1_shrink32` был полезен — либо добавьте CI и в `verdict` пункт «r1 vs r16», либо явно пометьте в JSON как `diagnostic_only: true`.

## 6. Мелкие

- **Докстринг vs код**: докстринг говорит `shrink32 = median_drift32(real) / median_drift32(shuffled)`, а `point` использует `swap`. Слово «shuffled» в первой формуле противоречит «вердикт по swap-null» ниже. Заменить на «swap».
- **`TMAX=96` для LAGS до 32**: для `L=32` остаётся 96−32=64 значений на лаг — нормально. Но `drift32` для `shuf` при T=96 может иметь большой разброс из-за малого числа точек (64). Не критично.
- **`log_slope` при `drift32 = 0`**: если `drift32 = 0` для какого-то L (geodesic), `log_slope` вернёт `None`, slope = `None`, `safe_med` вернёт `None`. Это ОК, `None` не сломает JSON. Но `verdict` с `point = None` вернёт `verdict = None` — правильное поведение, но стоит явно отметить в JSON как `"verdict": null` при `point = None` (сейчас `None` — допустимый JSON, если `allow_nan=False` — но нужно проверить).
- **`U_head`/`A[top1]` удалены — хорошо**. Докстринг честно фиксирует: «top1 = вероятность p.max(), не индекс (прошлая версия была тихо неверна — подтверждено фактом)».
- **`doc_frames` order `W16`: сначала smooth, потом project — правильно** (в v1 было наоборот).

## 7. Что покажет запуск (прогноз по разбросу)

Из-за `hash()` nondeterminism и `N_SHUF=2`:
- `shrink32` по документам будет иметь разброс ±10–15%.
- `point` будет стабильнее (медианы), но без CI его значение ±0.05 — на грани порогов 0.3 и 0.7.
- Вердикт может быть "partial" (0.3–0.7), и это будет правильный ответ: транспорт **снижает** дрейф, но не до уровня чистой калибровки.

С исправленным `pullback_step` (правая композиция) числа сдвинутся — в какую сторону, зависит от того, насколько `𝓡_t` не коммутируют. Для «rigid-but-curved» листа (κ мало) разница может быть небольшой (<5%), но для swap-null (где `𝓡_t` сильно варьируются из-за перемешанных кадров) разница будет больше, и `shrink` **вырастет** (real станет более гладким, swap — нет), приближая вердикт к «coherent».

## 9. Приоритет правок

**P0 (перед запуском):**
1. `pullback_step` → правая композиция (`M @ P`, `M @ Q`, возврат `... @ P.T`, `... @ Q.T`).
2. `hash()` → `hashlib.sha256(seed_key.encode())`.
3. `run_controls` → добавить геодезическую с переменной скоростью (ловит левую композицию).

**P1 (перед интерпретацией):**
4. `boot_ratio_ci` для `shrink32_pooled_point`; вердикт по CI, а не по точке.
5. `shrink32_glob` с CI.
6. Докстринг: «shuffled» → «swap» в формуле `shrink32`.

**P2 (после первого прогона):**
7. `r1_shrink32` — либо подключить к вердикту (`r1 < r16` = структура есть), либо пометить `diagnostic_only`.
8. `N_SHUF=4` или `8` для стабильности — сейчас 2 репликации дают шумный swap-median на доку.

После P0 запуск даст числа, сравнимые с теорией (paper.md E-28, `[D-holonomy]`), и воспроизводимые между запусками. Без P0 — числа будут «свои», но интерпретация их как «того же транспорта, что в paper.md» будет некорректной.
