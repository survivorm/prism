# Маршруты переноса: что не исчерпано, что закрыто, когда останавливаться

Дата: 15.11.2026. Написано после того, как torch.xpu на iGPU не взлетел за три круга
(импорт, loader, рантайм) — чтобы дальше не повторять одни и те же круги, а иметь
явный список маршрутов и **условия остановки**.

## Статус маршрутов

| # | Маршрут | Статус | Основание (что известно, а не предположено) |
|---|---|---|---|
| 0 | **torch.xpu** (Intel XPU backend) | **закрыт по факту** | импорт чинится (loader), но `device_count == 0`; `sycl-ls` тоже падал ⇒ карту не видит ни тот, ни другой рантайм одновременно. Установлено: системный oneAPI **2026.0** и пип-овский **2025.2.1** несовместимы (один тег символов `LIBUR_LOADER_0.12`, разные наборы символов) ⇒ «тень рантайма». Остался один дешёвый выстрел: `install_xpu_torch.sh --recreate --runtime system` (torch **без** пип-oneAPI ⇒ системный рантайм). **Таймбокс: один вечер — и закрываем.** |
| 1 | **Свой SYCL-прибор** (`icpx -fsycl` + C ABI + ctypes) | **основной** | у вас **уже работает** llama.cpp-SYCL на этом же Iris Xe (prefill 174–307 tok/s) ⇒ тот же SYCL-стек рабочий. Не проверено мной: компиляция icpx (в песочнице нет), перечисление устройств **моим** кодом, скорость fp32 GEMM, корректность C ABI. ⇒ решающий дешёвый тест — `probe/probe_sycl_min.cpp` (одна команда, ~15 мин). |
| 2 | **OpenCL напрямую** (ICD есть: `/etc/OpenCL/vendors/intel.icd`) | не начат | запасной путь, если SYCL-перечисление не видит карту: `ONEAPI_DEVICE_SELECTOR=opencl:gpu`, либо прямой OpenCL через ctypes/pyopencl. |
| 3 | **Прямой Level Zero** (через ctypes) | не начат | драйвер на месте: `libze_loader.so.1`, `libze_intel_gpu.so.1.17.39758`. Компилятор не нужен. Но GEMM руками — большой объём ⇒ только если 1-2 закрыты, а нужен именно L0. |
| 4 | **oneMKL с GPU-бэкендом** | не начат | `/opt/intel/oneapi/mkl/2026.0/lib` уже в системе ⇒ можно взять готовый GEMM вместо своего ядра (остаются softmax/редукции). |
| 5 | **Не переносить: T4/Kaggle** | не начат, **самый дешёвый по усилию** | инфраструктура T4 уже есть. CPU-форвард E-45 = **51.7 с** ⇒ на T4 форварды ускоряются на порядок **без iGPU вообще**. Для «ускорить эксперименты» это может быть выгоднее всего. |
| 6 | **Статистическая экономия** вместо вычислений | не начат | пересчёт AT0_4/AT0_5 по пре-регистрации v4: ≤12 невырожденных доков, burst-доки — отдельный estimand, пер-доковое правило ⇒ меньше прогонов при лучшей честности. Не требует GPU. |

## Что делать ПРЯМО СЕЙЧАС (по цене)

1. **МАРШРУТ 0 (torch.xpu) ЗАКРЫТ — не тратим на него время.**
   Основания (проверены на машине): `device_count == 0` при любом сочетании
   рантаймов; системный oneAPI 2026.0 и пип-овский 2025.2.1 несовместимы при
   одном теге символов `LIBUR_LOADER_0.12`; XPU-сборок torch новее 2.9.1 нет.
   ⇒ **Зонд `probe/probe_xpu_pipeline.py` убран из дефолтного прогона** и включается
   только явно (`bash run_local.sh --with-xpu`): он отвечает на вопрос про torch.xpu,
   а не про «видит ли мой код карту», и в дефолте даёт только повтор selftest-эталона
   (он уже в pytest) и CPU-базу dense-пути (самая долгая часть прогона, уже измерена:
   base_pre 73.7 с, dense_metrics 125.8 с).
2. **15 минут** — `mkdir -p build && icpx -fsycl -O2 -std=c++20 probe/probe_sycl_min.cpp -o build/probe_sycl_min && ./build/probe_sycl_min`
   **СТАТУС (16.11.2026): карта ВИДНА моему SYCL-коду** (3 устройства: Iris Xe / CPU /
   Iris Xe — две записи GPU означают два бэкенда одной карты), fp32 GEMM = 70.8 GFLOP/s
   даже наивным ядром ⇒ dense-путь окупается. **НО `aspect::fp64` на карте = НЕТ** ⇒
   DPC++ не соберёт ни одного ядра с `double` ⇒ device-код переведён на fp32, а
   R/A-split closure (G6) считается на хосте в fp64 (на устройстве она неразрешима:
   шум fp32 ~1e-6·scale при closure ~1e-13).
3. **Сборка настоящей библиотеки (30–60 мин):**
   `CXX=icpx cmake -B build -DPRISM_SYCL_STATIC_STDCXX=ON -S . && cmake --build build -j`
   ⇒ `build/libprism_sycl.so`; затем
   `PRISM_SYCL_LIB=build/libprism_sycl.so python3 py/test_parity.py`.
   **Если падает загрузка с `GLIBCXX_3.4.31 not found`** ⇒ это несовместимость libstdc++
   (conda-python старше системного g++), а не дефект кода: либо пересоберите со статической
   линковкой (она включена по умолчанию), либо гоняйте под тем же python'ом, которым собрано,
   либо укажите `PY=/path/to/python-with-numpy`.
   (без `mkdir -p build` линкер падает: icpx **не создаёт** выходной каталог)
   Проба сама выдаёт вердикт: сравнивает **тайлованное** fp32-ядро (16×16, локальная
   память) с CPU-базой 28 GFLOP/s ⇒ ≥50 GFLOP/s = «dense-путь окупается».
   Наивное ядро печатается рядом (нижняя граница) и служит базой для отношения fp64/fp32.
   (маршрут 1, решающий тест). Три ответа сразу: устройство видно? fp32 GFLOP/s? fp64 GFLOP/s?
   Это заменяет целый круг возни с torch, потому что **тот же стек у вас работает**.
3. **Параллельно, без GPU** — пре-регистрация v4 (burst-критерий `cv_du > 0.5`,
   пер-доковое правило, n ≥ 12, null-слой ≥ 1e4) и клетка R1′. Наука не зависит от iGPU.

## Условия остановки (зафиксированы заранее, чтобы не спорить постфактум)

| результат | решение |
|---|---|
| `probe_sycl_min` → `DEVICE_MISSING` | iGPU-трансфер **закрыт**; дальше маршрут 5 (T4) + маршрут 6 (статистика) |
| fp32 GEMM < 50 GFLOP/s | перенос dense-пути E-45 **не окупается** (нужно ≥ 10× к CPU-базе); остаётся только прибор/нулевой слой |
| fp64 < fp32/32 | fp64-редукции **не переносятся** ⇒ lse/max — частичные fp32 + объединение fp64 |
| `torch.xpu` не взлетел за один вечер | маршрут 0 закрыт окончательно, iGPU-тема закрыта |
| AT0_4 после пересчёта по v4 всё ещё неустойчив к правилу агрегации | линия идёт по **пре-регистрации и мощности**, а не по ускорению |
