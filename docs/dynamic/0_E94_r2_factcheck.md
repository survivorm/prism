(`~/work/llama.cpp`, HEAD `0b8cfb8fe`). Это ответ на ревью-луп r2 и техническая база для ТЗ r3.

  prompt-позиции — не сервер.
- ⚠ Замечание к ревью A (r2): цитируемые им идентификаторы **`completion_level`, `tokenize_start`,

  Вывод ревьюера («prompt-позиций в ответе нет») совпадает с реальностью, но его номера строк/имён
  не воспроизводятся → в r3 опираемся только на строки из этого файла-отчёта.

## 2. Учёта logit-распределений: `llama-perplexity --save-all-logits` — единственный patchless-путь,
   и у него жёсткие ограничения, которые ТЗ r2 не учитывал

- Флаг реален: `common/arg.cpp:2514` (`--save-all-logits`, алиас `--kl-divergence-base`).
- Формат файла (`tools/perplexity/perplexity.cpp:460-525, 619-620`):
  magic `"_logits_"` (8 B) → `int32 n_ctx` → `int32 n_vocab` → `int32 n_chunk` →
  `int32 tokens[n_chunk*n_ctx]` (**поток id, который реально скорил движок** — выравнивание проверяется
  по файлу, а не угадывается) → далее на позицию `nv = 2*((n_vocab+1)/2)+4` значений `uint16`
  (квантованные log-probs + 2 float в хвосте: logprob и prob истинного токена).
  ⇒ полное распределение доступно, но **квантовано до uint16** → шумовой пол margin/p1 надо измерять
  на валидации декодера, а не предполагать f32-точность.
- **Окно записи**: пишутся только позиции `first .. n_ctx-2`, где `const int first = n_ctx/2`
  (`perplexity.cpp:544`, вызов `process_logits(..., n_ctx - 1 - first, ...)` `perplexity.cpp:617-620`).
  ⇒ позиции 0..n_ctx/2−1 в файл не попадают вообще.
- **Минимальная длина**: `if (int(tokens.size()) < 2*n_ctx)` → отказ (`perplexity.cpp:480-484`).
  ⇒ 448-токенный док при `-c 512` не принимается; нужно **дополнение (padding) до ≥2·n_ctx**.
- Следствие (корректность): chunk 0 начинается с токена 0, модель каузальна ⇒ p1 на позиции t внутри
  chunk 0 = настоящая full-context p1, независимо от дополнения. Покрытие позиций 0..447 достигается
  **лестницей** `n_ctx ∈ {64, 256, 512}` (покрывает t ≥ 32, 128, 256 соответственно), дополнение — повтор
  того же текста до ≥2·n_ctx; из файла берём только chunk 0 и только позиции, где id-поток файла
  совпадает с CPU id-потоком (иначе позиция не сравнима — это и есть наш измеренный tokenizer-drift).
- Ресурс: ≈ `nv*2 B ≈ 496 KB` на позицию ⇒ при `n_ctx=512` (255 позиций) ≈ **126 MB на запуск**;
  6 доков × 3 конфигурации ≈ 2.3 GB суммарно, при стрим-парсинге и немедленном `unlink` пик ≈ 130 MB.
  ⚠ `/home` занят на 97% (14 G свободно) → логины писать в `/tmp` (15 G) и удалять в том же шаге.
- Валидация декодера (гейт, а не доверие): восстановленная из файла картина должна воспроизвести
  **собственный PPL**, который `llama-perplexity` печатает в stdout (та же порция позиций); расхождение
  больше 1e-3 → декодер неверен → STOP.

## 3. Ошибочные/лишние ходы, которые r2 допускал

- `/v1/chat/completions` с raw-`prompt` в этом форке не работает (raw-prompt принимает `/completion`);
  любой импровизационный переход на chat-эндпоинт ломает идентичность промпта (чат-обёртка) —
  в r3 это явный запрет, а не молчание.
- Sampling-эха применённых параметров в ответе нет (`task_params::to_json(only_metrics)` используется для
  метрик) ⇒ контроль штрафов только поведенческий (запрос с `repeat_penalty:1.1` против penalty-free).
- `top_logprobs: 2` даёт только два верхних значения: **эntropy/KL/полное распределение по нему не
  считается**. Всё, что требует полного ряда, — только маршрут §2 (или N/A).

## 4. Что из этого следует для ТЗ r3 (решение исполнителя, на утверждение ревью)

1. **Q1 (расхождение id-потоков движков)** остаётся на `llama-server POST /completion`
   (16 доков × r=2, greedy 384): там есть `tokens[].id` и logprob сгенерированных позиций — этого
   достаточно. Схема ответа фиксируется спайком (решающая таблица: есть/нет `top_logprobs` на позиции,
   входят ли prompt-позиции), а не предположением ТЗ.
2. **Q2 (кросс-движковое p1 при ИДЕНТИЧНОМ conditioning)** переезжает на §2: teacher forcing
   `llama-perplexity` (SYCL) против собственного CPU-референса (transformers fp32, копия формулы exp81b),
   сравнение только на позициях с совпавшим id-потоком. Главная метрика — медиана |Δp1|,
   вспомогательная — тай-корректный Spearman с пермутационным null.
3. **Q3 (logit-сигнал повтора)** считается **внутри одного движка** (margin-трек llama против rep8 llama,
   и отдельно CPU margin против CPU rep8), кросс-движковое смешение позиций запрещено: сравниваются
   *корреляции*, а не позиции двух движков.
4. Всё, что требует полного ряда и не влезает в бюджет (entropy, KL), — объявляется N/A с причиной,
   а не «считается по top-2».

## 5. ГЛАВНОЕ: сервер принимает сырые token ids → teacher forcing без токенизатора и без perplexity

- `tools/server/server-common.cpp:963-974` (`tokenize_input_subprompt`): `"prompt"` может быть
  **массивом целых** — `"prompt": [12,34,56]` берётся как готовый id-поток (`json_prompt.get<llama_tokens>()`),
  без `common_tokenize` вообще.
- BOS: комментарий `server-common.cpp:851` — «we only add BOS, when json_prompt is a **string**» ⇒
  для массива id BOS **не добавляется** ⇒ сдвига выравнивания нет (наши HF-пины получены
  `add_special_tokens=False`, то есть тоже без BOS — конвенции совпадают).
- Следствие для метрик: **учить движок ровно на CPU-id-последовательности** (prompt 64 + gen 384 = 448 id)
  можно через `POST /completion` с `{prompt: <ids>, n_predict: 1, logprobs: true, top_logprobs: 2,
  cache_prompt: true}`: ответ даёт logprob фактического следующего id и два верхних — то есть
  p1/margin/top1-выбор движка **при идентичном conditioning**, без tokenizer-drift, без 126 MB-файлов,
  без `n_ctx`-лестницы и без uint16-квантования perplexity. Это заменяет §2 как основной logit-маршрут.
- Стоимость и единственный риск — префиксный кэш: при растущих префиксах (`ids[:k]`, k=1..448) каждый
  запрос должен досчитывать ~1 токен. Тогда ≈0.2-0.3 с/позицию ⇒ 448 позиций ≈ 2-3 мин на док.
  **Спайк-гейт (обязателен, до метрик):** прогнать k=64 и k=128 на одном доке; если `timings` показывает
  рост `prompt eval` с k (кэш не бьёт) — маршрут закрывать и возвращаться к perplexity-пути §2.
  Скоуп по числу доков/позиций подбирается по измеренному времени, а не на глаз (потолок — 40 мин).
- Что по-прежнему НЕдоступно на этом маршруте: полное распределение (только top-2) ⇒ entropy/KL — N/A.

## 7. ⚠ Ключевое: `logprob` из сервера нормирован по **выжившему после сэмплера множеству**, а не по vocab

Живой спайк E94 (2026-11-12 00:04, `results/e94/SPIKE.json`, `/tmp/e94raw/w0_completion.json`):
при `top_logprobs: 2` каждый `completion_probabilities[i].top_logprobs` имеет длину **1**, а
`tokens_evaluated == 64` (ids-промпт принят без BOS/шаблона), `tokens_predicted == 8`.

Причина в исходнике (`tools/server/server-common.cpp:1502-1550`, `get_token_probabilities`):
`n_logits = llama_get_sampled_logits_count_ith(ctx, idx)` — это число **кандидатов, доживших до
сэмплирования**, дальшеsoftmax считается **только по ним** (`:1532-1549`), а отдаётся
`min(n_logits, n_probs_request)` записей. Поэтому:
1. `len(top_logprobs)` — это измеримый размер выжившего множества (прореживание min-p/top-p реально);
2. **`p_max := exp(logprob)` из ответа — вероятность, нормированная по выжившему множеству.**
   Сравнение её с полным softmax transformers (наш CPU-референс) **некорректно** как сравнение движков:
   часть разницы — ренормировка, а не движок;
3. чтобы p_max стал полным-vocab-значением, надо снять прореживание в самом запросе
   (`top_k` большим, `top_p:1.0`, `min_p:0.0`, `typical_p:1.0`, `xtc_probability:0.0`) и убедиться,
   что `len(top_logprobs)` дошёл до запрошенного `top_logprobs`; при `temperature:0` argmax от этого
   не меняется, так что Q1-поток остаётся тем же жадным;
4. побочно: при выжившем множестве размера 1 `logprob` обязан быть 0 (p=1) — это полезный инвариант
   для само-проверки парсера.

Вывод для ТЗ: метрика Q2 («медиана |Δp_max| llama vs CPU») законна **только** на каноне запроса со
снятым прореживанием; иначе она должна быть объявлена непригодной, а Q2 сводится к совпадению argmax
(`top1_agree`) и к «CPU-id ∈ выжившее множества». Проверка делается спайком (три замера A/B/C), а не
рассуждением.
