# Где живут артефакты (правило: git — не свалка)

Дата: 2026-11-20. Причина: git не переносит большие блобы (память/скорость клона/бандлы), при этом
артефакты нужны для воспроизводимости и для ссылок в `paper.md`. Решение ниже — не «пожелание», а
разделение ролей: **git — провенанс, HF — данные, /data — рабочий кэш**.

## 1. Пороги

| размер файла | где живёт | в git? |
|---|---|---|
| ≤ 10 МБ | рядом с кодом/в `results/` как обычный файл | **да** (если это результат, а не кэш) |
| 10–200 МБ | HF dataset repo (private) + строка в `artifacts/registry.json` | **нет** (в git едет только запись реестра) |
| > 200 МБ | HF dataset repo; локальная копия — только если нужна сейчас | **нет** |
| регенерируемое (trackio-БД, `*_jcache.pt`, `P*_*.npz`, `at02_*.pkl`, токенизаторы из HF) | `/data/prism_kernels` или вообще удаляется | **нет** |
| логи прогонов (`logs/*.log`, `.log.gz` ≤ 1 МБ) | `logs/` | да (это провенанс) |

Жёсткое правило: **файл больше 10 МБ в git не коммитится**, даже если очень хочется. Гейт:
`python tools/artifacts.py gate` (падает на staged-файлах >10 МБ).

## 2. Куда именно кладём (варианты и почему выбран HF)

| вариант | плюсы | минусы | вердикт |
|---|---|---|---|
| **HF Hub dataset (private)** | бесплатно, версионирование по коммитам, частые/частичные загрузки, `hf_hub_download` с кэшем, приватность, тот же аккаунт, что для моделей | нужен токен; LFS-бэкенд HF (не свой) | **основной архив** (`prism-artifacts`) |
| Kaggle Dataset | удобно, если артефакт нужен внутри Kaggle-kernel; уже есть аккаунт | 20 ГБ/датасет, версии — отдельные «dataset versions», загрузка медленнее, нет частичного скачивания | **только если файл нужен из Kaggle** (дублица), не архив |
| `/data` (локальный диск) | быстро, уже 48 ГБ кэшей | один диск, 96 % занято, не бэкап | **рабочий кэш**, не архив |
| git-lfs в этом репо | «всё в одном месте» | утяжеляет клон и бандл, ломает текущую гигиену | **запрещено** |
| внешний S3/MinIO | полный контроль | администрирование | избыточно |

Итог: **HF private dataset `prism-artifacts`** — архив; **Kaggle** — дубликат для артефактов,
которые нужны в kernel; **/data** — горячий кэш.

## 3. Реестр (единственное, что в git)

`artifacts/registry.json` — компактный JSON, хранит провенанс, а не данные:

```json
{"schema":1,"hf_repo":"<user>/prism-artifacts","items":{
  "LAYERMASS2_raw.txt":{"local_path":"results/e77/LAYERMASS2_raw.txt","size":184320,
    "sha256_16":"…","exp":"E77","note":"сырые клетки v2","hf_path":"E77/LAYERMASS2_raw.txt","hf_revision":"…"}}}
```

Правила:
- ключ = имя артефакта (уникальное, как в `paper`/`ref-exp`), `local_path` — путь восстановления;
- `sha256_16` — сверка при `pull`/`verify`, чтобы «восстановленный» файл не мог оказаться чужим;
- перезапись файла = новая запись с новой sha (старую не удалять, а обнулять `hf_path` у прежней —
  опубликованные вердикты не переписываются задним числом, AGENTS.md п.10).

## 4. Команды (`tools/artifacts.py`)

```
python tools/artifacts.py scan            # что весит > 10 МБ (кандидаты на вынос)
python tools/artifacts.py gate            # предкоммит-гейт (>10 МБ в staged → rc=1)
python tools/artifacts.py add PATH --exp E65 --note "…"
python tools/artifacts.py verify          # sha локальных копий против реестра
python tools/artifacts.py verify --hf     # + сверка со списком файлов в HF-репо (сеть)
python tools/artifacts.py scan --top 100  # пометка [НЕ В РЕЕСТРЕ]: файл >порога, которого нет в реестре
python tools/artifacts.py push --repo <user>/prism-artifacts [--dry-run]
python tools/artifacts.py pull <name>     # восстановить в local_path, сверив sha
```

Токен: `hf auth login` (или `HUGGINGFACE_TOKEN` в окружении запуска, **не** в репо).
Без токена `push`/`pull` не работают; `scan/gate/add/verify` работают всегда.

## 5. Порядок для новой находки

1. `scan` → вижу файл >10 МБ.
2. Решение: регенерируемый кэш? → не архивируем (только путь в доке). Уникальный результат? → п.3.
3. `add` (появится запись с sha) → `push` → `git add artifacts/registry.json` + карточка/док.
4. Кто читает результат: `pull` по имени, сверка sha — и только тогда число идёт в отчёт/paper.

## 6. Что НЕ архивируем никогда

- `trackio`-БД (`.trackio/`) — регенерируемый кэш от логов; source of truth — логи.
- кэши якобианов/генераций (`*_jcache*.pt`, `P1_own.npz`, `P2_corpus.npz`, `P3_rnull.npz`,
  `gen_AT_C*_qwen.npz`, `at02_*.pkl`, `jac4_par_*.bin`) — регенерируются скриптом серии;
- веса моделей — они уже на HF upstream;
- `.venv`, `*.so` сборки, логи оболочки/агентов (`pi-bash-*.log`).

- **Ключ реестра (schema 2) — путь файла** (`results/e64/tpu/P1_own.npz`), а не basename: одинаковые имена

  `scan` теперь помечает `[НЕ В РЕЕСТРЕ]` и печатает их сумму, т.е. дырка видна без ручного сверять.

## 8. Что проверено прогоном (20.11), а не на глаз

1. **Выгрузка состоялась**: 46 уникальных объектов в `survivor-m/prism-artifacts` (dataset, публичный) на 50 записей реестра, каждой записи
   в реестре соответствуют `hf_path` + `hf_revision` (коммит HF), `sha256_16` сверен при `verify`.
   Регенерируемые кэши (`exp27_jcache.pt`, `gen_AT_C*`, `*_jcache*`) не выгружались — по §6.
2. **`pull` был нерабочим, найден дефект**: `Path.replace(dst)` → `OSError: [Errno 18] EXDEV`
   (кэш HF и репо на разных ФС), а `shutil.move` → `FileExistsError`, потому что в снапшоте HF файл —
   симлинк на блоб, а цель уже существует. Заменено на `shutil.copy2` + `unlink` ссылки.
   Проверено в двух режимах: `pull AT8/AT8_2_R2_series.npz` (перезапись локального) и
   `pull --dest /tmp/pulltest.npz` — `sha OK` в обоих. Вывод правила: **проверять восстановление, а не
   только выгрузку** — до прогона реестр выглядел полным при нерабочем `pull`.
   Оговорка о провенансе: `tools/artifacts.py` попал в git уже исправленным, промежуточные ревизии
   (`replace`, `move`) не коммитились, поэтому «было сломано» подтверждается только сообщениями об ошибках
   из прогона, а не диффом — в git-checklist этот путь восстановлению не подлежит.
3. **Стриминг из HF измерен** (вопрос «можно ли читать прямо из HF»): подкачка целого файла 82.8 МБ —
   **11.0 с (7.6 МБ/с)**, после неё чтение члена npz — **0.001 с**; ranged-чтение `.npy` 13.1 МБ
   через `HfFileSystem` — 2.8 с (**4.7 МБ/с**), т.е. медленнее полной подкачки; `np.load` прямо из
   облака на 82.8 МБ npz — 2.9 с, на 1.58 ГБ npz (192 члена) индекс 3.5 с + **0.7 с** на один член.
   Вывод: стриминг оправдан только для малого среза большого холодного файла (0.7 с против ~208 с
   на скачивание 1.58 ГБ); для обычного чтения — «скачать один раз, читать локально» (в 1000+ раз
   быстрее на повторных чтениях). Отдельная ловушка: `hf_xet` (чанковый дедуп/параллелизм) стоит
   только в системном python, в `.venv` его нет — ranged-чтение из venv идёт plain-HTTP.
