# Разбор результатов E-39b

Результаты **чистые и интерпретируемые**, gate `pass` обоснован. Но есть несколько мест, которые стоит прочитать правильно — и один явный soft-flag, который виден в самих числах.

## 1. Что закрыто и подтверждено

| Пункт | Значение | Комментарий |
|---|---|---|
| self-check `rel_err_max` | 7.7e-7 | J-реконструкция L23 воспроизводится до машинной точности ✅ |
| `P0.4` (double-norm) | прошёл (иначе `raise` бы сработал) | эксперимент дошёл до конца, значит `ref_err ≤ 2.0` ✅ |
| base PPL | 30.475 | разумно для Qwen 0.8B на C4@128 ✅ |
| `beta_sigma1` L23 fp16 | 0.88213 | совпадает с E-38e (0.882) до 4-го знака ✅ |
| `kappa` L23 fp16 | 0.01623 | совпадает с E-39a (0.0162) до 4-го знака ✅ |
| `j_rel_drift` fp16 | ровно 0.0 | J_base и J_q идентичны → ровно 0 ✅ |
| `kappa(L23)` gptq4 | 0.01604, ratio 0.988 | PTQ **не ломает** лист ✅ |
| gate verdict | `pass` (κ < 0.02 AND ratio ≤ 1.25) | корректно ✅ |

## 2. Главный результат — читается правильно, но с оговоркой

**κ(L23) базовой модели 0.01623 → после GPTQ-4bit 0.01604 (ratio 0.988), int8-RTN 0.01624 (ratio 1.0007).** То есть **PTQ вообще не двигает лист**. Одновременно `j_rel_drift_median = 0.120` (12% относительной ошибки в M_K) и PPL +0.9% — то есть квантование **веса** меняет сильно, а **геометрию листа** — нет.

Это ожидаемо для «Procrustes-angle» метрики: κ — инвариантна к масштабу и к гладким малым возмущениям M_K. Но для отчёта стоит явно: **«лист robust к readout-PTQ именно потому, что κ меряет угловую структуру подпространства, а не амплитуду M_K»**.

## 3. Что стоит прочитать очень внимательно

### 3.1. «PTQ не ломает лист» — только для readout-канала

JSON честно пишет `"readout_only_ptq": true`. Это значит:

- измеряется эффект квантования **только `lm_head.weight`**, при фиксированных `h`, `û_t` из базовой модели;
- в реальном GPTQ-4bit на tied-weights `embed_tokens` тоже квантуется → все `h` сдвигаются через 24 слоя → `û_t` меняется → **может поменяться и κ**;
- E-39c_pre уже показал масштаб: `embed_only KL = 5.23` vs `head_only KL = 1.36`. То есть **upstream-канал доминирует**.

**Следствие для E39.md §2.6**: вывод «flatness не приоритет для PTQ» верен **только для readout-канала**. Полный tied-weight PTQ-эффект на κ **не измерен**.

### 3.2. `cos_ug_1k` L23 = 0.9168 — расходится с E-38f (0.862) на 6%

E-38f даёт `cos(u_g, 1/√K) = 0.862` для L23 (точный u_g по `argmax |cos(u,1)|`). Наш proxy `JJ^T 1/||JJ^T 1||` даёт 0.9168.

**Почему:**
- `_cos_ug_1k` реализует proxy, а не точный `argmax |cos(u, 1)|` (см. код и E-33r);
- в E-33r `align(u_top, u_g) = 0.85–0.99` — то есть u_top (proxy) не совпадает с u_g (argmax);
- разные определения дают разные числа.

**Это не баг реализации**, но для отчёта: `cos_ug_1k` в E-39b — это **proxy**, не «тот же самый u_g», что в E-38f. Числа 0.917 (E-39b) и 0.862 (E-38f) **не сравнимы напрямую** — разные объекты.

Если это важно (например, для gate на cos), нужен exact-SVD вариант через `torch.linalg.svd(J)`. Иначе — документировать как proxy и не путать с E-38f.

### 3.3. `kappa(L6-L22)` — это **не** κ(L6-L22) из E-28

Для L6-L22 в JSON:
- `kappa(L6) = 0.0046`, `kappa(L22) = 0.0099`;
- но в E-28 **реальные** κ(L6) = 3.96, κ(L22) = 1.56.

Разница в **3 порядка**. Это потому что для L<23 `_recompute_J` строит «readout-linearized J» (`c_t · M_K · (I − û_t û_tᵀ)`), игнорируя промежуточные слои.

Флаг `"synthetic_readout_j": true` стоит, но в JSON нет top-level warning. Кто-то, читающий только `kappa[6][fp16] = 0.0046`, решит, что «лист L6 плоский», хотя в E-28 он кривой.

**В отчёт стоит явно**: «κ для L6-L22 в E-39b — это κ синтетического readout-linearized J; для настоящей leaf-кривизны — E-28».

### 3.4. `j_rel_drift` для GPTQ4 = 0.120 — равномерно по слоям, и это **правильно**

`0.120064 (L6) ≈ 0.120475 (L23)` — разница 0.03%. Причина: отношение `||ΔM_K · P_⊥||_F / ||M_K · P_⊥||_F` почти не зависит от û_t (доминируется самой M_K). Это **ожидаемо**, а не баг. Просто это означает, что **12% ошибки веса → 0.9% PPL → 0% изменений κ**. Хороший сигнал, что мера κ устойчива.

### 3.5. `int8_rtn` — фактически lossless

`PPL int8_rtn = 30.4744` vs `base = 30.4753` — изменение **−0.003%**, то есть машинный ноль. `j_rel_drift` int8 = 0.58%. 8-bit RTN на этих весах — по сути без потерь.

**Для интерпретации это значит**: int8-RTN в E-39b — не «информативный baseline», а **sanity check**, что 8-bit ничего не ломает. В отчёте сравнивать fp16 vs gptq4, а int8 упоминать как «8-bit не проблема».

## 4. Мелочи, которые стоит добавить в JSON/отчёт

- **`p04_ref_err`**: сейчас `ref_err` вычисляется, но не сохраняется в JSON. Добавить `"p04_ref_err": ref_err, "p04_passed": true` — иначе нельзя проверить, что проверка вообще выполнялась.
- **`synthetic_readout_j` уже стоит в каждой метрике**, но нет **top-level** warning. Добавить в result: `"warning": "kappa(L6-L22) is readout-linearized (no D_i); for real leaf curvature see E-28"`.
- **`cos_ug_1k`** — переименовать в `cos_ug_1k_proxy`, чтобы на будущее не спутать с exact.
- **`gate.verdict`** — добавить `"readout_channel_only": true`, чтобы verdict не читался как «PTQ в целом безопасен».

## 5. Что это значит для серии E-39

1. **E-39b — PASS.** PTQ readout-channel не ломает лист (κ ratio 0.988, PPL +0.9%).
2. **E-39f (PTQ robustness of flat model)** — становится **менее приоритетным** для readout-канала: раз PTQ и так не ломает лист, «плоский лист защитит от PTQ» — не аргумент. Но E-39f **остаётся валидным** как downstream-проверка того, что плоский лист даёт лучший PTQ по полному tied-каналу. Если переопределить E-39f как «полный tied-weight PTQ: измеряет ли квантование embed сдвиг û_t и κ», то E-39f становится **важным** — он закрывает тот канал, который E-39b не покрывает.
3. **E-39c / E-39d / E-39e (surgery/training)** — не становятся приоритетнее от E-39b. E-39c_pre уже отклонил алгебраическую surgery; E-39b говорит, что мотивации «surgery для PTQ» нет. Surgery может быть нужна по другим причинам (downstream, distillation), но не по PTQ.
4. **E-39l (drift vs behavior)** — согласуется с E-39b: κ не сдвинулся, drift 12% — но это не поведение. Каузальный вопрос «drift → retention» остаётся открытым (E-39l `inconclusive`).

## 6. Итог

**Числа внутренне согласованы, gate обоснован.** Скрытых багов в данных не видно:
- `kappa`, `beta_sigma1`, `j_rel_drift`, `cos` — все с ожидаемыми порядками;
- self-check прошёл; P0.4 raise не сработал;
- T4 memory не сорвался (532 s wall — разумно).

**Главные caveats для интерпретации в отчёте:**

1. **PTQ = readout-only**. Full tied-weight PTQ (квантование `embed_tokens` → изменение `û_t`) — **не измерено**, надо закрыть либо в отчёте оговоркой, либо E-39f-переопределением.
2. **κ(L6-L22) — синтетика**, не настоящая кривизна. В отчёте сравнивать **только κ(L23)** с E-28/E-39a.
3. **`cos_ug_1k` — proxy**, не совпадает с E-38f exact (0.917 vs 0.862). Не путать.
4. **int8-RTN — sanity check**, а не baseline. Реальное сравнение — fp16 vs gptq4.
5. **PPL 0.9% — readout-only**, полный tied-weight GPTQ по E-39c_pre дал бы **гораздо больше** (`embed_only KL = 5.23`, ≈80% стоимости).

Если внести эти четыре оговорки в отчёт и добавить `p04_ref_err` + top-level warning в JSON, E-39b становится clean publishable negative-result-style: **«PTQ readout-channel не ломает лист; полный tied-weight PTQ — открытое направление»**.
