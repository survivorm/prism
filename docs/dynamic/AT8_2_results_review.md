## Классификация

### MAJOR (чинить до вноса в доки; повторный прогон НЕ нужен — store на месте)

**MAJOR-1. Медианы оси A исчислены по популяции, противоречащей TZ §5 и самим cells claim.**
TZ §5: «ℓ_rec(n) по медиане доков (**по измеримым (doc,W)**)». По TZ §4 not_recovered-ячейки
измеримы (им присвоен ℓ_rec=D_max) — значит, входят в медиану. Код (`lrec_axis`,
`lrec_combined`) фильтрует `rec_status ∈ (recovered, no_effect)` — **выбрасывает
not_recovered без фиксации в TZ и в claim** (в комментарии к функции фильтра нет).
Последствия:
- W64: заявлено {61.5, 0.0, 49.0, 62.0}, ratio 1.0081, b 1.8543, r2 0.1528;
  по TZ-определению (полная измеримая популяция): **{60.0, 39.0, 49.0, 62.0},
  ratio 1.0333, b 0.7391, r2 0.1842**.
- combined: заявлено {11, 0, 0, 31}; по полной популяции: {44, 48, 55, 62}
  (b 1.2565, r2 0.9619, ratio 1.4091).
- Фильтрованные W64-медианы: n=2 — 2 дока (wiki_1, wiki_2); **n=4/8/16 — по одному доку
  (wiki_2)**. «Медиана по докам» на одном доке = значение этого дока; ratio 1.0081
  сравнивает wiki_2@n16 с mixture wiki_1+wiki_2@n2 — смешение доков между дозами.
- Внутреннее противоречие: cells claim **отчитывают l_rec для not_recovered ячеек**
  (напр., wiki_0|n2|W64: l_rec=18, rec_status=not_recovered), но эти же ячейки выкинуты
  из медиан.
- Вердикт от этого не меняется (ELASTIC в обеих популяциях, DIFFUSION недостижим), и
  prereg.note (MINOR-2 r1) предупреждает, что ось A неинформативна и вердикт сходится
  через ось B, — но **не говорит, что популяция медиан отфильтрована**.
Фикс (15 мин, без модели): либо (a) пересчитать ось A по TZ §5 (полная популяция) как
основную и оставить фильтрованную вторичной с явной пометкой «censored excluded»;
либо (b) зафиксировать в TZ v1.2 определение «censored (not_recovered) значения ℓ_rec=D_max
исключаются из медиан» (статистически обоснованно — цензурированные наблюдения) и
перомарить axis_A/lrec_by_n в claim. Как есть — числа оси A в claim не воспроизводятся
ни по TZ, ни с пометкой, и не могут уходить в доки/paper.

### MINOR (не блокируют прогон; поправить при фиксе MAJOR-1)

**MINOR-1. NOT_RESOLVED-условие «большинство not_recovered» (TZ §5) не реализовано.**
В коде — только «мало пар (doc,n) с ℓ_rec>0» (n_meas_doc_n по W64 = 7 ≥ 6 ✓). Реально:
55/116 = 47.4% не-мажорити (здесь вердикт не страдает), но **на уровне оси W=64 —
15/20 = 75%**: если гейт читать по оси, вердикт был бы NOT_RESOLVED. TZ не уточняет
популяцию гейта. Фикс: реализовать гейт по полной измеримой популяции + уточнить TZ.

**MINOR-2. trackio: нет `{"stage": …}` точек (AGENTS p.4 — обязательно) и нет в config
`md5` лога / `seed` (p.5).** Прогон трассируемый (start-config, 32 per-dose, finish со
status/verdict/claim_sha), crash-handler есть — но правило про крупные этапы не выполнено
дословно. Фикс: в следующих прогонах — stage-точки (загрузка модели / analysis) + md5/seed
в config (seed — n/a, детерминированный forward, зафиксировать так).

**MINOR-3. Resume — designed-сценарий, не протестированный в этом прогоне** (AGENTS p.2:
«designed-сценарий guard'а обязан быть протестирован»). Fresh run (строки resume в логе
нет), целостность store при resume не проверяется (h23_sha — хранимый, а не
пересчитываемый — циклична). Для one-shot прогона приемлемо; в smoke-стадии resume
(частичный store + повтор) не прогонялся.

## ИТОГ

Механика, хэш-цепь, гейты, полнота, ℓ_rec, лог/claim/store-сходимость и E-71B-обобщение —
всё пересчитано независимо и совпадает (0 расхождений во всём, что проверялось числом).

робустен к выбору популяции оси A и сходится через ось B, как и предсказано пре-регом.
Блокирующая проблема одна — **MAJOR-1**: заявленные числа оси A исчислены по популяции,
которая противоречит TZ §5 и самим cells артефакта, и не зафиксирована нигде. Фикс
дешёвый (пересчёт из store + пометка в TZ/claim), повторный прогон не нужен.
