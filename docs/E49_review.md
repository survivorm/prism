Посмотрел код и JSON. Сразу важное: **код `exp49_leaf_info.py` и JSON `exp49b2_floor_*.json` — это, судя по структуре, разные эксперименты**. В коде нет `shuffle / block / blockmix / syn_CA_smooth / other_doc / paired...`, а в JSON нет `W×r×metric`-сетки. Поэтому числа из JSON этим кодом напрямую не проверить. Но в самом коде есть несколько существенных ошибок/неточностей, а в JSON — контрольные тревоги.

## 1. Ошибки и неточности в коде `exp49_leaf_info.py`

### 1.1. Главная математическая ошибка: M-метрика через Cholesky реализована неверно

В `main`:

```python
G = A.T @ A
Lch = torch.linalg.cholesky(G + jitter)
```

`torch.linalg.cholesky(G)` возвращает lower-triangular `L`, такую что  
`G = L @ L.T`.

А в `frame_in_metric` написано:

```python
"""L: G=LᵀL; возврат — ортонорм. базис L·span(V)"""
...
Wm = L @ V
return torch.linalg.qr(Wm)[0]
```

То есть код использует `L @ V`, как будто `G = L.T @ L`. Но PyTorch даёт `G = L @ L.T`.  
Правильно для G-метрики было бы использовать `L.T @ V` (или брать `Lch = cholesky(G).T`).

**Следствие:** все результаты с `metric="M"` в этой сетке — это не метрика `G = A.T @ A`, а другая метрика `L.T @ L`. Если M-числа где-то использовались, их нужно пересчитать. Это не косметика, а реальная математическая ошибка.

### 1.2. M3 «голономия» заявлена в docstring, но не считается

В docstring обещаны методы M1–M4, включая:

> M3 голономия окна L=8 vs shuffled-null с bootstrap CI по документам

Функция `holonomy()` в коде есть, но **нигде не вызывается**. В `doc_stats` и `main` считаются только `s_lag`, `tau` и `v1`.  
Значит, если в результатах E-49 нет отдельного блока holonomy — это не потому, что «не нашли», а потому что код её не запускает. Заявление о M3 в docstring не соответствует реализации.

### 1.3. Контроли проверяют только одну ячейку сетки

`run_stage1()` проверяет контроли только для:

- `r = 16`,
- `W = 1`,
- `metric = "eucl"`.

А основная сетка включает `W = 1,4,16`, `r = 1,2,4,16`, `metric = eucl/M`.  
То есть для большинства ячеек **нет проверки, что конвейер вообще различает white и coherent**. Tau в этих ячейках может быть неинтерпретируемым.

### 1.4. Контроль B не является строго геодезическим

В `control_coherent`:

```python
w = nz(torch.randn(D, ...))
...
w = nz(w + 0.05 * (z - (z @ u) * u - (z @ w) * w))
u2 = cos(delta) * u + sin(delta) * w
u = nz(u2)
```

Здесь `w` не ортогонализуется к `u` ни в начале, ни после обновления. Если `w` не перпендикулярен `u`, то `cos(delta)*u + sin(delta)*w` — не шаг по геодезической, а просто вектор с последующей нормализацией. Эффективный угол не равен `delta`, и контроль B может быть «менее coherent», чем задумано. Это может смещать `tau`.

### 1.5. Сглаживание имеет краевой эффект

`smoothed_us` для `W > 1` делает причинное среднее:

```python
hs = torch.stack([h[max(0, t - W + 1):t + 1].mean(0) for t in range(len(h))])
```

На первых `W-1` позициях окно короче. Значит, начало последовательности сглажено слабее, чем середина. `tau` и `s_lag` по всем позициям могут быть смещены. Обычно либо отбрасывают первые `W-1` позиций, либо используют центрированное окно.

### 1.6. Для LFM3 не проверяется tied weights

```python
W_head = m.get_input_embeddings().weight.detach()
if args.model == "qwen" and not (m.lm_head.weight.data_ptr() == W_head.data_ptr()):
    W_head = m.lm_head.weight.detach()
```

Для Qwen проверка есть. Для LFM3 — нет. Если у LFM3 `lm_head` не tied с эмбеддингами, то `A` строится по **неправильной матрице** (эмбеддинги вместо output head). Это может полностью испортить LFM3-числа.

### 1.7. Для LFM3 произвольный набор токенов

```python
U = list(range(0, 384, 3))[:128]
```

Для Qwen берётся частотный `U128` из кэша, для LFM3 — просто каждый третий токен из первых 384. Это не сопоставимые наборы. Сравнение `qwen` vs `lfm3` по `tau` может отражать не архитектуру, а разный выбор токенов.

### 1.8. G вырождена, jitter 1e-10 делает её искусственно полной

`G = A.T @ A` имеет ранг ≤ 128 при `D=1024`. Добавление `1e-10 * mean(diag)` делает её формально положительно определённой, но число обусловленности огромное. Для M-метрики это может давать численные артефакты. Это не обязательно ломает top-r, но должно быть явно проверено.

### 1.9. Мелочи

- `v1_lag` использует `acos(abs(cos))`, то есть углы > 90° складываются. Для sign-fixed `v1` это скрывает большие повороты; лучше документировать.
- `holonomy()` имеет потенциальную проблему порядка умножения `P @ R`; но она не используется, так что это пока не влияет.
- `run_stage1` не проверяет, что white-контроль даёт плоскую лаг-кривую, только `tau > 0.7`.

## 2. Замечания к JSON `exp49b2_floor_*.json`

### 2.1. Что показывают числа

`tau` — это мера «неаддитивности» движения:
- `tau ≈ 0` — движение когерентное, шаги складываются, как по геодезической;
- `tau ≈ 1` — белый шум, шаги независимы.

В JSON:

| Модель | W | real tau | block tau | blockmix tau | CA | CB | H2 |
|---|---:|---:|---:|---:|---:|---:|---|
| Qwen | 4 | 0.4437 | 0.4879 | 0.4875 | 0.6821 | 0.4778 | true |
| Qwen | 16 | 0.3914 | 0.3950 | 0.3930 | 0.6041 | 0.4748 | false |
| LFM3 | 4 | 0.4818 | 0.5108 | 0.5079 | 0.6856 | 0.6164 | true |
| LFM3 | 16 | 0.4417 | 0.4430 | 0.4437 | 0.6038 | 0.6339 | false |

Простыми словами:

- При умеренном сглаживании `W=4` реальная траектория **более когерентна**, чем block/blockmix-контроли: `real tau` заметно ниже. Для Qwen разница `−0.043`, для LFM3 `−0.029`, и CI не включает 0. Это и есть «H2 survives».
- При сильном сглаживании `W=16` реальная траектория становится почти такой же, как block-контроль: разница `−0.001…−0.004`, CI часто включает 0. Поэтому «H2» больше не выживает. То есть **лёгкое сглаживание открывает медленный канал, а сильное — всё усредняет и стирает различие**.

### 2.2. Но есть контрольная тревога: `other_doc`

В JSON `other_doc` — это, судя по названию, замена документа на другой. Если лист несёт информацию именно о траектории, `other_doc` должен быть заметно хуже real. А числа такие:

- Qwen W4: real 0.4437, other_doc 0.4509 — разница всего 0.007;
- LFM3 W4: real 0.4818, other_doc 0.4786 — **real даже чуть хуже** (выше tau).

То есть эффект «real лучше контроля» очень маленький, а для LFM3 в W4 — вообще не в ту сторону. Это важное ограничение: возможно, `tau` ловит не документ-специфичную траекторию, а общее свойство модели/головы. В verdict-rule `other_doc` не входит, поэтому JSON этого не замечает.

### 2.3. Для LFM3 не проходит coherent-контроль

В коде selftest требует, чтобы coherent-контроль давал `tau < 0.5`. В JSON для LFM3:

- `syn_CB_smooth` W4 = 0.6164;
- W16 = 0.6339.

Это **выше 0.5**. То есть на LFM3 контроль B не подтверждает, что `tau` вообще различает coherent и white в нужную сторону. При этом verdict H2 для LFM3 W4 = true, потому что rule не проверяет CB. Это несогласованность: результат объявлен выжившим, хотя соответствующий контроль не прошёл ожидаемый порог.

### 2.4. Названия `CA_floor` / `CB_ceiling` запутывают

Для Qwen W4:

- `CA_floor = 0.6821`,
- `CB_ceiling = 0.4778`.

«Floor» численно больше «ceiling». Если CA — это высокий tau (менее когерентный контроль), а CB — низкий, то названия перепутаны или означают не то, что кажется. Это не математическая ошибка, но терминологическая ловушка.

### 2.5. `interleave_check` > 1

`interleave_check` даёт `tau ≈ 1.47–1.83`. Это не «ещё один null»: `tau` не ограничен сверху 1. Значение >1 означает, что прямой угол `t→t+2` меньше, чем шаг `t+1→t+2`, то есть путь неаддитивен в другую сторону. Интерпретировать это как «не null» можно, но нельзя читать как вероятность или как «более белый, чем white».

## 3. Итог простыми словами

1. **Код E-49 содержит реальную ошибку в M-метрике** (Cholesky orientation). Если M-результаты использовались — их надо пересчитать.
2. **M3 holonomy в коде не считается**, хотя заявлена.
3. **Контроли проверены не для всех ячеек**, а для LFM3 coherent-контроль в JSON не проходит порог `< 0.5`.
4. **JSON E-49b2 показывает:** при `W=4` реальная траектория листа когерентнее block-контролей на обеих моделях; при `W=16` это преимущество исчезает. Это согласуется с идеей «умеренное сглаживание открывает медленный канал, сильное — стирает».
5. **Но `other_doc` почти не отличается от real**, а для LFM3 W4 даже чуть хуже. Это серьёзно ограничивает вывод «лист несёт информацию именно о траектории документа»: возможно, эффект не документ-специфичен.
6. **Вердикт H2 в JSON слишком оптимистичен**, потому что rule не включает `other_doc` и CB-контроль. Если включить, картина для LFM3 и для утверждения «это про траекторию» станет слабее.

Если коротко: **числа выглядят внутренне согласованно для W4 vs W16, но экспериментальная поддержка неполная; в коде есть баг M-метрики и несколько контрольных дыр. Перед выводами я бы пересчитал M-метрику, добавил other_doc/CB в verdict, проверил tied weights у LFM3 и прогнал контроли для всех W/r/metric.**

Смотрел `exp49b2_floor.py` как генератор JSON `exp49b2_floor_*.json`. **Арифметика вердикта в коде соответствует JSON** — я не нашёл расхождения «код считает одно, в JSON лежит другое». Но есть несколько существенных ошибок/неточностей в контролях и наследуемых функциях. Ниже — по убыванию важности.

## 1. Ошибки и неточности

### 1.1. Coherent-контроль `synth_coh` — не геодезический, хотя в docstring обещаны геодезические шаги
В `synth_coh`:
```python
u = nz(randn)
w = nz(randn)
...
u2 = cos(delta)*u + sin(delta)*w
...
w = nz(w + 0.05*(z - (z@u)*u - (z@w)*w))
u = nz(u2)
```
`w` не ортогонализуется к `u` ни при инициализации, ни после обновления. Если `w` имеет компоненту вдоль `u`, то `cos(delta)*u + sin(delta)*w` после нормировки — это **не** шаг на угол `delta` по геодезической. Эффективный угол меньше/другой. Это прямая неточность относительно заявленного «шаги δ=0.02 по геодезическим».

Последствие видно в JSON: для LFM3 coherent-контроль не выходит на ожидаемый режим:
- LFM3 W4: `CB_smooth = 0.6164` — выше порога `<0.5`, который сам же код проверяет в selftest из `exp49_leaf_info`;
- LFM3 W16: `CB_smooth = 0.6339`, а `CA_smooth = 0.6038` — то есть «когерентный» контроль **менее когерентен**, чем «белый». Это провал контроля.

При этом вердикт H2 **не проверяет CB**. Поэтому для LFM3 H2 может «выжить», хотя coherent-контроль сломан.

### 1.2. `other_doc` не входит в вердикт, а его числа убивают интерпретацию «это про траекторию документа»
В JSON:
- Qwen W4: `real = 0.4437`, `other_doc = 0.4509` — почти одинаково;
- LFM3 W4: `real = 0.4818`, `other_doc = 0.4786` — **real даже чуть хуже** (выше τ).

Если лист нёс бы информацию именно о траектории **этого** документа, `other_doc` должен быть заметно хуже. Он не хуже. Значит, измеренная когерентность, скорее всего, **не документ-специфична**, а является свойством модели/головы/локальной динамики. Вердикт это не ловит, потому что `other_doc` не включён в `verdict_rule`.

### 1.3. `frames_of` понижает точность до float32
```python
out.append(torch.linalg.qr(V / V.norm(dim=0, keepdim=True))[0].float())
```
В `exp49_leaf_info` кадры считаются в double, здесь — `.float()`. Для τ, который может быть близок к нулю, это лишний шум и несогласованность между скриптами. Не катастрофа, но лучше не даункастить без причины.

### 1.4. Наследуемые из `exp49_leaf_info.load_model` проблемы для LFM3
`exp49b2_floor.py` импортирует `load_model` из `exp49_leaf_info`. Там для LFM3:
```python
W_head = m.get_input_embeddings().weight.detach()
# проверки tied weights для LFM3 нет
U = list(range(0, 384, 3))[:128]
```
То есть:
- если у LFM3 `lm_head` не tied с эмбеддингами, `A` строится по **неправильной матрице**;
- набор токенов `U` для LFM3 — произвольный `range(0,384,3)[:128]`, а не частотный `U128`, как у Qwen. Кросс-модельное сравнение τ может отражать не архитектуру, а разный выбор токенов.

Для Qwen проверка tied weights есть, для LFM3 — нет. Это надо чинить.

### 1.5. `N_REP = 2` — мало для block/shuffle/blockmix
Парные разности используют среднее по 2 реализациям. Это снижает дисперсию, но 2 — всё ещё очень мало. CI может быть оптимистичным. Не ошибка, но ограничение.

### 1.6. `syn_CA_smooth` — это не «белый» контроль, а «сглаженный белый»
После `smoothed_us` с `W=4/16` независимые векторы становятся локально коррелированными. Поэтому `CA_smooth` даёт τ ≈ 0.68/0.60, а не ≈1. Это нормально, но название `CA_floor` вводит в заблуждение: это не «пол белого шума», а «сглаженный белый». Как контроль он слабее, чем настоящий white.

### 1.7. Мелочи
- `boot_ci` импортируется из `exp49_leaf_info` и использует тамошний `RNG` с сидом 47, а локальный `RNG` в `exp49b2` — с сидом 49. Воспроизводимость CI зависит от чужого сида; лучше иметь локальный.
- `real_minus_CA_bootdiff` точечная оценка — разность медиан, а парные — медиана разностей. Не ошибка, но разные estimand’ы.
- `blockmix`/`interleave_check` не проверяют, что у `ok_` та же длина `T`. В JSON длины совпали, но код хрупкий.
- `assert len(Vs) % W == 0` есть только для real-документов, для синтетики — нет (там T=384 делится, но лучше явно).

## 2. Что означают результаты простыми словами

`τ` — это мера «неаддитивности» движения кадров:
- **τ ≈ 0** — шаги складываются как по гладкой траектории, движение когерентное;
- **τ ≈ 1** — шаги независимы, белый шум.

### W = 4: умеренное сглаживание открывает медленный канал
Для обеих моделей:
- Qwen: `real τ = 0.4437`, `block τ = 0.4879`, `blockmix τ = 0.4875`;
- LFM3: `real τ = 0.4818`, `block τ = 0.5108`, `blockmix τ = 0.5079`.

Real заметно ниже block/blockmix, CI разности не включает 0. Это значит: если порезать траекторию на блоки длины 4 и перемешать блоки (или взять блоки из другого документа), движение становится менее когерентным. То есть у реальной траектории есть когерентность **длиннее 4 позиций**, которую перестановка блоков разрушает.

### W = 16: сильное сглаживание стирает различие
- Qwen: `real 0.3914`, `block 0.3950`, `blockmix 0.3930`;
- LFM3: `real 0.4417`, `block 0.4430`, `blockmix 0.4437`.

Разности почти нулевые, CI включает 0. То есть при окне 16 реальная траектория уже не отличается от перестановки блоков длины 16. Простая интерпретация: характерная длина когерентного медленного канала — **между 4 и 16 позициями**. При W=16 блочный контроль сам сохраняет достаточно локальной непрерывности, и разница исчезает.

### Но есть две серьёзные оговорки
1. **`other_doc` почти не отличается от `real`**, а для LFM3 W4 даже чуть хуже. Значит, когерентность не похожа на «информацию о своём документе»; скорее это общее свойство поля J для данной модели.
2. **Coherent-контроль на LFM3 сломан**: CB выше 0.5 и на W16 выше CA. Поэтому для LFM3 вердикт H2 опирается на контроль, который сам не проходит ожидаемый режим.

## 3. Итог

- **Код и JSON согласованы**; ошибки в вычислении вердикта я не вижу.
- **H2 при W=4** формально подтверждается: real когерентнее block и blockmix на обеих моделях.
- **H2 при W=16** не подтверждается: сильное сглаживание стирает различие.
- **Но** `other_doc` показывает, что эффект, вероятно, **не документ-специфичен**, а `synth_coh` для LFM3 не является валидным coherent-контролем. Поэтому самый сильный результат — Qwen W4; LFM3 W4 требует переделки контроля.
- Наследуемые из `exp49_leaf_info` проблемы (tied weights и произвольный `U` для LFM3) могут дополнительно смещать LFM3-числа.

Если коротко: **«при умеренном сглаживании виден когерентный медленный канал; при сильном он исчезает» — да. «Это канал именно траектории документа» — пока нет, `other_doc` против. «LFM3 подтверждает» — слабо, потому что coherent-контроль на LFM3 невалиден.**
