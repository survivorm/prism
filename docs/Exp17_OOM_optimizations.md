Коротко: **не все предложенные ранее решения эквивалентны**. Часть из них меняет только скорость/память и математически безопасна, но часть меняет сам объект вычисления или граф, а значит — либо точность, либо смысл Exp17.

В вашем эксперименте важно разделять два режима:

1. **`create_graph=False` / detached Jacobian**  
   Нужен только для значения bridge loss и градиентов через `lm_head` при зафиксированном `J_norm`.

2. **`create_graph=True` / fresh Jacobian**  
   Нужен для того, чтобы bridge loss дифференцировался через `h` и градиент дошёл до `o_proj` LoRA. Это уже не просто значение Якобиана, а вторая производная / HVP.

Многие решения безопасны только для режима 1 и ломают режим 2, если сделать их наивно.

## 1. Что полностью эквивалентно для значения Якобиана и обычного моста

Если мы говорим про вычисление самого `J`, значения `L_bridge`, evaluation и detached-bridge для `lm_head`, то без потери математического смысла можно использовать следующее.

### 1.1. Безопасная формула `softmax_jacobian`

Формула вида:

```python
J_bar = (p[:, None] * J).sum(dim=0, keepdim=True)
J_p = p[:, None] * (J - J_bar)
```

или эквивалентно:

```python
J_p = J - p[:, None] * (p @ J)
```

если `p` нормализована, является **алгебраически точным** применением проектора:

\[
J^{(p)} = (\operatorname{diag}(p) - pp^T)J
\]

Это не меняет результат, только не строит плотную матрицу `diag(p) - pp^T`.

**Статус:** эквивалентно, можно использовать всегда.

---

### 1.2. Выбирать только строки `lm_head` для `token_set`

Вместо:

```python
W_eff = mS.lm_head.weight + B_lh @ A_lh       # [V, D]
J_S = W_eff[token_set] @ J_norm
```

можно строить только:

```python
W_rows = mS.lm_head.weight[token_set]
if lora:
    W_rows = W_rows + B_lh[token_set] @ A_lh
J_S = W_rows @ J_norm
```

Это **точная проекция** на нужные токены. Полный `W_eff` на весь словарь не нужен.

**Статус:** эквивалентно для `token_set`, если `W_rows` остаётся дифференцируемым там, где нужен градиент по `lm_head`.

---

### 1.3. Row-wise вычисление без `retain_graph` для detached Jacobian

Если вам нужен только численный Якобиан, то вместо:

```python
logits_subset = logits[0, token_set]
for i in range(len(token_set)):
    grad = autograd.grad(logits_subset[i], h, retain_graph=(i < len(token_set)-1))
```

можно делать:

```python
for i in range(len(token_set)):
    h_i = h0.clone().detach().requires_grad_(True)
    z_i = forward_upper_to_one_logit(h_i, token=token_set[i])
    grad = autograd.grad(z_i, h_i, retain_graph=False)[0]
```

Для фиксированных весов это даёт **те же самые строки Якобиана**, с точностью до порядка редукций в CUDA.

**Статус:** эквивалентно для значений, безопасно для памяти.  
Но: **это не сохраняет `create_graph`-путь до `o_proj`**, если вы просто замораживаете граф и делаете `h` листом.

---

### 1.4. `save_on_cpu`

```python
with torch.autograd.graph.save_on_cpu(pin_memory=True):
    ...
```

Этот механизм переносит сохранённые для backward тензоры на CPU. Сами значения и градиенты при этом не должны меняться.

**Статус:** математически эквивалентно, если ваша модель и кэш корректно работают с `saved_tensors_hooks`.  
Но нужно проверять на гибридных слоях Qwen3.5 и на `create_graph`, потому что некоторые кастомные/кэш-операции могут плохо сочетаться с этим.

---

### 1.5. CPU fallback в float32

Если GPU не влезает, можно считать тот же объект на CPU в том же `float32`.

**Статус:** практически эквивалентно, возможны только мелкие различия из-за порядка редукций. Смысл эксперимента сохраняется.  
Цена — скорость.

## 2. Что эквивалентно только при очень аккуратной реализации

### 2.1. Отказ от полного `J_norm [D, D]` в пользу только нужных строк `W_U @ J_norm`

Это **самый важный пункт для вашего случая**.

Сейчас `compute_hidden_jacobian(..., create_graph=True)` считает:

\[
J_{\text{norm}} = \frac{\partial h_{\text{norm}}}{\partial h_{l_S}} \in \mathbb{R}^{D \times D}
\]

а потом делает:

```python
J_S = W_eff[token_set] @ J_norm
```

Но для реального `bridge_loss` полный `J_norm` не нужен. Нужны только строки:

\[
J_S[i] = \frac{\partial (w_i^T h_{\text{norm}})}{\partial h_{l_S}}
\]

где `w_i` — строка эффективного `lm_head` для токена `i`.

То есть можно считать:

```python
z_i = h_norm @ w_i
J_i = autograd.grad(z_i, h, create_graph=True)[0]
```

или векторно через `grad_outputs`.

Математически для значения `bridge_loss` это эквивалентно, потому что исходный объект используется только через произведение `W_rows @ J_norm`.

**Статус:** эквивалентно для `bridge_loss`, если сохранён тот же `token_set`, тот же контекст, тот же `softmax_jacobian`, та же `p_L`.

Но есть важное отличие для градиентов.

---

### 2.2. `create_graph` row-wise вместо полного `[D, D]`

Для `o_proj` LoRA важно, чтобы граф был живой:

```python
h -> h_norm -> J_i -> bridge_loss
```

и чтобы `autograd` мог пройти обратно до `A_attn`, `B_attn`.

Поэтому просто:

```python
with torch.no_grad():
    ...
h = h.detach().requires_grad_(True)
```

будет **недостаточно** для o_proj bridge.

Но можно считать только нужные строки с `create_graph=True`:

```python
J_i = torch.autograd.grad(
    outputs=h_norm @ W_rows[i],
    inputs=h,
    create_graph=True,
)[0]
```

Это даёт граф, который может дойти до `o_proj`, если `h` связан с патчем `o_proj`.

**Статус:** потенциально эквивалентно и намного экономнее, потому что строк `U`, а не `D`.  
Но нужно аккуратно обращаться с памятью и с тем, что `softmax_jacobian` связывает строки через `J_bar`.

---

### 2.3. Чанкование с накоплением градиентов

Для памяти важно не держать все `U` графов сразу.

Вместо того чтобы собрать весь `J_S`, затем весь `J_S_p`, затем один `loss.backward()`, можно делать:

```python
optimizer.zero_grad()

for chunk in chunks(token_set):
    compute chunk graph with create_graph=True
    compute chunk bridge contribution
    scale by chunk_size / len(token_set)
    chunk_loss.backward()
```

Если лосс аддитивен по строкам, то градиенты накапливаются точно.

Но в вашем случае есть нюанс: `softmax_jacobian` делает строки зависимыми через:

```python
J_bar = sum_k p_k * J_k
```

То есть строка:

```python
J_p[i] = p_i * (J_i - J_bar)
```

зависит не только от `J_i`, но и от всех остальных строк через `J_bar`.

Поэтому наивный чанк без учёта `J_bar` будет **не полностью эквивалентен**.

---

## 3. Как сделать чанкование с `softmax_jacobian` математически точным

Есть важный момент: `J_bar` можно вычислить одним векторным проходом.

Пусть:

- `y = h_norm`
- `W_rows: [U, D]`
- `p: [U]`

Тогда:

\[
J_i = \frac{\partial (w_i^T y)}{\partial h}
\]

и

\[
\bar{J} = \sum_i p_i J_i
= \frac{\partial ((\sum_i p_i w_i)^T y)}{\partial h}
\]

То есть можно ввести:

```python
v = (p[:, None] * W_rows).sum(dim=0)   # [D]
```

и вычислить:

```python
J_bar = torch.autograd.grad(
    outputs=h_norm @ v,
    inputs=h,
    create_graph=True,
)[0]
```

Это один дифференцируемый вектор, а не `U` отдельных графов.

Дальше для каждой строки:

```python
J_i = torch.autograd.grad(
    outputs=h_norm @ W_rows[i],
    inputs=h,
    create_graph=True,
)[0]

Jp_i = p[i] * (J_i - J_bar)
loss_i = (1.0 / U) * (1.0 - cosine_similarity(Jp_i, J_tgt_p[i]))
loss_i.backward()
```

Если делать это по строкам или маленькими чанками, накапливая градиенты параметров, то математически это может быть эквивалентно полному:

```python
J_S = W_rows @ J_norm
J_S_p = softmax_jacobian(J_S, p)
loss = (1 - cos_sim(J_S_p, J_tgt_p)).mean()
loss.backward()
```

при выполнении условий:

1. `W_rows` участвует в графе, если нужен градиент по `lm_head`;
2. `h` связан с `o_proj` LoRA;
3. `J_bar` не отдетачен;
4. все строки `token_set` учтены;
5. масштабирование по `U` корректно.

**Статус:** эквивалентно в принципе, но сложнее в реализации.

## 4. Что эквивалентно только частично или не эквивалентно

### 4.1. Заморозка всех параметров при `create_graph=True`

Если вычисляется **значение** Якобиана, параметры можно считать константами. Заморозка базы — нормально.

Но если задача — получить градиент в `o_proj` LoRA через мост, то нельзя замораживать сами `A_attn`, `B_attn` или рвать граф между `h` и патчем `o_proj`.

Ваш эксперимент специально делает:

```python
def _patched_o_proj(...):
    return _orig_fwd(x) + delta
```

чтобы `h` зависел от `A_attn`, `B_attn`, а затем `create_graph=True` позволяет получить:

\[
\frac{\partial L_{\text{bridge}}}{\partial A_{\text{attn}}}, \quad
\frac{\partial L_{\text{bridge}}}{\partial B_{\text{attn}}}
\]

Если это отключить, `o_proj` будет обучаться только через KL. Это уже **не полный эксперимент 17**, а деградированная версия.

**Статус:** для значений — допустимо; для обучения `o_proj` через мост — меняет смысл эксперимента.

---

### 4.2. Использование только детаченного `J` вместо `create_graph`

Это ваш текущий OOM fallback:

```text
o_proj falls back to KL-only, lm_head keeps detached-J bridge
```

Для `lm_head` bridge остаётся валидным.  
Для `o_proj` bridge исчезает.

Математически:

```python
J_norm.detach()
```

убирает путь:

```text
bridge_loss -> J_norm -> h -> o_proj LoRA
```

**Статус:** значение моста остаётся осмысленным, но обучающее воздействие на `o_proj` через мост теряется. Это потеря части смысла эксперимента.

---

### 4.3. Уменьшение `token_set` / top-K

Например:

```text
256 -> 128 -> 64 -> 32
```

Если одновременно подрезать:

- `token_set`;
- `W_rows`;
- `J_tgt_p`;
- `p_L`;

и заново нормализовать `p_L`, то получится корректный **усечённый мост**.

Но это уже не тот же самый `L_bridge`, который был определён для исходного `token_set`.

Особенно важно: в `paper.md` есть наблюдение, что для моста иногда важны не только топ-токены, а более полный спектр/хвост. В выводах про defrag сказано, что при малом ранге мост теряет монотонность, потому что часть структурного сигнала сидит вне узкого топа.

**Статус:** приближение. Можно использовать как аварийный режим, но это меняет метрику и может изменить смысл диагностики.

---

### 4.4. Уменьшение длины последовательности `S`

Если уменьшить `S`, то изменится:

- контекст;
- кэш;
- скрытое состояние `h`;
- сам Якобиан.

Если таргеты были посчитаны для исходного `S`, то сравнивать новый студенческий Якобиан с ними нельзя без пересчёта таргетов.

Если пересчитать таргеты на том же укороченном `S`, то это будет валидный, но уже другой эксперимент.

**Статус:** приближение/смена протокола, не эквивалентно исходному эксперименту.

---

### 4.5. `bf16` / `fp16`

Для значений и градиентов пониженная точность — это приближение.

Может помочь памяти, но:

- изменит масштаб численных ошибок;
- может изменить `identity loss` с `1e-8` до заметно больших значений;
- может повлиять на косинусы там, где нормы малы;
- особенно чувствительно для ранних слоёв и очень малых градиентов.

**Статус:** не без потери точности. Можно использовать только после отдельной валидации и с пометкой, что режим приближённый.

---

### 4.6. Low-rank / defrag / случайные проекции

Идея считать не `U` строк, а `r` проекций:

\[
J^{(p)} \approx U_r J_r
\]

хороша для ускорения и для некоторых приложений.

Но для самого моста это не эквивалентно. В `paper.md` есть вывод:

- `J^(p)` имеет малый эффективный ранг;
- defrag ускоряет backward;
- но `bridge` при малом `r` теряет монотонность/структуру.

То есть для диагностики `L_bridge` это плохая замена.

**Статус:** приближение, не подходит, если нужен точный смысл моста.

---

### 4.7. Градиентный checkpointing

Сам по себе checkpointing задуман как переиспользование вычислений:

- вперёд дешевле память;
- назад — с повторным forward.

Для первого порядка он может быть математически эквивалентен, если рекомутация детерминирована и не меняет состояние.

Но в вашем случае есть проблемы:

1. Нужен `create_graph=True` / вторая производная.
2. Есть кэш.
3. Есть гибридные слои: `full_attention` и `linear_attention`.
4. GDN мутирует `conv_state` / `recurrent_state`.

Если checkpointing начнёт пересчитывать слой с кэшем и тот кэш мутирует, результат может стать неправильным.

**Статус:** потенциально эквивалентно, но только если проверено, что:

- рекоммутация не портит кэш;
- поддерживается двойной проход;
- нет недетерминированных сайд-эффектов.

Без проверки это не «безопасно без потери смысла».

---

### 4.8. Отказ от `deepcopy(prefix_cache)`

Это очень важный пункт.

Если вы просто используете `prefix_cache` без клона, а модель его мутирует, то повторные проходы будут работать уже с изменённым контекстом. Это математически неверно.

Для Qwen3.5/GDN особенно критично:

- `conv_state` мутирует in-place;
- `recurrent_state` обновляется.

Поэтому:

- либо нужен корректный `_deep_clone_cache`;
- либо read-only cache wrapper, который гарантированно не даёт мутаций;
- либо нужно клонировать только те части, которые реально мутируют, и сбрасывать их после прохода.

**Статус:** эквивалентно только если доказано, что состояние контекста не меняется между вычислениями строк. Иначе — некорректно.

---

## 5. Что можно использовать без потери точности результата

Если под результатом понимать **число `bridge_loss`, evaluation, detached-мост, `lm_head`-bridge**, то безопасно:

1. **Не строить полный `W_eff` на словарь.**  
   Использовать только `W_rows = W_eff[token_set]`.

2. **Не строить плотный `diag(p) - pp^T`.**  
   Применять проектор формулой через `J_bar`.

3. **Считать строки Якобиана по одной или чанками без общего `retain_graph`.**  
   Для значений это точно.

4. **Использовать `save_on_cpu`.**  
   Если он работает с вашей моделью, это почти бесплатная по точности страховка.

5. **Использовать CPU fallback в `float32`.**  
   Медленно, но математически почти то же самое.

6. **Не менять `token_set`, `S`, dtype, вероятность/веса.**  
   То есть все аварийные уменьшения `top_k` и `S` выключить из «точного» режима.

## 6. Что можно использовать без потери смысла эксперимента

Смысл `exp17` в том, что:

- `lm_head` LoRA обучается через мост;
- `o_proj` LoRA обучается через мост в моменты свежего `create_graph=True` Якобиана;
- между рефрешами `lm_head` может использовать stale/detached Jacobian;
- OOM fallback сейчас превращает `o_proj` в KL-only.

Чтобы сохранить смысл, нужно не потерять градиент в `o_proj`.

### Безопасные и осмысленные изменения:

#### 1. Заменить полный `J_norm [D, D]` на нужные линейные комбинации

Вместо:

```python
J_norm = compute_hidden_jacobian(..., create_graph=True)   # [D, D]
J_S = W_eff[token_set] @ J_norm
```

считать только:

```python
J_S_rows[i] = autograd.grad(h_norm @ W_rows[i], h, create_graph=True)[0]
```

Это сохраняет объект, который реально нужен для лосса.

#### 2. Делать градиентное накопление по строкам/чанкам

Не хранить все `U` вторых графов сразу, а:

```python
for i in token_set:
    loss_i = ...
    loss_i.backward()
```

или маленькими чанками.

Это снижает память, если реализовано правильно.

#### 3. Явно считать `J_bar` для `softmax_jacobian`

Чтобы чанкование не сломало проектор:

```python
v = p @ W_rows
J_bar = autograd.grad(h_norm @ v, h, create_graph=True)[0]
```

и затем использовать его в каждой строке.

#### 4. Использовать `save_on_cpu` вокруг `create_graph`

Если это работает с Qwen3.5/GDN, это хороший способ снизить GPU memory без изменения математики.

#### 5. Держать `A_attn`, `B_attn` в графе

Нельзя замораживать `o_proj` LoRA в момент вычисления свежего моста, если нужен градиент через него.

---

## 7. Что нельзя использовать, если нужна полная эквивалентность

Если цель — «не улететь в OOM, но не потерять смысл и точность», **нельзя** считать допустимыми:

1. `h.detach().requires_grad_(True)` для `create_graph`-моста без отдельного живого пути через `o_proj`.
2. Заморозку `A_attn`, `B_attn` во время вычисления свежего `J`.
3. Удаление `create_graph` для `o_proj`, если эксперимент заявляет обучение `o_proj` через bridge.
4. Обрезку `token_set`, если она не объявлена как отдельный приближённый режим.
5. Уменьшение `S` без пересчёта таргетов.
6. `bf16/fp16` без отдельной валидации.
7. Низкоранговые проекции вместо полного моста.
8. Использование кэша без гарантии неизменяемости.

## 8. Что из этого объясняет ваш лог

В логе видно:

```text
Pair 31_23: J_norm done 1024/1024 in 0.7s
Pair 28_21: J_norm done 1024/1024 in 31.6s
Pair 24_18: OOM around 512/1024
Pair 20_15: OOM around 256/1024
Pair 16_12: OOM around 128/1024
```

Это очень похоже на то, что `create_graph=True` держит графы для всё большего числа строк `J_norm`. Чем раньше слой, тем больше оставшихся слоёв и тем дороже каждый граф.

То есть узкое место — не обязательно сам `J_norm` как матрица `1024×1024`, а **графы для каждой строки**, создаваемые:

```python
torch.autograd.grad(..., retain_graph=True, create_graph=True)
```

Поэтому самый осмысленный точный путь — не хранить все строки `J_norm` с живыми графами, а вычислять только нужные комбинации `W_rows @ J_norm` и сразу делать вклад в лосс.

---

## 9. Практический вывод

### Полностью безопасно для точности и смысла, если нужно только значение моста

Можно:

- считать только `W_rows`;
- не строить полный `W_eff`;
- использовать безопасный `softmax_jacobian`;
- считать строки по одной;
- использовать `save_on_cpu`;
- использовать CPU в `float32`.

### Безопасно для смысла полного `exp17`

Можно, но требует аккуратной переделки:

- вычислять не полный `J_norm`, а только `J_S = W_rows @ J_norm`;
- делать это через `create_graph=True`;
- накапливать градиенты по строкам/чанкам;
- явно учитывать `J_bar` из `softmax_jacobian`;
- не детачить `o_proj` LoRA в свежем графе.

### Не безопасно без потери смысла

Нельзя для полного эксперимента:

- просто заменить `create_graph` на detached row-wise Jacobian и сказать, что `o_proj` всё ещё обучается через мост;
- заморозить `o_proj` LoRA во время свежего моста;
- обрезать `token_set`/`S` без пересчёта таргетов и без пометки, что это другой режим.

## 10. Минимальная рекомендация

Если нужна максимальная вероятность сохранить смысл `exp17` без математических потерь, я бы делал так:

1. Для `lm_head` bridge оставить detached `J_norm` или считать его безопасно по строкам.
2. Для `o_proj` заменить полный `create_graph` `J_norm [D,D]` на **матрично-свободное вычисление нужных строк**:
    - `W_rows = lm_head.weight[token_set] + B_lh[token_set] @ A_lh`;
    - вычислить `J_bar` через один векторный проход;
    - для каждой строки или чанка считать `J_i = grad(h_norm @ W_rows[i], h, create_graph=True)`;
    - сразу формировать `loss_i` и делать `backward()`.
3. Обернуть это в `save_on_cpu`, если GPU memory всё равно не хватает.
4. Только если это не влезает — переходить к явно приближённым режимам: меньше `token_set`, меньше `S`, `bf16`, CPU, — и помечать их как отдельные аварийные конфигурации.

То есть **главное точное изменение**: не пытаться удержать в памяти весь `J_norm` с живыми графами, а вычислять только те его линейные комбинации, которые реально участвуют в `bridge_loss`.
