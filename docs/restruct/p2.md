# Предложение по реструктуризации: MAIN + 4 REF-документа

## 1. Диагноз: что делает документ громоздким

Текущий документ смешивает три разных типа контента:

| Тип | Примеры | Кому нужно |
|---|---|---|
| **Утверждения и их доказательная база** | «мост монотонен», «поле J fibered», «ρ_gf < 0.1» | всем читателям |
| **Полные протоколы экспериментов** | params, N, K, S, T-блоки, P0-баги, оговорки | тем, кто воспроизводит/проверяет |
| **Сырые данные и код** | листинги, JSON-ключи, все промежуточные числа | тем, кто пересчитывает |

Сейчас ~60–70% объёма — это типы 2 и 3, «вклеенные» в основной текст. Из-за этого:
- основной нарратив тонет в деталях (E-32r.3 занимает ~1 страницу ради 3 выводов);
- невозможно быстро оценить статус и перспективы;
- обсуждение «что делать дальше» требует чтения протоколов.

## 2. Целевая структура: 5 документов

```
MAIN.md          — самодостаточный обзор (~35–45 стр.)
REF-MATH.md      — полный матаппарат + доказательства
REF-EXP.md       — полный журнал экспериментов (все E-*)
REF-CODE.md      — листинги, инфраструктура, статистика
REF-INDEX.md     — глоссарий, индексы символов/экспериментов/гипотез
```

**Ключевой принцип:** MAIN содержит всё необходимое для понимания и обсуждения; REF — для проверки, воспроизведения и углубления. MAIN не требует открытия REF для понимания результатов.

## 3. Структура MAIN (v5.0)

- 7 ключевых findings — по 1–2 строки каждый
- Статус P0–P3 (таблица)
- Как читать документ (навигация к REF)

### I. Проблема и подход (~4 стр.)
- §1 Мотивация, цели, статус (сжать: убрать повторы P0/P1/P2)
- §2 **Эссенциальные** символы (только используемые в MAIN; полный индекс → REF-INDEX)
- §3 Архитектурный контекст (сжать: GDN-детали, in-place мутации → REF-CODE)

### II. Метод (~8 стр.)
- §4 Якобиан, модели, размерности — определения + `[L-dim]`, `[L-comp]` как **утверждения** (доказательства → REF-MATH)
- §5 Gramian-коррекция — `[L-gram]` + identity-результат; proof → REF-MATH
- §6 ESG, спектральные метрики, ранги — определения + `[L-rank]`, `[L-fisher]`
- §7 Gap и bridge — **полностью** (это ядро; sentinel-режимы, направления, масштабная слепота)
- §8 Gauge-оператор — `[L-gauge]`, `[L-gauge-J]`, `[L-rms]` как утверждения; proofs → REF-MATH
- §9–10 Реализация — 1–2 стр. обзора (3 прохода, batched backward, GDN-cloning); код → REF-CODE
- §11 Диагностика P0/P1 — краткий обзор

## 4. Правила разнесения

| Контент | Куда | Обоснование |
|---|---|---|
| Определения, леммы (утверждения) | **MAIN** | нужны для понимания |
| Доказательства лемм | **REF-MATH** | нужны для проверки |
| Формулы с выводом (Приложение D/E) | **REF-MATH** | проверка |
| Полные протоколы экспериментов (params, N, K, S) | **REF-EXP** | воспроизведение |
| T-блоки, P0-баги, оговорки | **REF-EXP** | верификация |
| Сырые числа сверх ключевых | **REF-EXP** | пересчёт |
| Листинги кода | **REF-CODE** | воспроизведение |
| Инфраструктура (загрузка, кэш, статистика) | **REF-CODE** | воспроизведение |
| Полная таблица символов | **REF-INDEX** | справка |
| Полный глоссарий | **REF-INDEX** | справка |
| Индекс экспериментов B.1, реестр H1–H8 | **REF-INDEX** | справка |
| Ключевые числа (1–2 на finding) | **MAIN** | понимание |
| Ссылки на JSON/скрипты | **REF-EXP/CODE** | проверка |

**Правило:** если утверждение в MAIN требует числа для понимания — оставить 1–2 ключевых; полную таблицу — в REF. Если эксперимент — kill-switch или foundational — дать больше контекста в MAIN (E-0.1, E-1, E-3, E-34), остальные — 1–2 строки.

## 5. Что выигрываем

- **MAIN ~35–45 стр.** (vs текущие ~150+): читается за 1–2 часа, достаточен для обсуждения.
- **Executive Summary** даёт статус за 2 минуты.
- **Findings-ориентация** позволяет обсуждать «что это значит», не продираясь через протоколы.
- **REF-EXP** сохраняет полную воспроизводимость (ничего не теряется).
- **Навигация** явная: каждый finding ссылается на REF-EXP §, каждая лемма — на REF-MATH §.

## 6. План миграции (порядок действий)

1. **Создать Executive Summary** — выписать 7 findings + статус из текущего §20.
2. **Создать §III Findings** — сгруппировать текущие E-* по 8 findings, сжать каждый до 1 абзаца + ключевые числа (использовать §20 «Подтверждено» как основу).
3. **Перенести Part V (Эмпирика) целиком → REF-EXP** без потерь; в MAIN оставить только Findings-сводку.
4. **Перенести доказательства** из Part II и Приложений D/E → REF-MATH; в MAIN оставить формулировки лемм.
5. **Перенести листинги C.1–C.9 + инфраструктуру §12–13 → REF-CODE**; в MAIN — §9–10 обзор.
6. **Перенести полные таблицы символов (§2), глоссарий (A), индексы (B) → REF-INDEX**; в MAIN — эссенциальные символы + краткий глоссарий.
7. **Обновить «Как читать»** — навигация по 5 документам.

## 7. Риски и как их снять

- **Риск:** читатель MAIN не поймёт, почему finding валиден, без протокола. → **Решение:** в каждом finding — 1–2 ключевых числа + статус (N, CI, метод) + указатель на REF-EXP.
- **Риск:** REF-EXP станет «свалкой». → **Решение:** сохранить текущую структуру E-* внутри REF-EXP (она уже стабильна и проиндексирована); MAIN ссылается на §E-*.
- **Риск:** дублирование определений между MAIN и REF-INDEX. → **Решение:** MAIN — определения, используемые в тексте; REF-INDEX — полная таблица + расширенный глоссарий; каноническая секция — одна (в MAIN), REF-INDEX ссылается.

## 8. Итоговая рекомендация

Принять структуру **MAIN + 4 REF** с Findings-ориентацией MAIN. Это сохраняет всё необходимое для понимания и обсуждения в одном файле (~35–45 стр.), а полную доказательную базу и воспроизводимость — в четырёх справочных документах. Начать с шагов 1–3 (Executive Summary → Findings → перенос Part V в REF-EXP): это даст 80% эффекта при минимальных усилиях.
