## 2. Что именно проверять (по находкам)

### M1 — `svd_top`: отрицательные шаги в выходах (был КРАСНЫЙ тест в репо)
Было: `U_out = U0[:, ::-1]`, `Vh_out = V[:, ::-1].T` → `torch.from_numpy` (потребитель —
`prism/backend.py`) падал `ValueError: ... negative strides`.
Стало: helper `_pos_strides` (`sycl_prism/py/prism_sycl.py`), применён в ОБЕИХ ветках
(m<n и m≥n).
Проверь КРИТИЧЕСКИ:
1. `_pos_strides` проверяет **шаги**, а не флаг `C_CONTIGUOUS` — это существенно: у
   вырожденных осей (shape `(1,1)`, `(1,r)`) numpy считает view «contiguous» и
   `ascontiguousarray` НЕ копирует, оставляя strides вида `(4,-4)`. Воспроизведи:
   `np.zeros((1,1),np.float32)[:, ::-1].flags['C_CONTIGUOUS']` → True при strides (4,-4).
2. Оба выхода покрыты (U и Vh), обе ветки.
3. Значения не изменились: сверка с `np.linalg.svd` (f64) по σ и подпространствам.
4. Логика REVERSE по-прежнему соответствует конвенции torch (S descending): сравни с
   CPU-веткой `Backend.svd_top` (`torch.linalg.svd`).

### M2 — `svd_top`: ложный лимит (заявляли m,n ≤ 1024, падало при min(m,n) > 256)
Было: внутренний `eigjac` лимитирован n ≤ 256, guard `svd_top` этого не знал → падение
из чужого слоя. Стало: guard `min(m,n) <= 256` + сообщение на уровне svd_top.
Проверь: (а) большой-но-узкий случай ОБЯЗАН работать (257×40, 1024×128: малая сторона
≤ 256); (б) 300×400 и 257×300 — ошибка ИМЕННО svd_top; (в) согласованность лимита в
`docs/TZ_sycl_new_ops.md` §2.4, `docs/SYCL.md` §4.4, docstring `ps.svd_top`, docstring
`Backend.svd_top` — четыре места, ни одного противоречия.

### m1 — `eigjac(curve=...)`: тихий no-op
Было: `np.asarray(curve, np.float64)` копировал f32/список ⇒ «на месте» не выполнялось.
Стало: требуется `np.ndarray` c `dtype == float64` (иначе ValueError), C-contiguous.
Проверь: контракт «на месте» реально работает для f64; f32/список — ValueError; в TZ
§2.3 записано ограничение типа.

### m2 — комбинированный объём памяти
Добавлено: `_mem_budget_bytes()` (кэш 0.5·global_mem, iGPU делит RAM с хостом) +
`_check_mem()`, применено в `gemm`, `eigjac`, `eigbot`; в C++ сообщения о
`malloc_device failed` теперь содержат GiB и размерности.
Проверь: (а) формула `need` для каждого вызова соответствует реальным буферам
(`gemm`: dA M*K + dB K*N + dC M*N + хост-копия C; `eigjac`: 2 dev + 3 host по
batch*n²; `eigbot`: 4 f64-копии host-Cholesky + L32 + dev-копия); (б) нет ложных
срабатываний на реальных размерах AT2c/AT0_3 (128×1024, 1024×128, batch=16384 n=128,
batch=1024 n=256); (в) в reference-режиме guard не мешает; (г) guard не перекрывает
проверку dtype/формы неудобным образом.

### m3 — формула local-бюджета
Было (py и cpp): `2*n*r*4 + r²*4 + 64*4` — члена `r²*4` в ядре `eig_iterate` НЕТ,
`sh` = `WG+1` = 65 элементов, не 64. Стало: `2*n*r*4 + (WG+1)*4` (py `_WG = 64`).
Проверь СВЕРКОЙ С ЯДРОМ (`sycl_prism/src/prism_sycl.cpp`, `eig_iterate`:
`local_accessor<float,1>` lv/lw/sh — их реальные размеры) и что граница приёма не
сдвинулась вредно: n=1024 → r=7 принимается, r=8 → PS_ERR_LOCAL. Заодно: сообщения
об ошибке в py и cpp содержат ТУ ЖЕ формулу, что и код (не осталось старой строки).

### n1–n5, n6, n7 (ниты/миноры)
- n1: отступ `hResid[b] = ...` восстановлен внутри цикла `eig_postprocess`.
- n2: дублированный/противоречивый комментарий у `EIGJAC_CHUNK` сведён в один
  (старый блок утверждал «правило TZ ⇒ C=256», фактическое значение — 64).
- n3: мёртвая ветка `local_bytes = 0; if (> 65536)` в `eigjac_impl` удалена.
- n4: `std::stable_sort` по λ — NaN уводится в конец (компаратор больше не нарушает
  strict weak ordering).
- n5: убрана лишняя копия `astype(np.float32)` над уже-f32 массивами в `svd_top`.
- n6: `permutation_null` при `K < 9` — ValueError вместо тихого `band=NaN`.
- n7: `acf_moments` при `K > N-1` — ValueError с диапазоном, как в reference
  (раньше RuntimeError «неверные аргументы» из C).
- n8: симметрия входа `eigjac` — записана как КОНТРАКТ в TZ §2.3 (проверка не добавлена
  сознательно). Оцени, приемлемо ли это решение, или требуй проверку.

### Отдельно: два бага, найденных ПО ХОДУ закрытия (проверь их правки особенно строго)
1. **Каскадный баг, внесённый в правку m2 и исправленный**: в `eig_impl` условие
   `(!dA.p || (inverse && !dL.p) || !dV.p)` было заменено на `!dL.p` без guard
   `inverse` ⇒ `eigtop` (inverse=false, `dL` намеренно нулевого размера) падал
   «malloc_device failed» на ВСЕХ размерах. Сейчас guard восстановлен. Проверь, что
   в коде нет других мест, где `Dev(q, 0)` (нулевой размер) трактуется как ошибка.
2. **`prism/backend.py`, 2D-ветка `matmul`**: `a2` не присваивался (только в
   `if was_3d`) ⇒ `UnboundLocalError` на `ps.gemm`, то есть 2D-matmul через sycl не
   работал никогда; тест `tests/test_backend.py::test_sycl_matmul_2d` был КРАСНЫЙ.
   Сейчас `a2 = a`. Проверь ветку целиком (was_3d True/False, формы, dtype, порядок
   `reshape`) и что нет такого же дефекта в других методах backend (`eigh`, `svd_top`).

### Известное ОЖИДАЕМОЕ изменение артефакта (не считать регрессией без проверки)
`results/AT0_3/eigjac_convergence.json`: `wall_s` для L6/L23 был 0.05/0.035 с
(состояние ДО чанкинга: весь sweep-цикл в ОДНОМ запуске ядра), стал ~1.9/1.3 с.
Причина — не замедление ядра, а фиксированный оверхед запуска на чанк (F1-watchdog:
1 launch = 1 чанк, host-стоп-проверка): для batch=1 это `sweeps_to_1e-5`=6 запусков
по ≈0.3 с (строка `c1≈0.35с` тюнинг-таблицы = стоимость ОДНОГО запуска). Проверено:
`offdiag_final` бит-в-бит совпадает между двумя прогонами (`1.469484374183594e-07`),
`test_eigjac_determinism` зелёный. Оцени: (а) согласуется ли это с тюнинг-таблицей
в `eigjac_tuning.json`; (б) не пора ли записать этот трейд-офф в TZ §2.7 явно
(твоё мнение — в отчёт, правку не делаешь).

## 5. Критерии вердикта
- PASS — все M1/M2/m*/n* закрыты, регрессий нет, доки согласованы.
- PASS_WITH_MINORS — закрыто, но остались ниты, не влияющие на контракты.
- REVISE — есть незакрытая находка, регрессия, несогласованность доков с кодом или
  guard, который не достигается.
- FAIL — правки ломают работу (например, `eigtop`/`matmul`/`svd_top` перестали
  работать на заявленных размерах).

Помни: «тест зелёный» ≠ «контракт выполнен» — проверяй именно контракт (dtype, шаги,
порядок, «на месте», лимиты) и сверяй числа с `np.linalg`/reference-бэкендом.
