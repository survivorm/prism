## Про хранение

Согласен с ощущением, но вывод не «артефакты в Kaggle, git чистый». Правильное разделение — **bytes и утверждения — разные слои**:

| слой | что | где |
|---|---|---|
| **Claims** | per-experiment JSON: параметры, sha входов, sha оценщика, числа, null-полоса, вердикт | **в git** (КБ–МБ) |
| **Bytes** | npz/pt (траектории, веса, лупы), логи | **hash-addressed store вне git** + зеркало |
| **Manifest** | claim-id → {script_sha, bytes_sha256, params, verdict} | **в git** (КБ) |

Правило проверяемости: *утверждение проверяемо ⇔ его строка в manifest + её bytes fetch-ятся и совпадают по sha*. И `prism/artifacts.py` на 80 строк: manifest → локальный кэш → иначе скачать из зеркала → **сверить sha** → отдать путь.

**Kaggle-dataset — да, но как зеркало, не как основное хранилище:** сеть становится обязательным шагом каждого перезапуска; ревизия датасета — mutable-контейнер, поэтому нужен sha-пин, иначе «скачалось то же» не гарантия; и это риск повторить §42 в другом месте (единственная копия в одном аккаунте). Ranking: (1) content-addressed локальный store `/data/prism_artifacts/<aa>/<sha>.bin` + manifest в git — обязателен, дёшев; (2) off-machine зеркало — Kaggle dataset **или** GitHub Release, пин ревизией + sha, и лучше два независимых; (3) Git LFS — только если хочется git-native (квота GitHub 1 ГБ упрётся первым томом).

**Первое зеркало — сегодня.** После §42 от артефактов Nov6–10 не осталось ничего, а в репозитории их нет вообще (`.gitignore:72` = `results/e*/**`). То есть сейчас новый корпус существует в одном экземпляре на одной машине — это ровно та конфигурация, которая уже один раз всё сожгла.

## Куда двигаться содержательно

**Главная ставка: «поле как ёмкость», а не «кривая как объект».**

Формулировка: у модели есть **измеримая ёмкость** — локальное выученное поле шага. Её сила растёт с обучением, у неё есть **порог и насыщение**, она **текстово вызывается**, **не зависит от политики генерации**, её **не несёт случайная модель**, и — ключевое — она **причинна для дальнего адресования (роутинга)**, хотя не несёт смысла.

Почему именно эта ставка: она единственная даёт **положительный** количественный результат, связывает две половины серии (геометрию и поведение), имеет уровни 0/Z/M, объясняет, зачем проект вообще нужен (монитор/диагностика/починка), и **фальсифицируется целиком** — если поле не нужно для роутинга, программа умирает целиком, а не по частям.

| уровень | утверждение | предсказание | фальсификатор |
|---|---|---|---|
| **0** | поле — ёмкость | R-нулевой уровень точен (4e-6), текстовость, позиционная слепота | поле есть у random-весов |
| **Z** | **доза–ответ** с порогом и насыщением | λ≤0.5 ⇒ ~0; взрыв 0.6→0.7; плато глубже финального (сверхвыброс) | на 3 сидах и soup-пути линейно ⇒ порога нет |
| **Z** | **ось масштаба**: позиция горба постоянна **в токенах** (≈3–4), но не в словах | hump_words = hump_tokens / tok-per-word(домен) различается code/math/chat | hump одинаков и в словах ⇒ масштаб не токенный (N-2 закрыт границей, но **не опровергнут**) |
| **M** | **необходимость**: модель без поля теряет иглу на 32k и не получает выигрыша от «режима» | BASE-random ≈ 0.75 или хуже, эффект режима ≈ 0 | random-веса тянут иглу ⇒ поле не нужно для роутинга |
| **M** | **достаточность**: инъекция бризера в состояние **улучшает** извлечение | при равной ёмкости needle ↑ | инъекция ухудшает ⇒ поле — побочный продукт |

**Что запускать (по цене, без новых метрик):**
1. **«Золотая пятёрка»** (1 день) — один скрипт пересчитывает 5 опорных чисел (dip-anchor, hump, plateau, R-null, λ₁) с sha оценщика и null-полосой в manifest. Это минимальный «репо-инвариант»: после него слова про поле снова можно проверять, а не пересказывать.
2. **Hump в словах** (30 мин, на имеющихся кривых) — самая дешёвая попытка закрыть N-2 на своих данных.
3. **Random-веса на 32k-игле** (1 GPU) — тест «необходимость», прямая сшивка геометрии с поведением.
4. **Инъекция бризера** (1–2 GPU) — тест «достаточность», первый **интервенционный** тест поля в серии ⇒ переход на уровень M.
5. **Base vs instruct (E-73)** — чьё это поле: обучения или выравнивания.
6. **Доза–ответ с 3 сидами + soup** (2–3 GPU) — закон, а не кривая; чинить гейт E-71 по ревью (ступенька **в коде**, контроль на усечение, ≥3 сида).

**Что расчистить, иначе серия читается как программа отрицательных результатов:**
- **e76…e85 («оптика динамики»)** — держать как приложение, не как ярус: там виден паттерн «каждая гипотеза умирала как артефакт» (фантомный lane, поздние провалы e, мёртвый гейт e80). Честно, но это не результат.
- **ω̂ выкинуть** — не переносится между моделями; заменить на позицию горба и на λ₁ (спектральный, осмысленный).
- **Два канала** — оставить как рамку диагностики (R/P + петля), но не как отдельный сюжет: это инструмент, а не результат.
- **Правило клетки** (уже принято): клетка = предсказание + фальсификатор; без фальсификатора не запускается.

**Чего не делать:** не расширять линию «ещё одной метрики» (e83/e85 — MDL/генеративное ядро: красиво, но это ещё один язык описания); не публиковать survivor-8 до честного LFM3-повтора; не начинать новую серию до «золотой пятёрки» — иначе третий раунд подряд будет разговаривать сам с собой.

**Моя сводка:** инфраструктура доверия (оценщик в git + manifest + золотая пятёрка) — 1–2 дня, это не «инфраструктура ради инфраструктуры», без неё всё дальнейшее — проза; ставка — «поле как ёмкость» с тремя уровнями; чистка e76…e85 в приложение.

Нужны от вас два решения: (1) утверждаем архитектуру «manifest в git + hash-store + Kaggle-зеркало» (или выбираем другое основное хранилище)? (2) «поле как ёмкость» становится главной линией, а e76…e85 уходят в приложение — да/нет? Если да, следующим шагом сделаю сам: манифест-слой + `prism/artifacts.py` + скрипт «золотой пятёрки» (считается на CPU, без torch, если поле можно пересчитать из npz).
