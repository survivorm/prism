## A (критичное): «G0a_tpu_hn_field не проверяет то, что заявлено»

**Частично принимаю. Техническое ядро — отвергаю: анализ ревью рассмотрел только одну из двух
веток `load_source`.**

`a1.load_source` (experiments/AT0_1_accounting.py:163-198) имеет две ветки:

1. **state (32 дока: own + corpus)** — `h` читается из raw-массива npz, `hn = ‖row‖` и
   `u = h/‖h‖` **пересчитываются**; хранимое `_hn`-поле (баг продюсера — колонные нормы)
   **не читается вообще** (проверено чтением кода, стр. 186-188). Для state ревью прав:
   unit-пин структурно истинен = регрессионный guard, а не проверка данных. Recon-проверка
   `U·hn vs raw h` для state — тождество (hn вычислено из этого h), данные она тоже не
   проверяет. Именно поэтому AT0_3 и подписывает свой check как «live_check», а в claim
   пишет: «a1.load_source пересчитывает row-нормы из raw-строк (_hn-поле не читает)» —
   те же выводы.

2. **gen (64 дока)** — в npz **только `_u` и `_hn`** (проверено: 704 ключа, pattern
   `{doc}_L{L}_u` / `_hn` / `_tok`; raw h отсутствует). `h_raw = U·hn` — и TPU hn-баг
   в pipeline входит именно через эти хранимые поля. Здесь unit-пин — **реальная проверка
   поля данных**: замер max dev = 2.43e-4 (= fp16-шум), tol 5e-3. Recon-проверка
   ревью (`U·hn vs raw h из npz`) для gen **невозможна** — raw h в файле нет.

Итог: «check не ловит случай B, ради которого написан» верно только для state, где
случай B на результат не влияет (поле не читается). Для gen ловля есть (unit-пин на
`_u`), плюс — см. самокоррекцию ниже.

**Самокоррекция (ревью навело на реальный баг в моём комментарии):** scale-пин
(«mean(hn) ≈ RMS(h)·√D») — это **проверка однородности row-скал** (sdev ≈ CV²/2), а НЕ
row-vs-column: для константных колонных норм dev = 0 — пин проходит. Мой комментарий
«разделение √(1024/384) = 1.63» — неверен. Замеренная чувствительность: ловит CV ≳ 0.63.
Замер gen: scale-dev 0.023 ⇒ CV ≈ 0.21.

**Остаточный риск (зафиксирован в claim, поле `G0a_hn_field.gen_layers.residual_risk`):**
константный или слабо-неоднородный `_hn` (CV < 0.63) недетектируем от файла — независимого
референса row-скал в gen npz и meta (только dom/si/sha_ok/gen) нет. Замеренная
разбросность hn 0.93–1.87 согласуется с истинными row-нормами, но это согласование,
не доказательство.

**Что сделано:**
- гейт вынесен в функцию `g0a_hn_gate(docs)` (fail-loud до цикла клеток — п. F);
- записан в claim (`gates.G0a_hn_field`): что именно проверяется на каждом source,
  замеренные deviations, пороги, residual_risk;
- сообщение об ошибке и logline говорят ровно то, что проверяется (без «hn не
  row-norm'ы» как утверждения о данных);
- designed-сценарии протестированы exec'ом точной функции (AGENTS.md п. 2):

| сценарий | исход |
|---|---|
| реальные данные (96 доков × 5 слоёв) | PASS: state 3.33e-16, gen unit 2.43e-4, scale 0.023 |
| state-регрессия: u построен из column-norm'ов | **CAUGHT** (dev 0.640) |
| gen: порча скал CV ≈ 1 (экспоненциальные множители) | **CAUGHT** |
| gen: константный hn | PASS — задокументированное ограничение |

## B (существенное): «AR refuted по D_center_l1, который знак-зависим»

**Механизм принимаю (он верен), в текущих данных вердикт НЕ sign-driven — замерено.**

Механизм: `band_shares_vec` делит band-массы на `(r−1)/2` (знаковая полная сумма лагов),
так что при расхождении знаков real/null `D_center ≈ |P_real| + |C|` — надувается.
Ревью прав в том, что это возможно.

**Замеры (store #1, все 9 пар (obj, ar) × 478 клеток):**
- Знаки real: h_raw и du_unit — **отрицательные** (frac_neg = 1.00 по всем 478 клеткам,
  median sum_rho = −0.497); v_tangent — **положительные** (median +16.1).
- Знаки AR-null: median по клеткам −0.26/−0.36/−0.43 (h_raw/du_unit, ar1/ar2/ar4) и
  +16.4 (v_tangent). **Причина согласования: AR-фит (Yule-Walker) строится по ACF real —
  null наследует знаки real.**
- Frac сидов со знаком, совпадающим с real: **mean = 1.00, min = 0.90** (одна клетка
  du_unit ar1).
- **Решающий тест**: D_center с sign-flip null-профиля к знаку real — **идентичен**
  orig до медианы во всех 9 парах (1.679/0.794/0.374/1.684/0.793/0.382/0.034/0.023/0.022).
  Вердикт не sign-driven в этих данных.

**Что сделано (варианты b+c, без смены pre-reg метрики):**
- пер-cell `frac_cells_seed_sign_mismatch` (доля сидов со знаком ≠ real, усреднённая по
  клеткам) + `sign_check_ok` (≤ 0.1);
- note в агрегате: «verdict — из D_center_l1 (sign-normalized профили); интерпретация
  'про band-форму' валидна при sign_check_ok; при расхождении знаков refuted был бы
  sign-driven» + механизм согласования знаков;
- pre-reg (store) дополнен тем же условием.

**Вариант (a) (verdict из D_bands_L1) — отвергаю:** D_bands_L1 тоже несёт знаковые
band-массы (свободен только от нормировки на полную сумму — sign-safe в слабом смысле),
у него нет null-распределения, а pre-reg метрика — D_center. Смена метрики post-hoc —
нарушение пре-регистрации.

## C: «band_sums_direct — нет guard lo > hi»

**Отвергаю: guard — мёртвый код, сценарий недостижим.**

Инвариант: в `BANDS = ((1,1),(2,2),(3,8),(9,32),(33,96))` для каждой полосы lo ≤ hi.
`if lo > N−1: continue` стоит **до** использования hi; если lo ≤ N−1, то
`hi_new = min(hi, N−1) ≥ min(lo, N−1) = lo` ⇒ `lo > hi_new` невозможно. Проверка на
N = 20: (1,1): S1 = C[2:21]−C[1:20] (оба длина 19); (2,2): S1 = C[3:21]−C[2:20] (18);
(3,8): hi_new=8, t1=12, S1 = C[9:21]−C[3:15] (12); (9,32): hi_new=19, t1=1,
S1 = C[20:21]−C[9:11] (1); (33,96): lo=33 > 19 → пропускается. Краша нет.

Guard на недостижимый случай — шум (AGENTS.md п. 2: «guard, чей результат… — мёртвый
код»). Вместо ветки — комментарий с инвариантом в коде.
