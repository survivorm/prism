# GEMM-тюнинг: свипы, физика, выбранный конфиг (17.11, сессия AT0_3)

Пробы: zz_sweep2/2b/3/4/5 (свипы), zz_microbench (потолки), zz_devinfo (EU/clock),
zz_repro/2 (воспроизводимость), zz_sustained* (sustained-режим), zz_buf_*/zz_oldpat* (история v17).

## Физика устройства (Iris Xe, ADL-P, 96 EU)
- FMA-пик: 96 EU × 8 FMA × 2 op × clock. @300 MHz = 460 GF/s; @1250 MHz = 1.92 TF/s.
- GPU **не фиксирует clock сам**: idle 300 MHz, под нагрузкой boost 733–1250 (терм. огранич. iGPU).
  `intel_gpu_frequency --set` требует root (нет).
- **Sustained-трюк**: непрерывная fire-8-kernels-без-wait петля удерживает 1250 MHz стабильно
  (120 сэмпл-точек, все 1250). Это честный sustained-режим для замеров без root.
- SLM-пропускная ~780 GB/s (zz_microbench, clock-зависимо). DRAM ~24–30 GB/s.
- **Driver-state нестабильность** (подтверждено 2×): burst-замеры дают фантомные цифры
  (1956 GF/s, 2.3× разброс FMA-бенча). Даже llama.cpp бьётся по прогонам 20.7–30.1 tok/s (37%).
  Sustained-замер моего ядра: 168.3/169.6 GF/s (0.8%) — стабильнее llama.
- `gt_cur_freq_mhz` в процессе ядра читает 300 даже под нагрузкой — не использовать для нормировки.

## Свипы (S0-верификация 1024³ на каждом конфиге, S1 = 4096×1024×4096)
- Тайлы 16–64 (sweep3/4): плато 90–171, шипы (64×8 kc8: 140.9), ландшафт не одноэкстремальный.
- Большие тайлы (sweep5): **не взлетели**. 128×128 kc8 noDB 145.8; 256×128 kc8 107.3;
  512×* = 12–17 GF/s (CPT=128 → register spill). 128×64 kc16 db = 171.8 ≈ лучший маленький (168).
  Вывод: при лимите 512 тредов/WG «больше лучше» не работает (у llama.cpp до 1024 тредов/блок).
- 2-колонные (c2, 32 строк × 2 кол/нить, gemm_usm5): SLM-байты на FMA /2 (4.1→2.1) —
  НЕ дало выигрыша (109.1 vs 117.6 в одном прогоне): 64 acc-регистра съели occupancy.
- Баг, пойманный S0-верификацией: gemm_usm4 не поддерживал TC>WGC (1 кол/нить), c2-вариант
  писал пол-колонн → FAIL. Заменён gemm_usm5 (acc[CPT][CPTC]).

## Зафиксированный конфиг
**gemm_usm4/5 <128,64,4,64,16,true>** (TR=128, TC=64, WGR=4, WGC=64, KC=16, double-buffer):
- sustained @1250 MHz, N=4096: **168–170 GF/s** (2 прогона, 0.8%)
- sustained @1250 MHz, N=248320 (реальный z_full 4096×1024×248320): **116.6 GF/s**
  → 2.06 TFLOP / 116.6 = **17.7 с vs ~29 с CPU (1.4×)**
- SLM: (128×16 + 16×64)×4×2 (DB) = 32 KB. WG=256 тредов, 32 FMAs/тред/kk (CPT=32, 1 кол).

## Отставание от llama.cpp и что дальше
- llama-bench p4096 Q4_K_M (SYCL, b=2048/ub=512 — лучший из 4 b/ub): 27–30 tok/s ≈ 440–480 GF/s экв.
  (16.1 GFLOP/tok). Отрыв 3–4× объясняется квантованием A (Q4_K: SLM/DRAM-байты /8) — не тайлингом.
- fp16-A в SLM (байты /2, без потери формата входа) — следующий рычаг, если 1.4× на wide-N
  окажется недостаточно для бюджета AT2c; решение — на TZ-ревью (точность ps.gemm vs f64-эталон).

## Протокол замеров (обязателен для любых GPU-чисел в этом репо)
1. S0-верификация (1024³ vs f64-эталон, rel<1e-2) ПЕРЕД замером каждого конфига.
2. Sustained-режим (fire-8 без wait, ≥25 с), не burst-5-итераций.
3. Частоту брать внешним сэмплером (separate process) в sustained-окне; внутрипроцессные
   чтения 300 под нагрузкой — артефакт.
4. Сравнение конфигов — ТОЛЬКО в одном прогоне (межпрогонный дрейф больше внутрипрогонного).
