## A. Текст ТЗ, который ревьюится (дословно)

```markdown
# E94/S3b — микро-рука: кусается ли `top_k` на этом форке (предрегистр, 02:49 UTC)

## Зачем (один вопрос, не про M1/M2)

Условие 2 гейта руки B требует «эмиссент зависит от ширины набора / на контроле нет».
Прогон S4pp дал `probe_dependence=false`, но само-ревью (`2_REVIEW_E94_probeS3S2S4_exec_r1.md`
§1, §8) показало, что свип **не демонстрировал применения ширины**: при `top_k=1` и `top_k=400`
отчёт одинаков (`n_tl=20`, один порядок id), а по исходнику (`server-context.cpp:1790`)
отчёт при `post_sampling_probs=false` берётся из логов ДО сэмплера — то есть путь отчёта
**в принципе** не может показать действие `top_k`.

Вопрос руки S3b один: **применяется ли `top_k` к пост-сэмплированному набору кандидатов на
этом форке.** Ответ определяет статус текущего `gate2_met=false`:
«отрицательный результат» или «инструмент не годится». Про M1/M2 здесь не говорится ничего.

## Что уже известно из исходника (догадки не тестируем)

* `populate_token_probs`, ветка `post_sampling` обрывает цикл на первом `p == 0.0`
  (`server-context.cpp:1967-1992`). При `temperature=0` вероятности не считаются →
  отчёт пуст при любом `top_k`. **Значит контроль при T=0 мёртв; нужен T>0.** Это же
  объясняет `n_tl=0` у `S2a/S2b` в основном прогоне.
* `top_k` в цепи сэмплеров есть (`samplers=[...,top_k,...,temperature]` — эхо артефакта),
  `speculative.types=none`.

## Запросы (4, один запуск сервера, аргументы и модель как в S4pp)

Общая форма: `temperature=1.0`, `seed=8181`, `n_predict=1`, `cache_prompt=false`,
`post_sampling_probs=true`, `n_probs=20`, `logprobs=true`, `top_logprobs=20`.

| tag | адрес | top_k |
|---|---|---|
| `S3b-k1-probe`   | Q2 w4 k=70 (адрес пробы) | 1 |
| `S3b-k400-probe` | Q2 w4 k=70 | 400 |
| `S3b-k1-ctrlA`   | Q2 w13 k=101 (контроль) | 1 |
| `S3b-k400-ctrlA` | Q2 w13 k=101 | 400 |

Порядок ровно такой. Число запросов сверяется ассертом до лонча сервера (4).
Артефакт: `results/e94/S3b.json` — **отдельный файл**, `S4pp.json` не перезаписывается.

## Правило решения (записано ДО запуска; иного чтения не будет)

Пусть `N(x)` = `n_tl` строки `x`.

1. `N(k1-probe) == 1` и `N(k400-probe) > 1` → **`top_k` применяется** к набору кандидатов.
   Тогда в основном прогоне при T=0 и `top_k=1` цепь оставляла ровно вершину 318, а выдан
   ранг-2 (310): условие 2 гейта вычислимо, и нынешнее `probe_dependence=false` получает
   право называться **отрицательным результатом** (эмиссия не следует за усечением).
2. `N(k1-probe) == N(k400-probe) > 1` → **`top_k` не применяется**. Рука S3 объявляется
   недействительной; `gate2_met=false` читается «инструмент не годится», рука B не
   запускается по этой причине, а не «из-за отсутствия довода».
3. `N(k1-probe) == 0` → гипотеза о `p == 0.0` неверна (или `post_sampling_probs` сломан
   иначе) → рука **невалидна**, выводов нет, разбирательство по исходнику.
4. Любой `HTTP != 200` / смерть сервера → рука невалидна, артефакт пишется с `halt_reason`.
5. Расхождение пробы и контроля само по себе ни о чём не говорит: контроль нужен только
   чтобы показать, что `N(k1)==1` не артефакт одного адреса.

## Чего здесь заранее НЕ утверждается

* Эмиссия этих 4 запросов **не читается** как довод о механизме: при `temperature=1.0`
  ридаут «эмиссент = аргмакс» не определён. Строкам присваивается `kind="mech"`,
  вердикт только механический (`mech_ok` / `mech_flat` / `mech_void`).
* `gate2` в `S4pp.json` не правится — ни предикат, ни числа. S3b даёт оговорку к чтению.
* Если выяснится (2), рука B не запускается; это предрегистрированное следствие, а не
  решение, принятое по факту.

## Само-аудит до запуска (обязателен, по AGENTS.md)

1. `kind="mech"` обязан иметь предрегистрированное чтение, иначе `unknown` (ловит аудит).
2. Ассерты: 4 запроса; модель из `/props` совпадает с конфигом (гейт идентичности как в
   S4pp, при несовпадении — 0 запросов, `rc=2`); `N` считается по `completion_probabilities[0]`.
3. Репетиция на mock-сервере: минимум три мира — `N=(1,20)` → правило 1; `N=(20,20)` →
   правило 2; `HTTP 500` → правило 4. Ни один мир не должен тратить запросы к живому серверу.
4. `json.dump` без numpy/NaN; артефакт пишется при любом исходе, включая крах.
5. Запуск только `./run_one.sh e94_s3b ...`; перед лончем — `free -g` и `pgrep -x llama-server`.

```

## B. Факты из исходника форка, на которые опирается ТЗ (перепечатаны, читать C++ не надо)

B1. Порядок цепи сэмплирования (взят из эха живого запроса, поле `echo.samplers`):
```
[penalties, dry, top_n_sigma, top_k, typ_p, top_p, min_p, xtc, temperature]
```
`top_k` идёт ДО `temperature`, `temperature` — последний. Прочие параметры этого запроса:
`temperature=0.0, top_p=1.0, min_p=0.0, typical_p=1.0, xtc_probability=0.0,
speculative.types=none, backend_sampling=false, n_probs=20, post_sampling_probs=false`.

B2. `server-context.cpp:1790`: `need_pre_sample_logits = sampling.n_probs > 0 &&
!post_sampling_probs` — при наших основных запросах это `true`, и отчёт строится из логов
ДО сэмплера. Следствие: по отчёту действие `top_k` не видно в принципе (это и есть причина,
по которой родилась рука S3b).

B3. `server-context.cpp:1967-1992`, функция `populate_token_probs`, ветка `post_sampling`:
берётся `common_sampler_get_candidates(..., sorted=true)`, `max_probs = cur_p->size`, затем
цикл по `i < min(max_probs, n_probs)` с `if (cur_p->data[i].p == 0.0) break;`. При
`temperature=0` вероятности не вычисляются и остаются 0.0 -> отчёт пуст при любом `top_k`
(это наблюдалось: `n_tl=0` у `S2a/S2b`). Отсюда требование ТЗ мерить размер набора при T=1.0.

B4. Неизвестное, явно не закрытое: `penalties`, `dry` и `top_n_sigma` (последнее — ветка
форка) могут резать набор; их дефолты не проверялись.

## C. Две претензии, которые исполнитель предъявил своему ТЗ сам (проверь независимо)

C1 (про перенос T=1.0 -> T=0). Исполнитель считает: усечение работает над МНОЖЕСТВОМ
кандидатов, температура лишь перемасштаивает вероятности внутри оставшегося множества и не
возвращает выброшенных, поэтому размер набора после `top_k` от `temperature` не зависит и
измерение при T=1.0 переносится на T=0. Согласен/не согласен с учётом B1 и B4?

C2 (про потолок `n_probs=20`). Исполнитель считает пару `k=1` vs `k=400` недостаточной
(одинаковый `n_tl` возможен по причине, не связанной с `top_k` => ложное «не применяется») и
хочет заменить её лестницей `k = 1,2,4,400` с ожиданием `N(k)=k` для малых k и плато 20 при
k=400; и добавляет отдельную ветку «растёт, но не равно k => режется чем-то ещё, рука
невалидна». Верна ли замена и полны ли ветки? Что бы ты добавил?
