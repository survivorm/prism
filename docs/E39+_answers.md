## §4 «Sentinel 50.7% — главное открытие раунда». Не принято: это не открытие раунда

Ровно это измерено и записано в **E-34** (`docs/ref-exp.md`, вывод 4): «Sentinel: 50.7%
позиций (2077/4096, одинаково по слоям — raw sum не зависит от слоя). **Крупный побочный
факт: top-128 токенов несут < 50% массы на половине позиций; порог 0.5 для raw-sums,
видимо, слишком строг**». И в `paper.md` §4 (строка E-34): «sentinel: 50.7% позиций
(top-128 несут < 50% массы)». Число 2077 = `0.50708 × 4096` воспроизведено этим раундом
побитово. Раунд добавил к E-34 ноль новых фактов про долю и два новых — распределение и
разбиение по доменам:

| величина (одинакова на всех 5 слоях, `P128` не зависит от слоя) | значение |
|---|---|
| масса top-128 на полном softmax: среднее / медиана | 0.4896 / 0.4759 |
| p10 / p90 | **0.0050 / 0.9952** |
| доля `< 0.5` | 0.5071 |
| средняя масса по доменам: wiki / math / code / chat | 0.4430 / **0.5398** / 0.5193 / 0.4563 |
| доля sentinel по доменам | 55.1% / 46.2% / 47.1% / 54.5% |

Отсюда следует то, чего ни E-34, ни ревью не говорили: **порог 0.5 — это разрез по среднему
широкого распределения** (масса практически равномерно заполняет (0, 1)), поэтому «sentinel» как бинарная
маска неустойчив: любой порог из 0.2–0.8 перекраивает сопоставимую долю позиций. Правильная
рекомендация — не «вынести в раздел», а **перестать использовать sentinel как бинарную
маску** и отчитываться кривой массы (или включать массу ковариатой), что и просил E-34.

**Provenance (проверено, потому что от него зависит всё §4):** `P128_RAW` в дополненной
копии кэша — **точнейшая** перенормировка `P128` того же файла (коллинеарность
`‖P128_RAW − s·P128‖_∞ / max ≤ 2.63e-5`, `s = Σ P128_RAW`), JR/U128/pool_fp copies
совпадают побитово. Значит массы — настоящие массы полного softmax, и «sentinel —
артефакт дозаписанного поля» отпадает.

**Твоя уязвимость 2 («а вдруг это специфика корпуса/calibration») закрыта, и ответ — ни то
ни другое:** `U128` строится в профайлере exp27b как **топ-128 токенов по частоте по
корпусу** (позиции 0–127, одна база на все позиции и все домены — иначе нельзя сопоставлять
ESG-спектры). 50.7% — свойство **этой общей базы**, не «top-128 на C4» вообще: по доменам
величина ходит на 0.09 и её можно сдвинуть выбором базы. И направление твоё предсказание
переворачивает: code/math покрываются **лучше** (0.52/0.54), чем wiki/chat (0.44/0.46) —
в коде доля общих синтаксических токенов велика.

## §4.3 «g_uni = uniform-доля под усечённым p». Не принято — для headline-числа это неверно

Заголовочные `g_uni` = 0.215/0.188/0.142/0.126/0.140 считаются как `‖Jᵀ1‖²/(K‖J‖²_F)`:
**`p` в формулу не входит**, поэтому перенормировка `p` на них не влияет. Проверено
численно — перезапуск probes воспроизвёл якоря с точностью < 1% и отдельно посчитал
p-независимую формулу: 0.21496/0.18818/0.14249/0.12577/0.14034.

Твоё предсказание «на полном softmax g_uni была бы **меньше**» случайно верно для другой
величины, для `Σp²`: **0.2380 (raw) против 0.4686 (p, ренормированный), ×1.97**, на alive-срезе
0.4666/0.5708 (это значит и про «`Σp² = 0.557`» из раунда 4 — это тоже ренормированный `p`).
Для `g_uni` чувствительность к `p` появляется только в p-взвешенном варианте (не
используется в статье): −7% (L23) … −30% (L6).

Настояственная оговорка к `g_uni` — не про ренормировку, а про **размерность**: «uniform» —
это uniform **по 128 векторам базы `U128`**, а не по словарю. Это `1/K`-зависимость, и
именно она (K=128 против K=32) объясняет разброс с E-10a (0.111–0.620), а не ренормировка.

позиций, где ренормировка — ×2 и больше.
