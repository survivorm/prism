## 3. Главный факт: распределения согласны **везде**, включая точки расхождения

`rank_cpu` (позиция CPU-токена в 20-ке GPU) равен **1 во всех 2304 позициях** — я проверил, что это
не заглушка: реализация `rank = ids20.index(cpu_id)+1 else None`, цензуры (`rank=None`) ноль.
Пример `w4, k=70`: у GPU `top_logprobs[0] = id 318, p = 0.6206`, у CPU-референса `p_max = 0.6207`
для того же id 318 — согласование до 4-го знака. При этом **эмитирован** другой токен (id 310, p = 0.3278).

То есть `median |Δp_max|` измеряет согласованность распределений там, где выбранный токен = аргмакс
(99.4% позиций), а в 14 точках он измеряет **разницу выборов**, а не численную разницу логитов.
Формулировка «логиты SYCL f16 воспроизводят HF fp32 с медианой 3e-6» корректна для насыщенных
позиций; для слоя `p_ref < 0.9` честнее «медиана 1.1e-4 (относительно 2.5e-4), аргмакс-выбор
расходится в 6% позиций».

## 4. Аномалия: при `temperature = 0` эмитируется не аргмакс собственного отчёта

Установлено измерениями (не умозаключением):

- условные пробники (Q2): **14 из 2304** (0.61%) — эмитированный токен ≠ вершина `top_logprobs` этого же ответа;
- свободная генерация (Q1, те же 16 доков, 6144 позиций): **16 из 6144** (0.26%) — то же самое;
- гипотезы, которые **отбракованы проверкой**, а не рассуждением:
  (а) штраф повторов из метаданных GGUF — эхо `generation_settings` в сырых ответах:
  `repeat_penalty 1.0, repeat_last_n 0, presence/frequency 0.0, dry_multiplier 1.0, xtc 0.0, typical_p 1.0,
  mirostat 0, temperature 0.0, top_k 400, top_p 1.0, min_p 0.0, seed 8181`;
  (б) сэмплирование на бэкенде — `backend_sampling: false`;
  (в) список вероятностей относится к соседней позиции — тест на 6144 позициях: из 16 расхождений
  «вершина списка = следующий эмитированный токен» **0**, «= предыдущий» 1, «ни то ни другое» 15;
  (г) прореживание кандидатов — `top_k 400` и измеренный ранее состав кандидатов ≥ 400, вершины
  расхождений в топ-20 присутствуют (иначе `rank_cpu` был бы `None`).

**Количественная связка с Q1 (то, что делает находку полезной, а не курьёзом).** Если считать
частоту таких флипов `q` независимой по позициям, то вероятность совпадения всего 384-токенного
потока с CPU-референсом равна `(1−q)^384`:

| оценка | q | P(384 без флипа) | ожидание identical docs из 16 |
|---|---|---|---|
| по Q1 (16/6144) | 0.00260 | 0.367 | **5.88** |
| по Q2 (14/2304) | 0.00608 | 0.096 | 1.54 |
| **наблюдение Q1** | — | 0.3125 (5/16) | подразумеваемая q = 0.00302 |

Измеренная частота флипов в свободной генерации (0.0026) и частота, подразумеваемая долей
идентичных доков (0.0030), отличаются в 0.86 раза — то есть **разночтение движков из Q1 целиком
объясняется этим редким флапом**, без обращения к «iGPU иначе считает повторы». Для биномика 5/16 при
p = 0.37 вероятность ровно 5 равна 0.188 — данных достаточно, чтобы связать порядки, и недостаточно,
чтобы уточнять механизм.

4. Свежий HF fp32-прогон для перепроверки `REPLAY.gen_p1` сегодня не делался (замороженный трек

5. Свежие 2304 файла сырья лежат в `/tmp` (tmpfs, 65 МБ) — их надо либо упаковать в репозиторий,

**(а) Флипы концентрируются на низких отрывах, но не сводятся к ничьим.** По 6144 позициям Q1

|---|---|---|
| `< 0.02` | 44 | **0.0682** |

| `≥ 0.2` | 5937 | **0.0008** |

Медиана отрыва на флипах = 0.119 (минимум 0.0005, максимум 0.377), на всех позициях — 0.9994.
Обогащение низкими отрывами ≈ 85×, но **5 флипов случились при отрыве ≥ 0.2** — то есть
«это просто ничьи/порядок округления аргмакса» не объясняет явление целиком.

**(б) Внутри-доковая таблица 2×2 — сильнее, чем согласование частот (§4).** По 16 докум Q1:
документы с ≥1 флипом против документов с идентичным 384-токенным потоком:

| | поток идентичен CPU | поток разошёлся |
|---|---|---|
| флипов ≥ 1 | 0 | 11 |
| флипов = 0 | 5 | 0 |

Разделение полное, точный критерий Фишера (односторонний) **p = 2.29e-04** (= 1/C(16,5)).
Ограничение: n = 16 доков, и ассоциация не доказывает механизм — документ с большим числом
низкоотрывных позиций и чаще флапает, и раньше расходится; но именно это и есть утверждаемый
механизм (расхождение требует позиции, где выбор неустойчив).

**(в) Что от этого выигрывает отчёт.** Утверждение «разночтение движков в Q1 объясняется редким
флапом» теперь опирается не только на совпадение порядков `(1−q)^384` (5.88 против 5), но и на
полное разделение по документам при p = 2.3e-04. Оба аргумента — наблюдательные, механистическую
проверку («детерминирован ли флип при повторе того же запроса, живёт ли он в префиксном кэше»)
оставить на утро: 3 повторных запроса `w4 k=70` + один `n_predict:8`.

## 8. Что я бы утверждал сегодня (черновик выводов,ожидает внешнего ревью Q2)

1. При одинаковом условии (teacher forcing одним и тем же id-потоком) **отчёт сервера SYCL/f16
   согласуется с HF fp32 с медианой `|Δp_max| = 3.07e-06`** (насыщенные позиции: 2.1e-06), а
   расхождения выбора сосредоточены в слое `p_ref < 0.9` (6% позиций слоя).
2. В 0.61% условных позиций и 0.26% свободных позиций сервер эмитит токен, не совпадающий с
   вершиной собственного отчёта; явление **детерминировано** и не объясняется штрафами, кэшем,
   прореживанием кандидатов, `backend_sampling`, запросом вероятностей ни порядком запросов.
3. Число таких флипов внутри документа **полностью** разделяет документы с идентичным и с
   разошедшимся потоком (2×2, точный критерий Фишера p = 2.3e-04), а частотная модель
   `(1−q)^384` предсказывает 5.88 идентичных документов против 5 наблюдённых.

## 9. Q2c: гипотеза сдвига отвергнута — и это меняет формулировку вывода (04:25, `results/e94/Q2c.json`, rc=0, порт 8113)

На резковершинном промпте («The capital of France is» / «…France», id из `/tokenize`) вершина
собственного списка совпадает с эмитированным токеном **во всех 4 проверенных позициях**
(`verdict_shift`: flip 0/4; `req2_prefill`: 11751 == 11751; декод-шаги 369/369, 13/13). В точке флипа
(`w4 k=70`) вершина списка стабильно 318 — та же, что в Q2b-A. Значит список не «сдвинут на позицию
назад» и не «устарел».

Остаётся одна непротиворечивая картина, и её надо формулировать именно так (важно для отчёта):
1. **Отчёт сервера согласуется с независимым эталоном**: в точке флипа `top_logprobs[0] = id 318,
   p = 0.6206`, а HF fp32 даёт для того же id и той же позиции `p_max = 0.6207` — расхождение 1e-4,
   то есть распределение, которое сервер сам печатает, — это распределение основной головы, то же,
   что считает эталон.
2. **Аномалия — в выборочной стороне**: при `temperature 0` (и даже при `top_k: 1`) сервер детерминированно
   выдаёт id 310, который и эталон, и собственный отчёт сервера считают примерно в 1.9 раза менее
   вероятным. То есть «сбой выбора, а не отчёта» — так и надо писать, с указанием, что механизм не
   установлен; кандидаты «штрафы», «кэш», «порядок запросов», «запрос вероятностей», «сдвиг отчёта»
   отброшены измерениями (Q2b A-E, Q2c), кандидат «NextN/MTP-голова (`qwen35.nextn_predict_layers = 1`)
   участвует в сэмплировании» **не проверен и переживает Q2c**: на резковершинном промпте MTP-голова
   тоже предсказывает «Paris», так что Q2c её не различает. Тест остаётся прежний: сервер с
   отключённым спекулятивным/MTP-путём (подобрать по `llama-server --help | grep -i spec`) и повтор
   Q2b-A.
### 9.1 Поправки по внешнему ревью Q2 (`2_REVIEW_E94_Q2_exec_r1.md`, VERDICT: REVISE, принято)

- Пункт (1) выше переформулируется так: **«напечатанный отчёт согласуется с независимым эталоном
  (расхождение порядка 1e-4), а выбор не совпадает с аргмаксом этого же распределения»**. Слова
  «расходится и с отчётом, и с эталоном» снимаются: отчёт и выбор рождаются из одного forward-прохода,
  то есть расхождение с отчётом — это *определение* флипа, а не второй независимый свидетель;
  независимый свидетель ровно один (HF fp32). Статистического двойного счёта нет: 14/2304 считаются
  по вершине отчёта, согласие отчёта с эталоном — отдельное наблюдение.
- Таблица 2×2 (§6-б) **не является независимым подтверждением** частотной связки (§4): это те же 16
  документов, и оба её нулевых угла опираются на то же согласие распределений (флип ⇒ выбор ≠ вершина
  списка; вершина списка = CPU-аргмакс ⇒ поток разошёлся). Корректная формулировка: «полное разделение
  в пределах тех же 16 документов (односторонний Фишер p = 2.3e-04), совместимое с общей предпосылкой;
  не независимое подтверждение; механизм не установлен».

3. Следствие для Q1, которое обязательно надо сказать вслух: раз выбор в редких позициях ломается
   внутри движка, то `rep8`-метрики свободной генерации измерены на потоках, содержащих эти сбои.
   Для `w4` это выглядит как готовая причинная цепочка: флип на **позиции 6** (Q2b-D: флипы 6 и 19) —
   совпадает с точкой расхождения свободного потока `prefix_len = 6` (Q1) — и дальше поток вообще не
   входит в режим повторов: `rep8_llama = 0.0026` против `rep8_cpu = 0.9531`. Единственный «гигантский»
   Δ из всей выборки объясняется не тем, что iGPU иначе считает повторы, а одним ранним сбоем выбора.

### 11.2 Что это меняет в формулировках

Ранее я писал: «выбор не совпадает с аргмаксом распределения, механизм неизвестен». Теперь
формулировка сильнее и проверяемее: **отказ не является «ошибкой аргмакса вообще» — это строгое
смещение на одну (реже две) позиции вниз по собственному, согласованному с эталоном, порядку
вероятностей, и оно никогда не происходит на высокоуверенных позициях.** Это сужает перебор:
любое объяснение должно давать (а) совпадение чисел отчёта с HF fp32 до 1e-4, (б) детерминизм,
(в) ранг 2–3, (г) нулевую частоту при `gap ≥ 0.6`.

Отбракованное раньше (§10) остаётся отвергнутым; это наблюдение его не оживляет, а добавляет к
списку ещё одно требование к любой гипотезе.

### 11.3 Как я ОТБИРАЮ перебор числом (то, чего нельзя было сказать глазами)

- «Эмитент приходит из другого, чуть иного вектора логитов» — предсказывает разброс рангов: при
  возмущении аргмакс уходит на #2 редко, на #4+ тоже нередко. Наблюдение «46/46 ранг ≤ 3» с такой
  гипотезой плохо согласуется, НО мощность у этого довода умеренная: распределение ранга при малом
  возмущении и так концентрируется на #2, так что это аргумент «сдвиг мал и упорядочен», а не
  доказательство конкретного off-by-one. Честный статус: наблюдение, не вывод.
- «Сдвиг индекса в отчёте» (§9, отвергнут) не возвращается: числа вероятностей согласуются с HF.
- «Штраф за повторы» не спасает и теперь: у `w9/w11/w12` (повторы на ~97% позиций) флипов НОЛЬ,
  хотя именно там любой штраф за повтор срабатывал бы постоянно. Проверено тем же срезом
  `top1 in last 16`: доля флипов 0.0019 при «вершина уже была в последних 16» против 0.0031 при
  «не была» — то есть обогащения в сторону повторов нет вообще.

### 11.4 Проба, у которой ЕСТЬ мощность (не запущена; требует GPU-раунда и ТЗ)

### 11.6. 04:30, самостоятельно: конкурентное объяснение ОТВЕРГНУТО числом (мощность всё-таки есть)

Идея, данная внешнему ревьюеру как главная мишень (item B брифа `0_BRIEF_E94_Q2rank_r1.md`):
«сдвиг на позицию» не нужен, если сэмплер просто **не всегда берёт вершину, а выбирает из того же
распределения с малым нарушением t=0** (эпсилон/возмущённый выбор). Проверка на существующем сырье,
без новых запросов: для каждой позиции флипа нормируем `p_2..p_20` того же отчёта и получаем
предсказание `P(rank = k | rank ≠ 1) ∝ p_k`.

По 16 уникальным позициям флипа (Q1, r1; r2 совпадает):

| ранг | ожидалось по эпсилон-модели | наблюдено |
|---|---|---|
| 2 | 6.53 | **13** |
| 3 | 2.58 | 3 |
| 4…20 | 1.22 + 1.00 + 0.73 + … (всего ≈ 5.7 на 4..20) | **0** |

- среднее `P(rank = 2 | rank ≠ 1)` по этим позициям = **0.408** (разброс 0.152–0.929);

  и даже при самом снисходительном `p = 0.5` — `0.011`;
- правдоподобие наблюдённой последовательности рангов под моделью: `log P = −17.97`
  (`P ≈ 1.6e-8`);
- отсутствие рангов ≥ 4 при ожидаемых ≈ 5.7: `≈ exp(−5.7) = 0.003`.

которых тоже нет.

- 16 позиций взяты из 16 документов, внутри документа позиции не независимы; точный тест —
  кластерный по документам, он даст более широкий интервал, чем наивный биномиальный;
- это отсекает НЕ весь класс объяснений: «известный фильтр, снимающий вершину при некотором условии»

## 12. ГЛАВНОЕ: расхождение движков — это и есть флип (измерено по закоммиченному сырью, 0 вычислений)

`results/e94/Q2rank.json`, секция `divergence_alignment` (код: `experiments/exp94_q2rank.py`).

Возьмём `prefix_len` из `results/e94/Q1.json` (число совпавших первых токенов потока llama с
эталонным CPU-потоком; значит первое расхождение — на индексе `prefix_len`) и сопоставим с
позициями флипов того же дока:

| | наблюдение |
|---|---|
| документы с хотя бы одним флипом | w0,w1,w2,w3,w4,w5,w6,w7,w8,w13,w14 (11) |
| документы, где поток расходится с эталоном | **ровно те же 11** (`diverging_eq_flipdocs = true`) |
| первый флип == индекс расхождения | **11/11** (w3: 1=1, w5: 1=1, w4: 6=6, w8: 8=8, w14: 22=22, w13: 53=53, w6: 41=41, …) |
| документы без флипов | w9,w10,w11,w12,w15 — все с `prefix_len = 384`, то есть неразошедшиеся |
| бернуллиева модель с тем же hazard (0.002604/позиция) | воспроизводит выравнивание «первый флип ровно в точке расхождения» во всех 11 документах: **0 попаданий из 20 000** (p < 5e-05) |
| то же про «пять документов без флипов» | ожидание 5.9, наблюдено 5 — вот ЭТО объясняется частотой, без механизма |

Что это меняет. Более ранний вывод раунда («расхождение llama/CPU — это f16-против-fp32 на
низкоуверенных позициях», § вывод по Q1) **неверен по направленности**: напечатанное распределение
llama согласуется с fp32-эталоном (`Q2.json`: `rank_cpu = 1` во всех 2304 позициях), а расходится
выбранный токен — и ровно одно такое событие создаёт точку расхождения. То есть «движки разошлись»
и «сервер выбрал не вершину собственного отчёта» — одно и то же событие, а не два независимых.

Оговорки, обязательные при цитировании:
* единица — документ (16), рука — только Q1 (свободная генерация), флипы по r1;
* поздние флипы (`j > prefix_len`) проверить по `prefix_len` нельзя: потоки уже разные, они
  согласуются, но доказательства не добавляют;
* обратное импликативно только для первого флипа: «флип ⇒ расхождение» там верно по построению,
  «расхождение ⇒ флип» — наблюдаемый факт 11/11;
* причину самого флипа (§11, гипотеза двух буферов логитов) это НЕ объясняет — оно объясняет, ПОЧЕМУ
  раунд принимал флип за «численную разницу движков».


## 13. Опровержение «численного» варианта гипотезы двух буферов (офлайн-пересчёт по закоммиченному raw, 04:35)

Идея, которую проверял: сервер считает логиты дважды (инкрементальный декод в Q1 и полный
промпт-прогон в Q2), между двумя копиями возникает малое возмущение, и его хватает, чтобы argmax
уехал на #2/#3. Если так — то на ПОЗИЦИЯХ С ОДИНАКОВЫМ КОНТЕКСТОМ две руки должны различаться по
логпробам сильнее, чем шум повторяемого запроса, и этого должно хватать для флипов.

Контекст по построению одинаков при `j < prefix_len`: Q1 = prompt64 + поток llama[:j],
Q2 = `ids448[:k]`, `k = j + 64` = prompt64 + `REPLAY.gen_ids[:j]` (см. `experiments/exp94_q2.py:5-9`),
а `prefix_len` — ровно длина совпадения этих двух потоков. Срез по 6 документам, где лежит raw Q2
(w0, w2, w4, w9, w13, w14), только id-совпадающие кандидаты из `top_logprobs`:

| срез | n | токен совпал | флипов | медиана \|dlogprob\| | max |
|---|---|---|---|---|---|
| одинаковый контекст (`j < prefix_len`) | **502** | **502/502** | **0 в Q1, 0 в Q2** | 1.69e-03 | **4.79e-03** |
| разошедшийся контекст (`j >= prefix_len`) | 1522 | 159 | — | 4.55 | 18.4 |
| шум повтора того же запроса (r1 vs r2, артефакт) | 122313 | 6144/6144 | — | 5.75e-04 | 9.53e-03 |

Вывод (он отрицательный, поэтому и короткий): **численный вариант гипотезы не выдерживает**.
Различие двух путей оценки на одинаковом контексте — максимум 4.79e-03 логит, т.е. того же порядка,
что шум повтора запроса (9.53e-03), и на ДВА порядка меньше зазора, который нужно перекрыть, чтобы
аргмакс уехал: по флип-позициям медиана `log(p1/p2)` = 0.6479, минимум по документам > 0.4 (§11).
Там, где контексты правда разные, различия исчисляются единицами логит — это не численный шум, а
реальное расхождение потоков.

Побочный, более полезный факт: **до точки расхождения флипов нет вообще** — 0/502 позиций, и
эмиссия двух рук совпадает 502/502. То есть порядок такой: пока отчёт самосогласован, жадный выбор
воспроизводит fp32-поток; первое же нарушение самосогласованности стоит ровно там, где поток
отделяется от эталона (§12). Оценку сверху это даёт такую: частота флипов ДО расхождения < ~0.6%
(правило трёх, 0/502), внутри окна расхождения — 0.0026 на позицию.

Оговорки, без которых цифра обещает больше, чем мерит:
* руки различаются не только «путём оценки»: у Q2 `cache_prompt: true` и `n_predict: 1`, у Q1
  `cache_prompt: false` и декод на 384 шага. Значит измеренная величина — «движок в двух режимах
  вызова», а не «две копии одного вызова»; порядок величины от этого не меняется (оба режима дают
  ~1e-3), но приписывать число конкретному механизму нельзя;
* docs с `prefix_len = 384` (w9 и др.) дают окно без единого расхождения, поэтому 502 позиции —
  это в основном неразошедшиеся документы; для разошедшихся окно по 1–53 позиции;
