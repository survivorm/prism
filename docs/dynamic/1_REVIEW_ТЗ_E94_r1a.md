участвуют (T1-прогон и T2-прогон имеют РАЗНЫЕ флаги — см. замечание 1 — и

### 11. MINOR — план без бюджета; git_sha неоднозначен

исполнителю нужно число, чтобы заметить зависание. git_sha — чей? prism или

### 12. MINOR — определение p1/margin (ответ на §7-Q1)

Цитата (§2): «P1-определение: вероятность фактического следующего токена
генерации (как в exp81b: p1 по logits референсного движка); у llama-side
считаем по её же logits её же выбранный токен — сравнение на выровненных
позициях, это СОВПАДЕНИЕ МЕР, а не битовое».

Вывод по Q1: ТЗ НЕ путает — на общем префиксе по определению выравнивания
gen_llama[t] = gen_cpu[t], id в softmax определён однозначно (выбранный
движком на этой позиции токен = один и тот же id у обоих). Формулировка
«её же выбранный токен» допустима.

Требовать: (a) добавить явную строку: «на выровненной позиции id_llama[t] ≡
id_cpu[t], т.е. p1_llama[t] = P_llama(id_t), p1_cpu[t] = P_cpu(id_t) — один и
тот же id»; (b) margin := p_max − p_2 (зафиксировать, не «для маргина»);
(c) в stream.json — n_aligned на док; если n_aligned < 20 — corr(p1) не
вычислять (null + пометка): корреляция по 3–5 точкам — не мера.

### 13. MINOR — «greedy» в этом билде не чистый argmax

Цитата (§0): «тот же greedy-стрим 384 шага».

Почему (F15): sampler chain при temp=0 включает top-k(40)/top-p(0.95)/
min-p(0.05) (smoke_err.log e93): при p_max < 0.05 min-p выбрасывает всех
кандидатов и движок выбирает по fallback — это расхождение с чистым argmax
transformers даже без числовой дивергенции. Это часть измеряемого «движки
численно разные», не баг — но ТЗ должно знать, что сравнивает.

Требовать: одно предложение в §0: «greedy у llama = argmax после top-k/min-p
фильтрации (temp=0, chain как в smoke e93); расхождения на низкотоверных
позициях — ожидаемый сигнал, не править».

## Ответы на §7-вопросы (сверка с факт-чеком)

1. p1 llama vs CPU: не путает (см. 12). Чистое — проверено: на выровненной
   позиции id совпадает по определению.
2. Объём/память: механизма `--logits-all` нет (1); при гипотетическом — ~1 ГБ/
   док (vocab 248,044, не 151.9k), RSS парсера ~МБ, гейт <2 ГБ тривиален;
   взаимоблокировка reader/writer на stderr-pipe ТЗ не закрывает (8).
3. Идентичность prompt: prefix_len гейт сдвиг от расхождения НЕ отличает, и
   сдвиг не гипотетический — чат-шаблон применяется автоматически (F5, e93
   smoke: 15→25 токенов): без `-no-cnv` префикс = 0 по всем 16 докам (2).
   HF round-trip 64 промпт-токенов 16/16 идентичен (F11) — угроза на стороне
   промпта не в токенизаторе, а в шаблоне; нужен гейт «prompt eval / 64
   tokens» + `llama-tokenize` (2b, 2c).
4. rep8: off и формула в ТЗ не записаны (5); при сдвиге промпта на 1 токен
   n-gram-границы сдвигаются и rep8 несравним — лечится тем же 64-гейтом (2).
5. id-дамп: в этом билде ТЗ мечтает (`--dump-logits`/`-cd 0`/id в `--verbose`
   — всего нет, F1/F2/F13). Реальные без-патч пути: server /completion
   logprobs (id в ответе, F3 — проверено по исходникам форка) и текст→re-
   encode. Запасной путь честен ЧАСТИЧНО: prompt-side 16/16 идентичен (F11),
   gen-side требует runtime-чека; несовпавшие ре-энкоды — invalid, а не
   подгон (3).
6. Ресурсы: 16×384 при 6–9 t/s = 11–17 мин генерации; +24 загрузки ×21 с ≈ 8
   мин; T2-парсинг; всего ~0.5–2 ч — в один прогон влезает. «Один llama
   одновременно» не обеспечен технически: параллельный exp91 — реальный второй
   llama (7). Скрытого второго llama в самом плане ТЗ нет (бенча в основном
   прогоне нет) — ок.
7. Гейты: «SYCL-регистрация в stderr» — строки нет в stderr completion, файл
   stderr не определён — гейт неизмерим (6); «repro-rate r=2» — позиций и
   прогонов не задано (10); неизмеримые слова: «ошибки движка» (6c), «пик RSS»
   (метод измерения не задан, 8c).
8. Прочее: ТЗ невыполнимо одним исполнителем из-за: T2 без механизма (1),
   битый промпт по умолчанию (2), несуществующие флаги (3), неверный источник
   (4), неопределённая метрика (5), неизмеримые гейты (6), нет llama-гарда (7).
   Научный вывод под угрозой именно (2)+(3): без них Q1–Q3 — вакуум.
