## Замечания

**1. BLOCKER — T2 (Q3) не выполним как написано: `--logits-all` в этом билде не существует.**
Цитата: «T2 (4 logits-дока: w0,w5,w10,w15): тот же прогон с `--logits-all`, stdout парсится СТРИМИНГОМ (никогда не держать словарь 151k в памяти...)».
Поломка: факт 1 — флага нет в build/bin, на который ТЗ пинит билд через e93_sycl_smoke.sh (B=~/work/llama.cpp/build/bin). §5 ТЗ запрещает правки llama.cpp (read-only) → патч невозможен. У T1 есть фолбэк (текстовое сравнение) и «факт выбрать на спайке»; у T2 фолбэка НЕТ: спайк §3.1 обнаружит отсутствие флага, а дальше у исполнителя нет санкционированного пути — гейты харнесса «парсер logits отработал на 4/4» и «стрим-парсер пик RSS <2 ГБ», поля stream.json `p1 corr`/`n_logits_positions` и метод Q3 висят на несуществующем механизме. В NOTES e93 («L2 полка (logits-all стрим по 16 докам)») видно: план перенесён из e93 без проверки наличия флага в этом билде.
Требуемая правка: переопределить T2 на проверенный путь (факт 3): `llama-server` + `POST /completion {prompt, n_predict:384, temperature:0, logprobs:true, top_logprobs:1}` → p1_llama по позициям = exp(tokens[].logprob) (при greedy top-1 и есть выбранный токен) + `tokens[].id` — это же решает id-дамп T1 без lossy decode→re-encode; `POST /tokenize` — сверка промпта (зам. 3); для маргина `top_logprobs:2` (зам. 8). Один сервер-процесс на все 24 запроса вместо 24 CLI-запусков = одна iGPU-миграция вместо 24 (PLAN.md: IGC-flaky после kill/relaunch). Убрать оценку «~GB-масштаб» и гейт «пик RSS <2 ГБ» (ответ сервера ≈60–100 КБ/док). Расширить спайк §3.1: фактический формат ответа выбранного пути — в FORMAT.md.

**2. MAJOR — Q2: Spearman по n=16 с массовой насыщенностью, без null-модели.**
Цитата: «Q2: Spearman rho по 16 точкам против REPLAY.json, и медиана |Δrep8|».
Поломка: факт 5: 13 из 16 доков в полосе 0.839–0.974, 10–11 из 12 сегментов в доке ровно 1.0. Ранжирование 13 насыщенных доков — шум; без null наблюдаемое rho неотличимо от случайного. ТЗ требует «скопировать функции» из exp81b, но null у exp81b — не функция: он в блоке C (2000 перестановок, seed 8181), и ТЗ его не требует. Плюс: (a) spear() из exp81b = argsort-of-argsort без коррекции тайов — при такой плотности тайов результат определяется привязкой; (b) REPLAY.json хранит не «rep8», а segments[8] (12 точек) — редукция к одной точке ТЗ не закреплена.
Требуемая правка: (a) закрепить rep8 (одна точка) = mean(segments[8]) (формула C из exp81b: `float(np.mean(res["docs"][k]["segments"][8]))`); (b) пермутацонный null: 2000, фикс. seed, перестановка одной стороны, rho + перцентили null (как в exp81b); (c) ranks с учётом тайов (или отчёт числа различных рангов); (d) медиана |Δrep8| — основная метрика (робустнее к тайам), rho — вспомогательная.

**3. MAJOR — идентичность промпта между движками не верифицируется: «главная угроза» объявлена, противоядия нет.**
Цитата: T1 «llama-completion с prompt-текстом (декод prompt-id через HF-токенизатор skip_special_tokens=True; флага chat-шаблона нет...)»; §7: «(3) идентичность prompt между движками (BOS/special/whitespace — главная угроза префикс-гейту)».
Поломка: llama ре-токенизирует текст своим BPE; шага проверки «промпт-токены llama == 64 id из HF» (exp81b: `tk(texts[i], add_special_tokens=False)[:64]`) в методе нет. При расхождении prefix_len = 0 независимо от согласия движков → Q1 конфаунд: меряет дрейф токенизации, а не робастность движка. Край не теоретический: реальные доки несут w8 (могиль «破..», «Náo Loạn») и w12 (zero-width space U+200B в «​Lastly») — roundtrip decode→re-encode на таком тексте не формальность. (Косвенно: skip_special_tokens=True здесь no-op — промпты собраны с add_special_tokens=False, special в них нет.)
Требуемая правка: обязательный pre-gate до метрик: сверить токенизацию промпта llama c HF-id по каждому доку (server: POST /tokenize на точный prompt-текст; CLI: --verbose-prompt); в stream.json — `prompt_match` на документ; при mismatch — Q1 по доку объявить «не интерпретируется» (prefix_len — не метрика движка), это прописать в ТЗ.

**4. MAJOR — гейт детерминизма вырожден: «Если <1.0» всегда истинно.**
Цитата: «3. Детерминизм: повтор одного микропрогона, доля несовпавших id. Если <1.0 — зафиксировать в ТЗ как факт, метрики не менять».
Поломка: доля несовпавших id < 1.0 (= <100%) выполняется тривиально (проходит даже почти недетерминированный движок); при чтении как «<1.0%» правила на случай ≥1% нет. Не отвечено, что происходит, если greedy реально не воспроизводится (SYCL-атомики → флипы argmax на near-tie): 16 доков T1 — по одному прогону, префикс — однократная выборка; выравнивающий набор Q3 тоже однократный; repro-rate покрывает только 4 T2-дока (r=2). Микропрогон ≤64 токена — крошечная выборка для заявления о недетерминизме.
Требуемая правка: осмысленный порог (напр., несовпадение >5% в микропрогоне → Q1/Q3 помечаются «не интерпретируются», в заголовок — repro-rate); решение: r=2 для T1 или явное декларирование single-run; прописать судьбу Q1-префиксов при невоспроизводимости.

**5. MAJOR — Q3: нет минимума позиций на «выровненной части».**
Цитата: «Позиции, где id-стремы разошлись, в Q3 не учитываются (но их число фиксируется)».
Поломка: сколько позиций останется в общем префиксе — неизвестно a priori (типично десятки); p1-трек близок к насыщенности (факт 5: p1_med 0.9991–0.9999 во всех 16 доках; exp81b: 91% p1 > 0.9) → корреляция по 10–50 почти-константным точкам маломощна; без гейта «ответом» может быть чистый шум.
Требуемая правка: явный минимум (напр., ≥32 выровненных позиций — прецедент exp81b: T>20 для p1-corr), иначе Q3 = «не измерено (prefix=X)»; дополнительно отчитываться std(p1_llama) на выровненном множестве (ниже eps → не интерпретируется даже при n≥32).

**6. MAJOR — артефакт не пересчитываемый: stream.json хранит только сводные числа.**
Цитата: «stream.json: шапка {git_sha, gguf sha256[:12], e64_id_list sha256, флаги, build}; на документ: prefix_len, rep8_llama, rep8_cpu, p1 corr (T2-доки), n_logits_positions, repro-rate (для T2-доков r=2)».
Поломка: сырые gen llama (id/текст) и p1_llama по позициям не сохраняются (§2: «файл не сохранять»). Тогда rep8_llama (по prompt+gen), prefix_len и p1 corr из артефакта не пересчитать без ре-руна ~40 мин — собственный §6 ТЗ (само-ревью артефакта, ВНЕШНИЙ ревью-луп кода+артефакта) не может проверить ни одного числа; «аудит результата» (AGENTS.md) превращается в повторный прогон.
Требуемая правка: сохранять на документ id-стрим gen llama (64+384 int, ≈2 КБ; если id-дамп невозможен — gen-текст + пометка) и p1_llama по позициям для T2-доков (384 float × 4). Итого <1 МБ.

**7. MINOR — источник 16 доков подписан неверно: в results/e64/tpu prompt-id нет.**

**8. MINOR — метрика «маргин» тождественно нулевая на выровненных позициях.**
Цитата: «на позицию — softmax-вероятность id, который взял CPU-референс на этой позиции, и максимум — для маргина».
Поломка: на выровненных позициях (общий префикс) argmax llama == общий id ⇒ p_max ≡ p_chosen ⇒ маргин ≡ 0 тождественно (разошедшиеся позиции из Q3 исключены по построению).
Требуемая правка: если нужен near-flip guard — маргин = p_top2 − p_top1 (server: top_logprobs=2); иначе убрать «маргин» из метода.
