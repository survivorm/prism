## 1. MAJOR-Self-1 — свип S3 не показал, что `top_k` вообще на что-то влияет

Оправдание гейта («зависимости от ширины нет») требует, чтобы ширина меняла что-то
наблюдаемое. В артефакте этого нет:

```
S3-k1-probe   : n_tl=20 ids_head=[318,310,326,369,783,4981] top1_lp=-0.47730168
S3-k400-probe : n_tl=20 ids_head=[318,310,326,369,783,4981] top1_lp=-0.47708988
```

`n_tl` одинаков при k=1 и k=400, порядок кандидатов идентичен, logprob расходится на
1e-3 (шум GPU). То же на контроле. При этом в запросе всегда стоит
`n_probs: 20, top_logprobs: 20` (строки 123–124), поэтому **отчёт при k=1 не сузился
ни до одного кандидата**. Следствие: наблюдение «эмиссент не меняется с k»
неотличаемо от наблюдения «`top_k` этим форком не применяется». Положительного
контроля на то, что `top_k` кусается, в руке S3 нет — ровно так же, как для бана
такой контроль есть (4 строки `ctrl_ok`), а для ширины его нет.

Значит `gate2_met=false` надо читать **«условие не вычислено»**, а не «независимость
показана». Рука B по предрегистру не запущена — это правильное и заранее объявленное
действие, трогать его задним числом нельзя; но *прочитать* это поле как
«эмиссия не зависит от top_k» нельзя.

Полуконтроль, который всё-таки есть (косвенно, из S2): при `post_sampling_probs=true`
отчёт схлопывается в `n_tl=0` (см. Self-3), то есть путь отчёта **реагирует** на
параметры запроса — значит «20 кандидатов при k=1» не всемогущая константа сервера.
Это сужает, но не закрывает логическую дыру: реагирование другого флага не есть
контроль `top_k`.

Что закрывает (2 запроса, отдельный артефакт, не перезапись S4pp.json): тот же адрес,
`top_k=1` vs `top_k=400` при `post_sampling_probs=true`; если при k=1 `n_tl` схлопнется
в 1 — `top_k` применяется, и тогда нынешнее `probe_dependence=false` становится
настоящим (отрицательным) результатом; если останется пустым/неизменным — `top_k`
на этом форке no-op, и вся рука S3 объявляется недействительной (что само по себе
факт о форке, а не о моделях).

## 2. MINOR-Self-2 — чтение пары S2 утверждает лишнее

эмиссента, ни отчёт»`. Отчёта в паре **нет с обеих сторон**: `top1=null`, `n_tl=0`,

для заявленного в предрегистре статуса «пара не различающая», и этого же достаточно,
чтобы сказать «про отчёт ничего не известно».

## 8. Исходник форка отвечает на два вопроса дешевле, чем GPU (03:15, `/home/survivor/work/llama.cpp/tools/server/`)

1. **Отчёт по построения не может показать действие `top_k`.** `server-context.cpp:1790`:
   `need_pre_sample_logits = n_probs > 0 && !post_sampling_probs`. У всех основных строк
   `post_sampling_probs=false`, `n_probs=20` → отчёт собирается из логов ДО сэмплера
   (`get_token_probabilities`), поэтому `n_tl=20` при `top_k=1` — не находка форка, а
   штатная семантика апстрима. Следствие для Self-1: **путь отчёта в принципе непригоден
   как положительный контроль ширины**; контроль возможен только по пост-сэмплированному
   набору кандидатов либо по самой эмиссии.
2. **Почему у S2a/S2b пустой отчёт.** `populate_token_probs`, ветка `post_sampling`
   (`server-context.cpp:1967-1992`): берётся `common_sampler_get_candidates`, и цикл
   обрывается на первом `p == 0.0`. При `temperature=0` вероятности не вычисляются
   (остаются 0.0) → `n_probs` схлопывается в 0. То есть `post_sampling_probs=true` при
   T=0 даёт пустой отчёт **для любого `top_k`** — предлагавшийся было контроль
   (`top_k=1` vs `400` при `post_sampling_probs=true`) мёртв до запуска. Это ответ на
   собственный вопрос Q3(b), найденный по исходнику, а не прогоном.
3. **Схема сэмплирования и отсутствие драфта** (эхо артефакта, `S4pp-2`):
   `samplers=[penalties,dry,top_n_sigma,top_k,typ_p,top_p,min_p,xtc,temperature]`,
   `speculative.types=none`, `backend_sampling=false`. `top_k` в цепи есть, `temperature`
   последний; плюс `server-context.cpp:1795`: `use_backend_sampling &= !need_pre_sample_logits`,
   то есть при запрошенном `n_probs` цепь считается не на бэкенде. Значит при T=0 и
   `top_k=1` цепь оставила бы РОВНО одну кандидату-вершину, и жадный выбор обязан был
   выдать 318; выдано 310. Это либо «`top_k` не кусается», либо «эмиссия не из этой цепи» —
   и различить эти два можно только контролем по пост-сэмплированному набору при T>0.
   Гипотеза «флип = драфт-модель» исходно закрыта: `speculative.types=none`.
