## Findings (новые)

- **F9 — фикс (MINOR)** — §2.3/§2.7: чанкинг и sweep-time-гейт зафиксированы на n=128, но операция специфицирована n ≤ 256. Стоимость sweep на матрицу ∝ n(n−1)/2: (256·255/2)/(128·127/2) ≈ ×4.02 ⇒ 4с/launch при n=256 → ~16с, 5×-запас к hang-check ~20с схлопывается до ~1.25× (твёрдый тест — один запуск, медиана 3-х может быть превышена). Потребителей с n=256 нет (реальные jcache — 128). Рекомендация: второй гейт AT0_3-тунинга на n=256, либо явная запись «гарантия watchdog для n ≤ 128; n=256 — worst ~16с», либо ограничение watchdog-заявления по n.
- **F10 — фикс (NIT)** — §2.3: bound на launch (4с) ясен, суммарное время вызова eigjac не ограничено ТЗ: max_sweeps × ⌈batch/C⌉ × 4с (worst 64×16×4 = 4096с; AT2c: 16 launch/sweep × 12 sweep ≤ 768с). Hang-check на compute-КОМАНДУ, watchdog-проблемы нет (согласуется с формулировкой v5.2-ревью) — но добавить одну строку в §2.3 для планирования стоимости вызова.
- **F11 — NIT** — §2.3: offdiag_rel считается на устройстве в f32 (редукция по ~n²/2 членов: bound ~2e-3 rel, типично ~sqrt(n²/2)·eps ≈ 1.5e-5; «1%» из чекалиста НЕ подтверждается — f32-мантисса ≈ 1.19e-7). Влияние на стоп-критерий offdiag_rel < 1e-5: максимум лишний sweep; порог теста 1e-4 — 100× запас к tol. Рекомендация: строка «offdiag_rel — f32-расчёт на устройстве, честный отчёт = f32-значение в f64».
- **F12 — фикс (NIT)** — fudge-guard XLA (§2.3) не имеет designed-тест-сценария в §2.7 (требование AGENTS.md для guard'ов; у gemm он есть, m-16). Рекомендация: случай «диагональная матрица + пара с |A_ij| ≤ 0.1·eps_f32·min(|A_ii|,|A_jj|)» — ожидаемо: ротация не применяется, без NaN, offdiag < tol со 2-го sweep.
- **F13 — NIT** — §2.7: «curve не растет (f64)» — неясная формулировка (видимо: буфер не расширяется, fill in place, dtype f64). Уточнить.

## Закрытие F1–F8

- **F1 (MAJOR, batch-чанкинг): ДОСТАТОЧНО.** Механизм ясен: 1 sweep = ⌈batch/C⌉ запусков, каждый ≤ C матриц (work-item — своя матрица). C: тунинг AT0_3, чанки {1,16,64,256,1024,4096}, t_sweep = медиана 3 запусков, C = наибольшее с t_sweep(C) ≤ 4с (5× к ~20с), нач. 1024; твёрдый pytest: 1 launch (batch=C, n=128) ≤ 4с И C ≥ 256, иначе громкий fail («GPU медленнее расчёта — не тихое замедление»). Сценарий «C=1024 не проходит» покрыт: C снижается по тунингу (256/64/16); не проходит даже 256 → fail-loud. Медиана 3 + отдельный single-run pytest-гейт — достаточно для ТЗ. Резервации: n=256 (F9), суммарное время (F10).
- **F2: дословно** — §2.3: «t = (A_jj−A_ii)/(2·A_ij)», конфликт буквы d устранён.
- **F3: дословно + тест** — §2.5: «curve[s−1] = offdiag_rel после sweep s (s=1..k), curve[k..size) = offdiag[0] (явный fill)»; §2.7 — явные assert (curve[k−1] == offdiag[0], curve[k..64) == offdiag[0], curve[0] > 0).
- **F4: дословно, лучше просили** — §2.3: «результат ЗАПИСЫВАЕТСЯ ОБРАТНО в vecs f32»; 5e-15/8.4e-5 явно атрибутированы f64-расчёту; новый замер после f32-cast ‖VᵀV−I‖ ≈ 3e-7 ≤ 1e-4.
- **F5: дословно** — eps_f32 = 1.1920929e-7 в формуле fudge-guard.
- **F6: дословно** — §0 стр. 83: полная сигнатура `ps.eigjac(A, max_sweeps=12, tol=1e-5, curve=None) → (vals f64, vecs f32, …)`.
- **F7: дословно** — C-ABI стр. 273–274: int64_t batch/n/max_sweeps/curve_len, double tol/vals/offdiag/offdiag_curve, float* vecs.
- **F8:** заявка «m-28, n-31, n-33 закрыты v5.2 (проверено полным файлом ревью)» — принимается; m-28/n-33 видны в §2.7 (max_sweeps=64 + offdiag < 1e-4; вывод 1e-2 для кластерных) — самостоятельная переверка в бюджете не делалась.
