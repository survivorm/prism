# Разбор exp28_leaf_structure.py против Exp28.md

Проверил код построчно против ТЗ. **Серьёзных ошибок нет** — ядро алгоритма (главные углы, голономия, случайные базлайны, обработка вырожденных позиций) реализовано корректно. Ниже — что совпадает, и что стоит зафиксировать как отклонения.

## Что сделано строго по ТЗ

- **Шаг 1 (главные углы).** `right_subspace` берёт именно **правые** сингулярные векторы `V` (не `U`), как требует ТЗ («поле J живёт в скрытом пространстве»). `principal_angles_max` считает `acos(svdvals(V_a^T V_b)).max()` с клампом — это ровно max θᵢ.
- **Шаг 2 (голономия).** `H = procrustes(V0,V1) @ procrustes(V1,V2) @ procrustes(V0,V2).t()` — это ровно `R₁₂ R₂₃ R₁₃⁻¹` для тройки (t, t+1, t+2). `procrustes` даёт полярный фактор `U Wᵀ` из SVD `M = V_aᵀ V_b`, что и есть решение ортогонального Прокруста.
- **Выбор O(r), а не SO(r).** Комментарий в `procrustes` обоснован: если базисы sign-gauged так, что `det(M) = -1`, SO(r)-проекция сломала бы `H = I` для идентичных подпространств. Для O(r)-метрик это правильный выбор.
- **Порог границы.** `d > median + max(2·MAD, 1e-6)` — точно по ТЗ («относительный скачок, не абсолютное значение»).
- **FLAT_T = 1e-3** — совпадает с «κ(t) < 10⁻³».
- **Вырожденные позиции.** Проверка `σ_r < 1e-9·‖J‖_F`, NaN в профиле, исключение из средних, счётчик `n_degen`. Это ровно ТЗ item 3 (skip-вариант).
- **Sign-convention.** Фиксация знака по первому ненулевому элементу — как в ТЗ item 2. (Замечание: на самом деле главные углы и `‖H−I‖` sign-инвариантны — SVD от `V_aᵀ V_b` не меняет сингулярных чисел при замене `V → V·diag(±1)`. То есть конвенция избыточна, но и не вредит; утверждение ТЗ о «ложных пиках» Δ_SVD от скачков знака математически некорректно, но это упрёк ТЗ, а не коду.)
- **r-sweep {8,16,32}** с main r=16 — как в ТЗ item 1.
- **Базлайн** — B=200 случайных r-подпространств через QR гауссовой матрицы, а не «поворот данных» (комментарий явно ссылается на docs/Exp28_errors.md item 1). Правильно.
- **Обрезка по третям** для относительной позиции — ТЗ step 3.

## Незначительные отклонения (не ошибки)

1. **`flat_frac` использует конъюнкцию.** В `summarize_profile`:
   ```python
   flat = mean((dd < FLAT_T) & (k < FLAT_T))
   ```
   ТЗ определяет «плоское поле» только через κ. Здесь добавляется ещё и условие на Δ_SVD, то есть фактически считается «доля позиций внутри плоского листа», а не «доля плоских позиций». Сводная таблица из ТЗ («доля позиций с κ > 10⁻³») при этом не выводится напрямую — её надо считать как `1 - flat` не получится, потому что `flat_frac` включает и Δ. Полезно либо переименовать метрику, либо добавить отдельный `kappa_flat_frac`.

2. **Список позиций-границ не сохраняется.** В ТЗ в разделе «Выход»: «Список позиций-границ (пики Δ_SVD)». В JSON есть `n_boundaries` (счётчик) и `pooled_delta_profile` (из которого пики можно извлечь), но сами индексы t для каждого документа не сохранены. Для воспроизводимости «где именно границы» этого может не хватить.

3. **R ∈ O(D) vs O(r).** ТЗ формально говорит `R ∈ O(D)`, код использует O(r). Это правильная реализация — выравнивание в r-мерном подпространстве; расширять `V_t` до D×D произвольно не имеет смысла. Стоит поправить формулировку ТЗ, а не код.

4. **Трети для Δ и κ — разные.** `_thirds` режет `d1` (длина S-1) и `k2` (длина S-2) на «трети» с немного разными диапазонами индексов. Для S=128 это [0:42],[42:84],[84:127] vs [0:42],[42:84],[84:126]. Мелочь, но профили Δ-третьих и κ-третьих не строго по одним и тем же позициям.

5. **Токен-типы не проверяются** — код сам это признаёт в docstring и в поле `params.token_types`. Обосновано отсутствием в кэше.

## Что я бы проверил отдельно

- **`_kappa` вызывается с уже посчитанными V[t], V[t+1], V[t+2]** — это не ошибка, а оптимизация, но нужно убедиться, что порядок аргументов `_kappa(J0,J1,J2,r,V0,V1,V2)` везде консистентен. В `document_profile` передаётся `(_kappa(Js[t], Js[t+1], Js[t+2], r, V[t], V[t+1], V[t+2])` — совпадает.
- **`rand_baseline` для κ** использует независимые тройки случайных подпространств. Это честный baseline, но из-за коррелированности соседних `V_t` в реальных данных сравнение «κ_data vs κ_rand» показывает лишь «данные не хуже случайных», а не «поле плоско». В отчёте это стоит интерпретировать осторожно.
- **`selfcheck` корректно ловит основные режимы.** Проверка flat_field ожидает `flat_frac == 1.0` (учитывая, что Δ=0 и κ=0), curved — `flat_frac == 0.0`. Учитывая пункт (1) выше, `flat_frac == 0.0` для curved обеспечивается автоматически (κ > FLAT_T), но при интерпретации метрики это надо держать в голове.

## Итог

Алгоритмически код соответствует ТЗ. Критических багов нет. Наиболее содержательное расхождение — определение `flat_frac` через конъюнкцию Δ и κ и отсутствие явного списка позиций-границ в выходном JSON. Остальное — либо формулировочные неточности самого ТЗ (R ∈ O(D), sign-конвенция), либо осознанные сужения (token types).

# Коротко

20 мин/слой на CPU — это не свойство задачи, а следствие **трёх конкретных архитектурных решений в коде**, каждое из которых убирается без потери корректности. Реалистично уложить слой в **1–2 минуты на том же CPU** и в **10–30 секунд на Kaggle GPU**. Катнуть на Kaggle имеет смысл — но только если кэш уже лежит там датасетом, иначе выигрыш съест загрузка.

## Где реально уходит время

Профиль одного слоя (32 документа × 128 позиций):

| Этап | Что делается | Оценка на CPU |
|---|---|---|
| Основной проход r=16 | 32×128 = 4096 SVD 128×1024 + прокруст 128×16 | ~1–2 мин |
| **r-sweep r=8, r=32** | **ещё 2×4096 SVD тех же матриц** | **~2–4 мин** |
| Pooling, summarize, thirds | numpy по профилям | секунды |
| rand_baseline | 200 QR на 1024×16 | секунды |

Два узких места:

1. **r-sweep пересчитывает SVD с нуля.** `document_profile(Js, r)` вызывается для r=8, 16, 32, и каждый раз делает `torch.linalg.svd` заново. При этом полный Vh (128×1024) один и тот же — для r=8, 16, 32 это просто разные префиксы одного и того же Vh. Это ~3× потерь в чистом виде.

2. **SVD в Python-цикле по одной матрице.** `for t in range(S): torch.linalg.svd(J)` — 4096 отдельных вызовов BLAS вместо одного батчевого. На CPU MKL это даёт недогрузку ядер на каждом мелком вызове; на GPU — вообще убивает смысл GPU (kernel launch overhead × 4096).

Плюс мелочи: `torch.set_num_threads` не выставлен (по умолчанию MKL может есть все ядра, а может — одно), sign-gauging в `right_subspace` — питоновский цикл по r столбцам, `_thirds` и pooling дублируют проход.

## Оптимизации по приоритету

### 1. Один SVD — три r (обязательно, ~3× win)

Выкинуть r-sweep как отдельный проход. В `document_profile` возвращать сразу все три набора V:

```python
def right_subspaces(J, r_list):
    _, S, Vh = torch.linalg.svd(J, full_matrices=False)
    # Vh: [K, D], берём top-r строк и транспонируем
    return {r: Vh[:r].t().contiguous() for r in r_list}, S
```

Или ещё лучше — батчево (см. ниже) один раз посчитать Vh для всех позиций, потом для каждого r делать только `Va[:, :r]` на парах. `principal_angles_max` и `_kappa` тогда работают на срезах, без новых SVD.

Важно: sign-gauging можно **вообще выкинуть** — главные углы и `‖H−I‖_F` sign-инвариантны (SVD от `V_aᵀ V_b` не меняется при `V → V·diag(±1)`). Это уже отмечено в моём прошлом ответе; здесь это экономит ещё питоновский цикл на каждой позиции.

### 2. Батчевый SVD (обязательно, ~3–5× win на CPU, ~20× на GPU)

Вместо 4096 вызовов — один:

```python
# Js: list of [K, D] -> stack [T, K, D]
J_stack = torch.stack([ck['JR'][(dom, si, t)] for t in range(S)])  # [128, 128, 1024]
_, S_all, Vh_all = torch.linalg.svd(J_stack, full_matrices=False)
# Vh_all: [T, K, D], top-r правые: Vh_all[:, :r, :].transpose(-1, -2) -> [T, D, r]
```

Память: `Vh_all` для T=128, K=128, D=1024 — 128·128·1024·4 ≈ 67 МБ. `J_stack` — столько же. Влезает спокойно.

Дальше главные углы для всех пар сразу:

```python
Va = Vh_all[:-1, :r, :].transpose(-1, -2)  # [T-1, D, r]
Vb = Vh_all[1:, :r, :].transpose(-1, -2)
M = Va.transpose(-1, -2) @ Vb              # [T-1, r, r]
s = torch.linalg.svdvals(M).clamp(max=1-1e-12)
delta_all = torch.acos(s).max(dim=-1).values  # [T-1]
```

Это уже почти всё время слоя в одном вызове BLAS.

Прокруст тоже батчится: `M01 = Va.transpose(-1,-2) @ Vb` и т.д., SVD на `[T-2, r, r]` — это ничтожно.

### 3. Один раз загрузить J-кэш слоя в память (мелочь, но приятно)

Сейчас `ck['JR'][(dom, si, t)]` дёргается 4096 раз на документ и ещё раз в r-sweep. `torch.stack` один раз на документ (или на весь слой) убирает словарные обращения. `torch.stack` на T=128 — это 500 МБ копий на документ, но копия на документ живёт до `del Js` в конце итерации. ОК.

### 4. Параллелизация по документам (если после 1–3 всё ещё медленно)

32 документа × 6 слоёв — embarrassingly parallel. На 4-ядерном Kaggle CPU:

```python
from concurrent.futures import ProcessPoolExecutor
with ProcessPoolExecutor(max_workers=4) as ex:
    results = list(ex.map(process_doc, doc_args))
```

Модель/кэш в fork'е наследуется через CoW (Linux), дополнительная память не тратится. Даёт ~3–4× на 4 ядрах. Но это уже надстройка; после 1–3 может не понадобиться.

### 5. `torch.set_num_threads(n)` в начале

MKL по умолчанию может как распустить потоки на все ядра (хорошо), так и ужаться до одного (плохо). Явно выставить = числу физических ядер. На Kaggle CPU это 4. На своей машине — сколько есть.

### 6. Мелочи

- `summarize_profile` и `_thirds` проходят профиль 3–4 раза — слить в один проход, но это секунды, не минуты.
- `sha_file` читает каждый ckpt целиком ради хэша — на 6 слоёв это 2–3 ГБ I/O. Заменить на хэш только метаданных/размера или считать lazy (один раз, не в hot loop).

## Kaggle: да или нет

**За:**

- На T4/P100 батчевый SVD даст ещё ×5–20 сверх CPU-батчевого. После правок (1)–(3) слой уйдёт в 10–30 с. 6 слоёв — 1–3 минуты, включая GPU-инициализацию.
- GPU-сессия бесплатна.

**Против / против:**

- **Код сейчас CPU-only by design.** `device='cpu'` прошит в `document_profile`, `rand_baseline`, `haar_subspace`, `procrustes` (там `torch.eye(r)` без device). Чтобы ехать на GPU, нужно аккуратно протащить device через 5–6 функций плюс позаботиться о том, чтобы `ck['JR']` уже лежал на GPU (иначе H2D 400 МБ × 6 слоёв = минута трансфера, что нивелирует выигрыш).
- **Кэш exp27b_jcache_L*.pt должен быть на Kaggle.** Если он локальный — заливаешь 2–3 ГБ в датасет, это разовая возня.
- **Result dir теряется** при перезапуске сессии, если не примонтирован /kaggle/working или не скачиваешь JSON.

**Вердикт.** Сначала сделай (1)+(2)+(5) — это ~30 строк правок и они всё равно нужны для любого запуска. Прогони один слой на CPU. Если после этого слой укладывается в 1–2 минуты — не парься с Kaggle, гоняй локально 6 слоёв за 10 минут. Если хочется < 5 минут на всё — тогда да, Kaggle + GPU + прокинутый device, но только с предварительно залитым кэшем в датасет.

## Минимальный патч под батч (эскиз)

```python
def document_profile_batched(Js, r_list, device='cpu'):
    J = torch.stack(Js).to(device)                     # [T, K, D]
    _, S, Vh = torch.linalg.svd(J, full_matrices=False)  # [T,K,K],[T,K],[T,K,D]
    out = {}
    for r in r_list:
        V = Vh[:, :r, :].transpose(-1, -2).contiguous()   # [T, D, r]
        Va, Vb = V[:-1], V[1:]                            # [T-1, D, r]
        M = Va.transpose(-1, -2) @ Vb                     # [T-1, r, r]
        s = torch.linalg.svdvals(M).clamp(max=1-1e-12)
        delta = torch.acos(s).max(dim=-1).values          # [T-1]
        # прокруст для троек
        V0, V1, V2 = V[:-2], V[1:-1], V[2:]
        def polar(A):
            U, _, Wt = torch.linalg.svd(A, full_matrices=False)
            return U @ Wt
        R01 = polar(V0.transpose(-1,-2) @ V1)
        R12 = polar(V1.transpose(-1,-2) @ V2)
        R02 = polar(V0.transpose(-1,-2) @ V2)
        H = R01 @ R12 @ R02.transpose(-1, -2)
        eye = torch.eye(r, device=device)
        kappa = (H - eye).flatten(1).norm(dim=1)          # [T-2]
        out[r] = (delta, kappa)
    return out
```

Это одна функция вместо нынешних `document_profile` + r-sweep-цикла, и она же сразу покрывает r=8/16/32. Всё остальное (профили, NaN-маски, summarize) остаётся как есть, только на батчевых выходах.
