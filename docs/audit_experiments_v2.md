## 3. Новые находки (все — тихие; ни одна не падает)

### 3.1 E-40.4 — объект `r_cross` изменён относительно пререгистрированной ставки «≈60» (не зафиксирован как отклонение)

*Ставка:* `docs/e40_todo.md:409` и `docs/models/2-2.md:131` — «пересечение двух кривых при r ≈ 60».
*Код:* `exp40_4_intersection.py:43–53` — `r_cross` = **первый нуль Δ(r) = cum_b(r) − cum_off²(r)**, где `cumshare` нормирует каждую кривую на 1. Это не пересечение исходных кривых, а пересечение их **накопленных долей**.

*Почему это важно:* исходный объект (точка, где `C_off²(l,r) = C_b(l,r)`) и новый (точка, где накопленные доли сравнялись) — разные величины; их «≈60» может совпасть, а может и нет, и при совпадении это совпадение **не то, что ставилось**. Автор это частично осознал: `bet_lineage` (`:102–113`) честно пересчитывает «≈60» на смешанных базах и пишет «в вердикт не входит».

*Проблема:* в `deviations_from_spec` (`exp40_4_intersection.py:135–145`) записаны только `D4_single_basis` и `D4_layers`. **Смена самого определения `r_cross` — то, ради чего существует пререгистрация, — как отклонение не зарегистрирована.** Итог: поле `prediction_check = {"predicted": 60, "observed": rc22, "verdict": hit/miss}` публикует «hit/miss» по ставке, сформулированной на другом объекте.

**Рекомендация:** завести `D4_r_cross_definition` с формулировкой старого и нового определения и пересчитать lineage старого определения на согласованной базе (данные для этого в `exp32tail_hessian_modes.json` есть) — тогда «hit/miss» станет честным.

### 3.2 E-40.4 — p-value пермутаций без поправки; 95 % CI смешан с sentinel

* `exp40_4_intersection.py:75`: `p_onesided = float((null_peaks >= peak).mean())` — доля без поправки. Канон самого проекта другой: `prism/nulls_and_stats.py:120,133` — `p = (1 + #{null ≥ obs}) / (B + 1)`. При B=1000 p может **выродиться в ровно 0.0**, а в проекте это исключено ⇒ числа из E-40.4 нельзя напрямую сравнивать с числами остальных серий.
* `exp40_4_intersection.py:83`: `boots.append(rcb if rcb is not None else 129.0)` — реплики без пересечения получают sentinel 129 (выше максимального индекса 128), и **этот sentinel участвует в квантилях** (`:84`). Итоговый `bootstrap_CI95` — не 95 % CI для `r_cross`: он смещён вверх на долю реплик без пересечения. Доля без пересечения публикуется отдельно (`:91`), но сам интервал от неё страдает.

**Рекомендация:** (1) p по конвенции проекта `(1+h)/(B+1)`; (2) CI — либо условный по репликам с пересечением, либо percentile-по-индикатору с явной пометкой; либо бутистрап CI по квантилю индикатора.

### 3.3 E-40.6 — объект `E_K` в коде ≠ `E_K` в `docs/paper.md` (срез и ранг) — ловушка на следующем шаге

| | Определение | Срез | Ранг |
|---|---|---|---|
| `docs/paper.md:391,393` | `E_K = J^(p)(J^(p))ᵀ` | «на срезе `p = p_0`, **fixP**» | «`rank(J^(p)) ≤ r = 16 < K`» |
| `docs/e40_todo.md` §8.1 | `E_K = J^(p)(J^(p))ᵀ` | «канонический срез» (не уточнён) | — |
| `exp40_6_R_profile.py:54–58,73–78` | `E_K = Σ_t P(p_t)J_t(P(p_t)J_t)ᵀ` | **per-position `p_t`**, пул по 128 позициям | ≤ 128 |

*Что совпадает:* код корректно считает `P(p)J = p⊙J − p(pᵗJ)` (`:58`) — это в точности исправленное `apply_P` из `prism/profiles.py` (моя прошлая находка M1), gauge-free ✓, `Jg_all` предвычисляется один раз на документ ✓.
*Что расходится:* в статье `E_K` — **однослойный** объект на фиксированном `p_0` с рангом ≤ 16; в коде — корпусный пул по позициям с per-position `p`, ранг до 128. Это **разные числа** под одним именем `R_can` (усечение до top-16 меняет и λmax, и tr ⇒ меняет и отношение).
*Почему пока не беда:* в `docs/paper.md` чисел `R_can` **нет** — статья определяет объект, но не публикует результат E-40.6 ⇒ сейчас это латентная ловушка, а не ложное число.

**Рекомендация:** до публикации чисел E-40.6 — либо привести §2.11.1 к формуле кода (корпусный ESG-грамиан на каноническом срезе `P(p_t)`), либо добавить в E-40.6 вариант `E_K` на fixP-склice и сослаться на него; текущую формулировку §2.11.1 («fixP», «rank ≤ 16») надо снять или оговорить.

### 3.4 E-40.2c — срез `K=64` построен на неренормализованном `p` ⇒ несопоставим с E-27.5

`exp40_2c_pos_slice.py:43–44`: `J = J[:, :K]`, `P = P[:, :K]` — усечение базиса U128 до 64 **без ренормализации** `p`. При `K=64` сумма `p` по усечённому базису < 1 ⇒ `P(p)` перестаёт быть матрицей softmax-якобиана ⇒ «gauge-free срез» для K=64 — не канонический срез, а субстохастическая проекция.

Сравните `exp27.5_pair_matrix.py:79–80`, где `pkv = P128[key][:K]; pkv = pkv / pkv.sum()` — ренормализация есть. Значит **`r_eff`/`sum_p2` при K=64 в E-40.2c и в E-27.5 — разные величины**, и сопоставление «ближе к E-27.5 (K=64)», заявленное в комментарии `:35`, не выполняется.

Влияние на главный вопрос сценария (плоскость `r_eff(t)`) — только на K=64-строку: по позициям `t` сравнение остаётся внутренне консистентным ✓. Сломано именно **сопоставление** с E-27.5.

**Рекомендация:** ренормализовать `p` после усечения (одна строка) либо явно назвать K=64-строку «неканонический субсрез» и убрать ссылку на E-27.5.

### 3.5 E-40.6 — covariate для partial-out берётся только со слоя L23 при маркировке «per-layer»

`exp40_6_R_profile.py:140,148`: `cov` считается как `mean_t max p_t` **на слое 23** и применяется ко всем слоям (`:153–156`). Поле называется `partial[str(L)]` с формулировкой «partial-out частотой токена (per-doc, per-layer)». Разброс `rho_diff_freq` по слоям объясняется **только** величиной `x = R_raw − R_can` (covariate одинакова), ⇒ слово «per-layer» вводит в заблуждение: ковариата слоевая только одна.

**Рекомендация:** либо `cov` per-layer (`load_layer(L)`), либо переименовать в `partial_L23_cov` и убрать «per-layer» из пояснения.

## 5. Что я проверил и нашёл **чистым** (исполнитель не покрывал)

1. **E-45 `_sparse_terms` — KL/TV.** Вывел из определения: для `v ∉ K` разность лог-вероятностей постоянна (`lse_b − lse_e`), откуда `KL(b‖e) = −Σ_k p_b,k Δ_k − (lse_b − lse_e)` и `KL(e‖b) = Σ_k p_e,k Δ_k + (lse_b − lse_e)`; члены `a_b`/`a_e` сокращаются ⇒ **код верен** (в `kl_be`/`kl_eb` знаки согласованы). TV = `½[Σ_{k∈K}|p_e−p_b| + (1−a_b)|e^{db}−1|]` — **тоже верен** ✓.
2. **E-40.2c — «перенос дословный».** Сверил `gram_r_eff` (`exp40_2c_pos_slice.py:38–64`) с `exp27_6_isolation.py:65–79` (`_gram`) и `:240–252` (`t6_eigengap`): формула gauge-free `Jg = Σ_k p_k J_k`, `Jb = p⊙(J − Jg)`, нормировка `Kf`, энтропийный PR `exp(−Σp log p)` — **совпадают построчно** ✓. Плюс встроенный контроль направления индекса `p_entropy` (`:63`) — независимая проверка класса B (реверс) ✓.
3. **E-40.6 — реализация критериев.** `(a′)` **не тавтология** (я проверил и снял своё подозрение: `R23 ≥ max(prof) − 1e-15` действительно ломается, если максимум не на L23); `(b)` пересчитывает `trough` внутри реплики ✓ и парность сохранена (один и тот же `idx` на все слои, `:108–113`); `(c)` сравнивает порядок значений и argmax ✓; bootstrap по документам с пересчётом профиля целиком ✓.
4. **E-45b — якобиан.** `analytic_J` (`exp45b_leaf_table.py:76–79`): `J_t = √D/‖h‖·(M − (Mû)ûᵗ)`, `M = W_U ⊙ g` — это **каноническое** определение проекта (`prism/exp38_hi_common.py:6,105`: `J(t) = (sqrt(D)/r_t) M_K (I − uuᵗ)`, лемма E-35), не самодельное ⇒ E-45/45b/46 меряют **тот же** лист, что и остальная серия ✓. `H` берётся как `model.model(...).last_hidden_state` ⇒ **уже после финального RMSNorm** (норма живёт внутри `model.model`), так что `H @ W_lmᵗ` — настоящие логиты модели ✓ (дополнительно раскрыто смещение токенизации к mainline в `:32`).
5. **Инфраструктура.** `_e38_cache._check_basis` падает громко при смешении позиционного и частотного кэша ✓; `jcache_path` при отсутствии файла возвращает канонический путь, и `torch.load` падает с внятным сообщением (не тихо) ✓; `except Exception` в E-28 — только в пиннинге ядер ✓; необсеянного RNG нет ни в одном из 117 скриптов (`np.random.default_rng()` без seed — 0 вхождений) ✓.
