## Находки

### 1. BLOCK — §3 «Окно на шаге t = `prompt + tokens[:t]`»: серверный контекст на 383 токена длиннее заявленного промпта
- **Где:** §3, п. про окно; косвенно §2 («окно = последние min(|last_tokens|, 64) принятых токенов»).
- **Что не так.** `request.prompt` = 64 id, но `response.tokens_cached = 447` во всех 32 файлах. По коду это размер **slot prompt**, а не prefix-cache: `tools/server/server-context.cpp:2118` — `res->n_tokens_cached = slot.prompt.n_tokens();` (а `n_prompt_tokens = slot.task->n_tokens()` = 64, `cache_prompt: false` в request, `tokens_evaluated: 64`). Т.е. сервер собирает slot prompt = 447 токенов из 64-токенного task-промпта: 383 токена добавляются сервером (шаблон/системный префикс). `init_sampler` (`server-context.cpp:419-427`) передаёт в сэмплер **все** токены slot prompt (`common_sampler_accept(smpl, id, false)` → `common/sampling.cpp:496` принимает в chain без условий). Следовательно реальное DRY-окно на шаге t — последние 64 из `(PREFIX(383−k) + USER(64) + SUFFIX(k) + tokens[:t])` = `USER[k+t:64] + SUFFIX + tokens[:t]`, а не `USER[t:64] + tokens[:t]` из ТЗ. Формула ТЗ точна **только при k = 0** (добавленные 383 — чистый префикс перед user-контентом, и ничего не дописано после). Для chat-форматной модели после user-контента почти наверняка есть suffix (открывающий ассистентский бегунок, k ≈ 3–5), и тогда окно сдвинуто на k токенов на **каждой** позиции: DRY считается по неверному контексту, весь перенос мусорный. ТЗ утверждает «сервер сам это эхом вернул» — но эхо (`response.prompt`) содержит только user-текст (276 символов, чистый BBQ-промпт), состав slot prompt из артефакта **не виден**: значение k артефактом не определяется. Усугубляет: формула ТЗ работает при k=0 лишь потому, что |USER| = 64 = `dry_penalty_last_n` ровно — хрупкое совпадение, при любой другой длине промпта ломается молча.
- **Чем подтверждено.** `jq`/python: `tokens_cached == 447` во всех 32 файлах, `len(request.prompt) == 64`, `response.prompt` — чистый user-текст; код `server-context.cpp:2110-2118`, `419-427`, `common/sampling.cpp:496`.
- **Как исправить (минимально, без нового эксперимента):** до переноса реконструировать полный slot prompt (447 id): либо взять его из лога/конфига harness, отправлявшего канон (S4-скрипты в репо должны содержать полные messages/system), либо применить chat-template из GGUF к канон-запросу и **заявить assert: длина == 447** (сравнить с `tokens_cached`). Затем окно = последние 64 из `(slot_prompt + tokens[:t])`. Если assert не сходится — стоп, а не «на глаз». Записать в §3 явный assert: `tokens_cached == len(slot_prompt)`, в prompt нет `-1` (LLAMA_TOKEN_NULL), и `prompt[10] == 0` **не фильтровать** (0 ≠ -1, сервер его принимает, `server-context.cpp:423`).

### 2. MAJOR — §4 контроль «penalty := 0 обязан ошибиться ровно на флипах» не проверяет перенос DRY вообще
- **Где:** §4, «Контроль (обязателен…)».
- **Что не так.** При `penalty := 0` adjusted = logprob, `argmax_C = top1` тождественно (top1 ∈ C всегда) — контроль проверяет только **согласованность полей артефакта** (cp[t] ↔ tokens[t], порядок top_logprobs, корректность `logprob`), код DRY при penalty=0 не исполняется вовсе. Любой неверный перенос DRY контроль проходит. Конкретные дырявые реализации, проходящие контроль:
  (a) окно `prompt + tokens[:t-1]` (off-by-one по t) — контроль окно не трогает;
  (b) пропуск шага 1 (rep_limit := 64 всегда, breaker'ы `\n : " *` игнор) — с частотой таких breaker'ов в тексте даст ложные UNEXPLAINED и ложное «H0 опровергнута»;
  (c) штраф на `rat(last_n_repeat-1-i)` вместо `rat(last_n_repeat-2-i)` (шаг 3, `:3545`) — штраф на токен, **оканчивающий** блок, а не продолжающий.
  Единственный требуемый unit-тест (доковый пример) — один маленький кейс; ветку Z-бокса (else-ветка `lt/rt`, `:3500-3526`) и логику breaker'ов он не покрывает гарантированно.
- **Чем подтверждено.** Код `:3486-3526` (Z-алгоритм с двумя ветками), `:3543-3553` (шаг 3).
- **Как исправить.** Добавить дифференциальный тест на реальный C++-код: в репо уже есть `llama_sampler_init_dry_testing` (`src/llama-sampler.cpp:3690`) и `copy_state` (`:3606-3612`) — мелкий тест-бинарник, который на ~1000 случайных окнах (включая: breaker на расстоянии <2 от конца, multi-token breaker, окно короче 64, `last_n_repeat <= allowed`) считает map штрафов через `llama_sampler_apply` и сравнивает с python-портом. Плюс независимый O(n²) наивный оракул (прямо: для каждого кандидата — максимальный повтор ≥ allowed внутри rep_limit) как второй контрольный. CPU-секунды, не новые запросы.

### 3. MAJOR — §4 корзины не взаимоисключающи, и правило 1 противоречит гейту правила 4
- **Где:** §4, определения `EXPLAINED/INCONCLUSIVE/UNEXPLAINED/TIE` и правила 1–4.
- **Что не так.**
  (a) Позиция с `max_C(adjusted) < lp20` **и** `argmax_C != emitted` попадает одновременно в `INCONCLUSIVE` и `UNEXPLAINED` → правило 2 («UNEXPLAINED ≥ 1 ⇒ H0 опровергнута») срабатывает ложно, хотя истинный виновник — невидимый хвост vocab. Аналогично TIE, включающий emitted, дублируется с EXPLAINED.
  (b) Правило 1 допускает INCONCLUSIVE-флип: 1 inconclusive-флип = 1/6144 ≤ 1% ⇒ по правилу 1 «H0 подтверждена», а гейт правила 4 («>= 15 из 16») одновременно запрещает утверждение — самопротиворечивый исход, т.е. пространство для постфактум-переформулировки. Гейт «15/16» при этом **не спасает слабый результат** (хорошо): 6 UNEXPLAINED ⇒ правило 2 уже отвергает H0, гейт избыточен, но и не нужен как «аварийный выход».
- **Чем подтверждено.** Логика определений ТЗ (формальная проверка): при `max_C(adjusted) < lp20` наружный токен с `logprob ∈ (max_C(adjusted), lp20]` выигрывает глобально, но позиция уже помечена UNEXPLAINED по второму определению.
- **Как исправить.** Явный приоритет: `INCONCLUSIVE` (max_C < lp20) → иначе `TIE` → иначе `EXPLAINED` (argmax == emitted) → иначе `UNEXPLAINED`. В правиле 1 добавить требование «все 16 флипов — EXPLAINED». Гейт правила 4 оставить, но сформулировать как «при любом UNEXPLAINED ≥ 1 или флипе вне EXPLAINED — утверждение запрещено», без промежуточных состояний.

### 7. INFO — законность правила INCONCLUSIVE (п. 2 задания): контрпримера нет
- **Где:** §3, абзац про кандидатов `C`.
