## 0. Чем мерил (три критерия, все проверяемы командой)

1. **Вес claim'а**: цитируется ли номер в `docs/paper.md`/`docs/ref-exp.md`, и это утверждение или
   скобка «серия E-65…E-72». Считал по строкам с `E-<n>` **и** slash/range-формами (`E-65/65b/66`),
   иначе двойное упоминание теряется: наивный `\bE-66\b` даёт 0, а реально E-66 стоит в L1228.
2. **Наличие артефакта**: `results/eNN*`, `results/expNN*`, плюс диски вне git (`/data`, `/tmp/recovered`).
3. **Цена перезапуска**: `grep -c from_pretrained` по скрипту — 0 ⇒ numpy-only (минуты), ≥1 ⇒ модель
   (0.8B на CPU — десятки минут, 4B — часы и на грани RAM: 62 ГБ всего, 17 ГБ доступно).

Вердикты: **высокая** (число держит вывод, перезапуск реален) / **средняя** (число цитируется, цена
выше) / **низкая** (не цитируется, но идея/инфраструктура нужна) / **не нужно** (мусор либо уже есть).

## 2. Что это значит по существу

- **Пять «высоких» — это не украшение, а несущие конструкции**: E-55/E-56 держат *опровержение*
  «глобального тока/Δ(k)-закона», E-63 — нуль-батарея, на которой стоят выводы E-60/E-62, E-80 —
  «lane — фантом», E-79 — единственная *независимая* проверка J-плоскости другим механизмом.
  Если хоть одно из них — артефакт кода, рушится не строчка в paper, а раздел.
- **Четыре «высоких» дешёвые**: 55, 56, 63, 80 — `model_load=0`, т.е. numpy по уже лежащим
  артефактам/кэшам. Их перезапуск = десятки минут на весь батч, без моделей и без GPU.
- **E-79 — особый случай**: он не «дорогой», он **сломанный** (один вектор вместо 32 ридоутов
  JL-скетча). Число cos 0.44–0.52, скорее всего, получилось из суммы строк якобиана; пока не
  переделано — claim в paper стоит на коде, который делает не то, что написано.
- **E-68 блокирует E-70a**: судья судит тексты harness'а, у которого (а) `HARNESS.json` отсутствует
  и (б) DynamicCache мутирует на месте. Значит «тройная панель обязательна» — вывод, у которого
  сейчас нет ни одного воспроизводимого прогона панели.
- **Класс «низкая» ≠ выбросить**: E-75/E-77/E-91 не перезапускаем (не цитируются, исполнение или ось
  сомнительны), но идеи из них уходят в `RERUN_SCRIPT_TRIAGE.md` §Г (template-чувствительность,
  масса слоя, корпусной рандом-контроль).

## 3. Порядок работ, который из этого следует

1. **Батч 1 (numpy, без моделей, ~1 час):** E-56 → E-55 → E-63 (9 клеток) → E-80 (+80b/80c).
   Все четыре — `model_load=0`; входы: `results/AT0/*`, кэши в `/data`, `e64_gpu.py` (CWD-relative
   путь — запускать из корня репо).
2. **Батч 2 (переделка кода, потом прогон):** E-79 (32 отдельных backward), E-68 (свежий кэш на
   кандидата + h-путь после выбранного токена) → E-70a.
3. **Батч 3 (модели, 0.8B):** E-65/65b/66/69/73 — по одной задаче за раз через `./run_one.sh`.
4. **Не трогаем:** E-24, E-67, E-78*, E-90, E-75, E-81* (реанализ из готового артефакта), E-72*,
   E-77*, E-91 — до отдельного решения.

**Оговорка (grey zone 60–95):** для всех номеров ≥60 числа в `paper.md` — «подозреваемый, а не
ориентир». Совпадение перезапуска с paper не очищает claim (код могли подогнать под вывод); чистка
только через независимый пересчёт — другой скрипт, другая реализация нуля или аналитический вывод.
Для 55/56/80 это выполнимо (у 80 уже есть 80b/80c как другой нуль), для 63 — через T-17 на другом
эстиматоре.
