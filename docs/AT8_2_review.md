## 2. Новые находки: TZ против кода

### 2.1 ⚠️ Главное: пре-рег пула (16 доков, ≥3 домена) молча заменён на 14 / 4 — и это меняет исход

**TZ v1.0 §6:** «первые 4 прошедших на домен → 16 доков (4×4). Fallback: … нужно **≥12 доков и ≥3 домена**».
**TZ §15 п.12** прямо фиксирует фактический пул: «wiki 10 / math 2 / code 7 / chat 6 → **14 доков (4/2/4/4)** — в рамках fallback».
**TZ §8:** гейт «≥ **12 из 16**».

**Код (машина r2):**
```python
DOMAINS_MIN = 4
if len(passed) < 2:
    raise SystemExit(f"INSUFFICIENT_POOL: домен {d} < 2 доков "
                     f"(DOMAINS_MIN=4 — все 4 домена обязательны)")
```
Плюс `INSIDE_PASS_FRAC = 0.75` → `ceil(0.75·14) = 11`, а не 12/16.

То есть **исполняемый пре-рег — это §20 (машина r2), а не §6**. §20 честно объявляет F7, но §6/§8/§15 продолжают утверждать обратное, и в документе нет пометки «§6 superseded by §20». Читатель TZ получает 16/≥3/12-of-16; код делает 14/4/11-of-14.

**Почему это не косметика.** Пул r1 (14 доков, math=2) достижим **только** под правилом r1 (`DOMAINS_MIN=3`). Под правилом r2 math с 2 прошедшими даёт `SystemExit` — прогона не было бы вовсе. А вердикт r1-машины на этом пуле был `LOOP_RESPONSE_DECAYS`. Цепочка:

```
правило пула r1 (≥3 домена)  →  math=2 допускается  →  14 доков
                              →  прогон существует  →  r1: DECAYS
правило пула r2 (все 4, ≥2)  →  INSUFFICIENT_POOL   →  прогона нет
```

Это не обвинение в подгонке — F7 был мой же пункт, и «все 4 домена» методологически строже. Но факт надо зафиксировать явно: **финальный вердикт стоит на пуле, который финальное правило пула запрещает.** И `DOMAINS_MIN=4` вместе с `len(passed)<2` делает мёртвой ветку fallback-филлеров из соседнего домена (`k=2` → `next_d`), которая в TZ §7 описана как рабочий путь для math. Код её содержит, но при `DOMAINS_MIN=4` она срабатывает только если домен имеет ровно 2 — что как раз и есть math, так что ветка жива. Хорошо, снимаю это: `k=2` допускается (`<2` — стоп), fallback работает. Остаётся расхождение 16↔14 и 12/16↔11/14.

**Патч (текст, не логика):** в §6/§8/§15 добавить строку «superseded §20 F7: фактический пре-рег — все 4 домена, ≥2 дока на домен, `ceil(0.75·n_docs)`; фактический пул 14 (4/2/4/4)». И в claim — поле `pool_rule: "all-4-domains, >=2 per domain"` рядом с `n_docs/n_domains`, чтобы артефакт был самообъясняющим.

### 2.2 ⚠️ `e_generic` объявлен exploratory, но управляет веткой вердикта; и скан по дозам не устранён

**Claim:** `e_generic_note = "exploratory/диагностика … в вердикте используется e_spec"`.
**Код:**
```python
else:
    mg = max(c["ci_low"] for c in gci.values())   # ВСЕ дозы
    if mg > dmin_near:
        v = "GENERIC_INSERTION_EFFECT"
```

Два дефекта в одном месте:

1. **Статус.** `e_generic` — не диагностика: при незначимом `e_spec` он один выбирает между `GENERIC_INSERTION_EFFECT` и `NO_LOOP_SPECIFIC_EFFECT`. Ответка §3.5 сама пишет: «Ветка GENERIC не сработала … отдельный нуль вердикт не меняет» — т.е. автор знает, что ветка есть. Значит `e_generic_note` ложен, и мой пункт 3.5 закрыт не полностью: я просил либо пометить как exploratory **и вывести из вердикта**, либо дать свой нуль. Сделана только пометка.

2. **F2 применён наполовину.** Множественность доз убрана для `e_spec` (`PRIMARY_DOSE=16`), но `mg = max(...)` по четырём дозам — это ровно тот скан, ради которого вводился F2. Четыре шанса пересечь порог вместо одного, без поправки. На store `mg = 0.1160` (n=16) < 0.1480, исход не меняется; при другом шуме — меняется.

**Патч (минимальный, вердикт на текущих данных не двигает):**
```python
mg = gci[pn]["ci_low"]          # primary dose, симметрично e_spec
```
и переписать note: «`e_generic` — вторичный вердиктный контраст (ветка GENERIC) с некалиброванным нулём; читается как индикативный, не как строгий тест». Либо, если хочется честной строгости, — вывести GENERIC из дерева в тег и оставить 4 исхода. Оба варианта допустимы, но выбрать надо **до** следующего прогона.

### 2.3 ⚠️ `n_fwd` выводится, а не измеряется; `full_run.wall_s` — молчаливый `None`

```python
n_fwd = an["n_docs"] * (1 + 3 * len(an["bootstrap"]))
```
Это арифметика *ожидаемой сетки*, выданная за факт прогона. Ответка §3.2 говорит «подтверждено: лог (182 `CE=`), store, trackio `n_fwd=182`» — но код ни один из этих источников не читает для `n_fwd`. Если прогон был partial + resume, или сетка поменяется, число останется «правильным» независимо от реальности. Тот же класс, что мой исходный 3.2 (98 из протухшей сметы): число не привязано к источнику.

`wall_s` парсится regex’ом по `RUNLOG`. Если лог ротирован/перезаписан реанализом (`RUNLOG` открывается `"w"` в `run_main`, а `reanalysis_main` его не трогает — ок) или строка не совпала — тихо `None`, без флага.

**Патч:**
```python
# факт, а не ожидание
n_fwd_log = len(re.findall(r"\bCE=", log_text)) if log_text else None
n_fwd_store = sum(1 + 3*len([k for k in store[dn] if k.startswith("n")]) for dn in docs)
full_run = dict(n_fwd_expected=..., n_fwd_log=n_fwd_log,
                n_fwd_store=n_fwd_store, wall_s=..., wall_source="log|absent")
assert n_fwd_log == n_fwd_store == n_fwd_expected, "n_fwd mismatch"
```
Три числа рядом + ассерт. Стоит миллисекунды, закрывает пункт навсегда.

Моё предложение было ошибочным. Остаётся только требование согласовать статус с ролью в дереве (2.2).
